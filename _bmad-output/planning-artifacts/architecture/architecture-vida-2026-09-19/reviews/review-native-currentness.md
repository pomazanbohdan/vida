# AD-20 native-client currentness and security review

Reviewed 2026-09-20. Scope: [ARCHITECTURE-SPINE.md](../ARCHITECTURE-SPINE.md) AD-20 and adjacent platform rules; [ADR-0014](../../../../../docs/03-architecture/decisions/ADR-0014-native-only-vida-clients.md), [native-client requirements](../../../../../docs/02-requirements/native-client-requirements.md), [platform NFR](../../../../../docs/02-requirements/platform-nfr.md), and [stack-selection brief](../../../../../docs/03-architecture/stack-selection-brief.md). Lens: current upstream platform facts, security boundaries and stale first-party browser requirements. No source document was edited.

## Verdict

**Conditional pass, no stale browser-client requirement found in current normative docs.** AD-20 faithfully separates installed VIDA clients from City Portal public web and independent protocol implementations. It does not silently approve or reject Tauri: “installed” is a distribution fact, whereas “native” may mean a native-widget UI, compiled native executable, or OS-integrated offline app; OQ-0008 correctly holds that user/product choice. Two refinements are needed before the shell/security prose is taken as an implementation contract.

## Findings

### P1 — Tauri hostile-content gate must test same-context script execution

`stack-selection-brief.md:44,55` now correctly names `AppManifest::commands`, per-webview allowlists, narrow plugin capabilities, CSP and Rust rechecks. This fixes the default Tauri app-command exposure problem: [Tauri Capabilities](https://v2.tauri.app/security/capabilities/) says registered `invoke_handler` commands are usable by all windows/webviews by default unless constrained. Yet capability boundaries attach to window/webview and origin; hostile document/forum HTML rendered in a *privileged* webview can execute with that webview's available IPC if an XSS/content-sanitization failure occurs. A negative test against a separate unprivileged webview alone would pass while leaving this path open. Specify non-executable/sandboxed rendering or separate low-privilege webview for untrusted content, and test injected script in the actual document/forum rendering context attempting both a privileged command and a cross-Space read. Rust must still authorize each Space/object/action on every invoked command. This is a security proof gate for a possible Tauri selection, not a claim that Tauri itself is unusable. [Tauri Runtime Authority](https://v2.tauri.app/security/runtime-authority/), [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), and [OWASP MASWE-0033](https://mas.owasp.org/MASWE/MASVS-PLATFORM/MASWE-0033/) support the boundary; MASWE is mobile-specific guidance, not a Windows compliance certification.

### P2 — Structural seed says “native UI” before UI toolkit is selected

`ARCHITECTURE-SPINE.md:265–266` labels the iOS and Android directories `# native UI and ... lifecycle/policy`, while AD-20, ADR-0014 and OQ-0008 explicitly defer the meaning of “native” and the UI toolkit. The live candidate is Flutter Android/iOS: [Flutter's architecture overview](https://docs.flutter.dev/resources/architectural-overview) says release apps compile to native machine code and use OS embedders, but Flutter normally draws its own widget tree rather than the host OS's UI widget library. Thus “native UI” could accidentally preselect SwiftUI/UIKit and Jetpack/Views, contradicting the candidate table. Rename seed comments to “installed iOS/Android shell and OS lifecycle/policy” or similarly neutral wording. Keep whether OS-native widgets are mandatory as OQ-0008.

## Verified facts and boundaries

- [Tauri architecture](https://v2.tauri.app/concept/architecture/) describes an installed desktop app combining Rust with HTML in an OS WebView; on Windows it uses [WebView2](https://v2.tauri.app/reference/webview-versions/). It is **not** a browser/PWA release merely because its UI uses a WebView. Whether it satisfies the user's desired “native” experience is not determined by the framework and remains OQ-0008. The draft correctly removes browser-UI reuse as a Windows selection criterion.
- [Flutter's current supported-platform matrix](https://docs.flutter.dev/reference/supported-platforms) includes Android, iOS and Windows; Flutter's own rendering does not prove OS background execution, secure storage, offline data durability or accessibility quality. AD-9, REQ-CLIENT-005 and STACK-G1/G6/G7 correctly require per-OS release-build/device evidence.
- The first-party browser/PWA/Wasm/gateway *client* is excluded in AD-20, ADR-0014, REQ-CLIENT-001 and NFR-PLAT-001. No contradictory live browser-client requirement was found in `docs/01-product`, `docs/02-requirements`, `docs/03-architecture` or `docs/04-specifications`. Wasm as a possible managed App-logic sandbox under ADR-0009 is a different concern and is not a browser client. City Portal public web, integration services, nodes and independent protocol clients remain explicitly in scope.
- “Offline” in AD-20 is bounded correctly: synchronized local read and permitted local intent do not mean remote delivery or another authority's acceptance without connectivity. AD-16/ADR-0003 still require immediate enforcement of *received* revocation and leave unreadable/disconnected-device limits explicit. OWASP [MASVS storage](https://mas.owasp.org/MASVS/controls/MASVS-STORAGE-1/) and [authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) support security tests, not a browser ban, UI toolkit choice, universal offline timeout or remote wipe promise.

## Suggested gate evidence

1. OQ-0008 records separately the supported OS list and the user's meaning of “native” (installed/OS-integrated versus host-native widget rendering); Tauri remains conditional until then.
2. Any Tauri spike proves an explicit app-command manifest and least-privilege capability map, no privilege aggregation across the untrusted renderer, same-context XSS→IPC/cross-Space negative tests, and Rust authorization independent of UI state.
3. Every selected installed OS runs the three-App offline/read-write/restart/reconnect and revocation suite; successful delivery or authority acceptance is never inferred from a local pending state.
