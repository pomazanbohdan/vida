# Reviewer gate — Owner appointment/removal reality and currentness

Reviewed 2026-09-20: `ARCHITECTURE-SPINE.md` AD-6, ADR-0001/0002/0003, and `space-membership-contract.md`. Verdict: **conditional pass for the intended governance model; not implementation-ready**. The current documents consistently reserve appointment/removal of Owners to a current built-in Owner, keep ordinary resource ACL separate, and acknowledge offline-copy limits. The gaps below still permit divergent or unsafe implementations.

## High findings

1. **First-Owner bootstrap is unstated.** AD-6 says only a *current* Owner may appoint *another* Owner (`ARCHITECTURE-SPINE.md:118`), and ADR-0002 requires every shared Space to have at least one Owner (`ADR-0002-default-role-presets.md:107,109`). The contract defines `RoleAssigned` only under the same existing-Owner authorization (`space-membership-contract.md:40`). A literal implementation cannot create the initial shared Space/Owner. Define a distinct, authority-accepted `SpaceCreated`/genesis transition that atomically assigns exactly one initial built-in Owner to an authorized creator; specify how creation authorization is checked and prevent reuse as a later Owner-appointment bypass. This is not a request to weaken the Owner-only appointment rule for an existing Space.

2. **Owner-cloned custom role still has an undefined governance ceiling.** AD-6 says an Owner clone “does not confer governance” (`ARCHITECTURE-SPINE.md:118`). ADR-0002 expressly excludes built-in Owner status/cardinality and *removal* from a clone (`ADR-0002-default-role-presets.md:75-79`), yet the base Owner preset lists transfer, security, keys and Space deletion among “all capabilities” (`:59`). One team could exclude only removal/appointment while another excludes every Space-governance verb. Define the non-clonable Owner-governance capability set (appointment/removal, transfer, policy control, key/security authority, Space deletion as intended), or explicitly state which are clonable. Add tests for each verb and aliases. OWASP's [Authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) supports checking permissions on every request, but does not decide VIDA's capability set.

## Medium findings

3. **“Derivative delegations” needs traceable provenance and a conformance gate.** AD-6 and ADR-0003 require one logical accepted transition to revoke all grants and derivative delegations (`ARCHITECTURE-SPINE.md:118`; `ADR-0003-offline-revocation.md:144`). This is a sound required result, not yet an enforceable algorithm: delegated ServicePrincipal grants may have multiple grant parents or a separate account, and the documents do not define whether revocation follows provenance, issuer, subject or explicit Space policy. Define delegation-edge IDs/parentage, multi-parent validity, and post-cut authorization tests before independent implementations claim full removal. Distinguish truly independent ServicePrincipal grants from grants derived from the removed membership.

4. **Owner-invite activation rechecks role, but not explicitly the current critical-policy quorum.** The contract correctly calls `InviteIssued` an intent and rechecks the inviter's current Owner status on activation (`space-membership-contract.md:42`); it also permits a policy-defined quorum for Owner appointment (`:40`). A quorum collected under an old roster/policy could be reused after it changes. Require authority to evaluate the *current* appointment policy/quorum and policy version at the `RoleAssigned(Owner)` acceptance point, or explicitly defer appointment until OQ-0031/OQ-0033 define the rule.

5. **Atomic logical revocation may temporarily pause valid writes.** ADR-0003 allows asynchronous key envelopes (`ADR-0003-offline-revocation.md:159`) but forbids old-grant authorization for new operations after the accepted cut (`:144`). This is secure if an affected scope cannot write with old epoch while new keys are unavailable; the availability consequence is not stated. Specify `rekey pending` behavior and a no-old-epoch write fixture, rather than implying both immediate access cut and uninterrupted collaboration. Do not equate logical authority acceptance with completed physical key distribution.

## Checks that pass

- Resource ACL `deny` cannot mutate Owner-governance authority; ADR-0001 now explicitly separates the domains (`ADR-0001-layered-access-control.md:56-61`). Admin policy-edit rights expressly exclude Owner-governance policy (`ADR-0002-default-role-presets.md:60,110`).
- `MemberRemoved` plus grant/delegation cut replaces mere role demotion; authority must check current built-in Owner at acceptance (`space-membership-contract.md:40-42`). The inviter-loses-Owner-before-activation case is explicitly rejected.
- The client promise is bounded to managed surfaces *after* revocation is learned, with best-effort cache purge; the documents do not claim remote erasure of offline devices, OS banners or copied plaintext (`ARCHITECTURE-SPINE.md:118`; `ADR-0003-offline-revocation.md:110`).
- The new governance text adds no named technology-version claim. The linked [OWASP Business Logic Security guidance](https://cheatsheetseries.owasp.org/cheatsheets/Business_Logic_Security_Cheat_Sheet.html) does support current-state/role rechecks and guarding alternate entry points; its guidance is correctly not presented as the source of VIDA's Owner-only product rule (`ADR-0002-default-role-presets.md:155-157`).
