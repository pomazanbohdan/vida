# Release-1 Web technology-currentness review — 2026-09-25

Scope: current named technology fit in `ARCHITECTURE-SPINE.md` (especially AD-1, AD-8–9, AD-11, AD-20, Stack and Deferred) and `ADR-0021-static-web-client-in-release-1.md`. This is an evidence review, not a new product decision or a completed Web prototype.

## Verdict

**Conditionally feasible; not implementation-proven.** Static Flutter Web hosting, Rust→browser Wasm and Iroh browser↔native traffic over a relay are individually supported by primary documentation. The combined VIDA profile—same Core semantics, durable offline browser state, authorized Android↔Web sync, full Core Apps and E2EE calls—has not been demonstrated in this repository. The documents mostly state these as conformance gates, which is appropriate; `status: final` on the spine must not be interpreted as technical readiness. `rg --files` on 2026-09-25 found no `pubspec.yaml`, `Cargo.toml`, Wasm build, Flutter bootstrap or service-worker implementation in this workspace.

## Findings, highest impact first

1. **[High] Offline *reopen* is an extra deliverable, not a consequence of static hosting.** AD-20 promises locally available Web data/actions offline, and ADR-0021 requires offline/reopen/reconnect convergence. `flutter build web` produces static deployable assets, but Flutter says it no longer generates/manages a caching service worker by default. Without an explicit offline app-shell caching/update strategy, a cold browser reopen without network may not load the application even if data survives in IndexedDB/OPFS. Define the service-worker/app-shell and cache-version rollback behavior as a separate Web release fixture; test cold reopen, updated assets, cleared cache, interrupted upgrade and an existing locally saved unsynced operation. Sources: [Flutter Web build/deploy](https://docs.flutter.dev/deployment/web), [Flutter Web FAQ, service workers](https://docs.flutter.dev/platform-integration/web/faq), [MDN service-worker offline model](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers).

2. **[High] Browser-local persistence cannot by itself satisfy the same durable-save claim as native storage.** ADR-0021 correctly lists quota/eviction and last-copy gates, but its Device-equivalence wording can be read as equivalent durability. Browser origin storage is best-effort by default; persistence can be requested but users can still clear it, and IndexedDB `complete` need not mean a power-loss-safe disk flush on every browser. In particular, the *only* local copy of an unsynced Resource is a different risk class from a replicated copy. Specify per-browser storage mode, transaction/commit receipt, quota/error handling, last-copy warning/recovery/export and user-facing “saved locally” semantics before accepting the parity claim. Sources: [MDN storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [MDN IndexedDB durability caveat](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB).

3. **[High] Rust/Wasm boundary is supported in principle, but the whole `vida-runtime` is not proven browser-compatible.** Iroh documents a browser Wasm build with `iroh = { version = "1", default-features = false }` and recommends an application-specific `wasm-bindgen` wrapper; it does *not* publish a browser NPM package. Current flutter_rust_bridge tooling advertises Web/Wasm generation, but also documents worker/thread limitations and a separate `build-web` step. Therefore “one production `vida-sdk` facade” is an architectural contract, not proof that the same native runtime crate, FFI generator or execution model compiles and behaves on browser Wasm. Choose and pin a concrete bridge profile only after a small Core+Iroh+storage+Flutter Web spike, including Safari/Firefox and cross-origin-isolation/worker options. Sources: [Iroh browser guide](https://docs.iroh.computer/languages/wasm-browser), [flutter_rust_bridge current quickstart](https://cjycode.com/flutter_rust_bridge/quickstart), [flutter_rust_bridge Wasm limitations](https://cjycode.com/flutter_rust_bridge/manual/miscellaneous/wasm-limitations).

4. **[Medium] Relay-only Iroh Web claim is current and correctly scoped; deployment proof remains open.** Iroh explicitly says all browser connections to other endpoints traverse a relay and remain end-to-end encrypted. The 1.2.0 Iroh release exists (2026-09-09). A statically hosted Web bundle can therefore participate as a client, but static hosting alone does not operate the required VIDA relay, distribute its address, or make it durable delivery. ADR-0021 and AD-1 correctly separate those concerns. Preserve a Web↔Android interoperability fixture that fails when the relay is unavailable, including honest pending/offline UI; do not present Web as direct P2P. Sources: [Iroh browser limitation](https://docs.iroh.computer/languages/wasm-browser), [Iroh self-hosted relay](https://docs.iroh.computer/iroh-services/relays/self-hosted), [Iroh 1.2.0 release](https://github.com/n0-computer/iroh/releases/tag/v1.2.0).

5. **[Medium] Full Release-1 Web calls and four-shell parity are scope gates, not supported by the Iroh browser examples.** The Iroh browser echo/chat/blob examples show transport/protocol feasibility, not VIDA's media adapter, background ringing, Web key custody or E2EE group calls. AD-35 and ADR-0021 already keep these as separate release proofs. Keep the release commitment, but require an explicit browser media/security fixture and a failed-gate status until there is a working Web↔native call prototype; avoid citing the Iroh browser chat example as call evidence. Sources: [Iroh browser examples index](https://github.com/n0-computer/iroh-examples), [Iroh browser guide](https://docs.iroh.computer/languages/wasm-browser).

## Internal consistency

- No contradiction between AD-1/AD-20 and ADR-0021 on Web transport: each says relay-only browser, direct-first native, no paid Hosted Space requirement.
- ADR-0021 explicitly supersedes the old browser exclusion in ADR-0014 and browser post-v1 consequence in ADR-0020; these older decisions remain historical, not evidence against the new scope.
- “Full-featured” is a product requirement. The documents correctly name per-platform gates; they should be surfaced in epic/story acceptance rather than being treated as already met by library selection.
