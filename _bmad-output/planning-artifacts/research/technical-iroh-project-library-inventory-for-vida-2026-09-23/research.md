# Бібліотеки й архітектурні патерни Iroh-проєктів

**Питання рішення.** Які компоненти з дослідженого каталогу варто перевіряти в однакових VIDA-прототипах? Це не ADR і не затвердження production-залежностей. Поточний транспортний інваріант VIDA — Iroh core 1.2; ролі, прийняття операцій, конфлікти й durable delivery залишаються контрактами VIDA ([stack brief](../../../../docs/03-architecture/stack-selection-brief.md), [ADR-0005](../../../../docs/03-architecture/decisions/ADR-0005-iroh-transport-foundation.md)).

## Короткий висновок для рішення

1. **Не існує одного готового Iroh-«супер-стека».** У прикладах Iroh виконує transport; автори окремо добирають CRDT/merge, op-log, SQLite/redb/Fjall, E2EE, blobs, outbox і platform bindings. Повторюваність бібліотеки є сигналом для прототипу, не доказом її придатності для VIDA.
2. **Найближчі порівняння для VIDA:** Irokle ↔ iroh-db ↔ Knot для signed/revision/sync core; Loro (Synesis) ↔ Automerge (echo, Kith) для документів; iroh-blobs ↔ альтернативний verified transfer для файлів; OpenMLS (Arachne) ↔ групова криптомодель iroh-beekem; iroh-ffi та UniClipboard/Engine як різні FFI/host-core референси. Engine — не доведений generic SyncLog provider ([окремий digest](digests/uniclipboard-engine-r6-luna.md)). Це **кандидати на однакові fixtures**, а не єдині допустимі реалізації.
3. **Найсильніший поточний risk signal — не номер версії.** README релізної ревізії `iroh-blobs` 0.103 прямо каже, що ця версія ще не вважається production quality; рекомендована там 0.35 залежить від Iroh 0.35 і не є простою заміною поряд з Iroh 1.2 ([README 0.103](https://github.com/n0-computer/iroh-blobs/blob/e82cbdcbdac9a78033174aad55e3199b2cf4c0dc/README.md), [0.35 manifest](https://github.com/n0-computer/iroh-blobs/blob/v0.35.0/Cargo.toml)).[1][2] Сам факт `<1.0` **не відсіює** бібліотеку.
4. **Activity треба читати по шарах.** У 30-денному зрізі `iroh` мав 27 default-branch комітів; `iroh-blobs`, `iroh-docs`, `iroh-gossip`, `iroh-ffi` — 0, проте деякі мали merged PR за 90 днів. `pushed_at`, зірки й загальна кількість issue самі не є оцінкою активної підтримки чи якості ([API-методика й таблиця](digests/upstream-protocols-r1-root.md)).

Це каталог, **не** доказ поточного стану.
- Три Luna-агенти незалежно перевірили storage/sync, messaging/security, network/mobile репозиторії; root перевірив офіційні upstream manifests і README. Перший прохід має 18 application repos та чотири upstream protocol libs; другий прохід розширює вибірку; поглиблення охоплює також дві editor CRDT libraries. Деталі, посилання й невизначеність у [storage digest](digests/storage-sync-r1-luna.md), [messaging digest](digests/messaging-security-r1-luna.md), [network digest](digests/network-mobile-r1-luna.md), [upstream digest](digests/upstream-protocols-r1-root.md).

- Зрілість оцінюється за функціональністю, тестами/fixtures, розвитком, реакцією на issue, сумісністю, ліцензією, security evidence та власними застереженнями розробників. Semver `<1.0`, зірки та число відкритих issue не є самостійним verdict.
- Другий прохід додав [storage/content](digests/storage-sync-r2-luna.md), [messaging/media](digests/messaging-security-r2-luna.md) і [network/mobile](digests/network-mobile-r2-luna.md) digests. Це вибірка релевантних реалізацій, не повний аудит усіх URL каталогу.

[Nexa Android](https://github.com/open-nexa/nexa-android/blob/main/app/src/main/AndroidManifest.xml) — окремий від NexaPipe app-shell reference: Android-only/arm64, min SDK 26, `VpnService` foreground service; Kotlin налаштовує TUN та reconnect, передає file descriptor у Rust. Сам client crate NexaPipe цього platform proof не дає. Це VPN/TUN сценарій, не готова VIDA mobile sync реалізація ([детальний digest](digests/network-mobile-r2-luna.md)).

**UniClipboard/Engine deepening.** Після окремої перевірки [Rust host/core facade, lifecycle та release provenance](digests/uniclipboard-engine-r6-luna.md) Engine лишається сильним reference для platform boundary. GitHub REST-зріз 23.09.2026: 401/849 комітів `main` за 30/90 днів (включно з merges); це високий темп, але не доказ generic sync або стабільності. [Release rc.18](https://github.com/UniClipboard/Engine/releases/tag/v1.1.0-rc.18) має конкретні lifecycle/durable-delivery fixes; [issue #101](https://github.com/UniClipboard/Engine/issues/101) показує відкриту затримку send через індексацію, а [issue #70](https://github.com/UniClipboard/Engine/issues/70) описує невирішений сценарій пропущеного reconnect/resume та membership backlog.[17] Останній є ризиком і планом repair, не доказом несправності кожної передачі clipboard; його треба перевірити на реальних пристроях перед будь-яким reuse. Власний clipboard wire protocol, optional HTTP rendezvous для pairing та pinned Iroh/blobs tuple не переносимо в VIDA без окремого суміснісного й безпекового gate. [Офіційні pairing docs](https://docs.uniclipboard.app/guides/pairing) розділяють default mobile `Regular sync` через HTTP companion та `Device connection (Experimental)`; тому UniFFI-артефакти Engine не є доказом готового рівноправного mobile Iroh sync, хоча experimental path варто перевірити в прототипі. Якщо VIDA пізніше додасть cross-device clipboard App, можна оцінити code reuse саме для цієї функції з явною згодою на capture/import; Messenger, Notes і Projects не мають успадковувати clipboard data model.

**UniClipboard follow-up 23.09.** [Окремий delta digest](digests/uniclipboard-mobile-and-governance-r7-luna.md) уточнює, що в UniClip source вже є native wrapper над версійованим Engine з lifecycle, Space та transfer API і pin на локально зібрані артефакти.[14] Це корисний integration pattern, але [product README](https://github.com/UniClipboard/UniClipboard/blob/main/README.md#pair-a-mobile-device-current-compatibility-mode) досі описує поточні мобільні релізи як HTTP compatibility, не P2P; отже source-level інтеграція не доводить release parity.[15] [Опубліковане governance disclosure](https://github.com/UniClipboard/UniClipboard/blob/main/ABOUT.md) називає проєкт таким, що його part-time супроводжує один незалежний maintainer без core team; високий commit count не є доказом резерву супроводу.[16] Вердикт лишається незмінним: architecture-pattern candidate; для прямого reuse потрібні pin, власні fixtures на релізних пристроях та план підтримки fork.

**Вечірній application-transport cluster 23.09.** [Окремий addendum](../../../../research/iroh-reference-projects-update-2026-09-23-evening.md) додає п'ять нових implementation references і один earlier-history agent reference. `maplayerdev` показує ACP/Codex/Cursor stdio JSON-RPC над Iroh 1.2 з Android/Tauri clients; `adbc-proxy` — stateful ADBC/Arrow RPC з endpoint identity і principal authorization, але на Iroh 1.1; `audia` — Iroh 1.2 + `iroh-gossip 0.101` у browser WASM із relay-only transport; `xivlantern-dalamud` — presence/chat/offline queue/file transfer за Rust C ABI для C# host; `mesh-lighthouse` — Iroh 1.2 MetaMesh node з signed state, durable HTTP inbox і restart replication. `AgnView` pins Python `iroh==1.1.0`, але його history починається раніше, тому це не post-cutoff discovery. Для VIDA ці записи розділяються на agent ownership, application RPC receipt, browser relay recovery, stable ABI lifecycle і durable inbox gates; Iroh transport сам по собі не дає жодного з цих application contracts.

**Device-sharing та embedded chain 24.09.** [Окремий addendum](../../../../research/iroh-reference-projects-update-2026-09-24.md) додає `legato`, `bloop` і `rusty_esp_sense`. `legato` — pre-alpha KVM/device-sharing spike з mDNS/tickets, pair ALPN, SAS, `EndpointHooks::after_handshake` і allow-list; `bloop` — Tauri desktop P2P з Iroh 1.2 + mDNS, one-time pairing, paired EndpointId ACL та explicit privacy-minimal schema; `rusty_esp_sense` — host-only Janus ESP32 CSI reader, що через `rusty_esp_iroh-host` подає live telemetry у room-calibrated Candle model. Їхні VIDA gates різні: OS input/device permissions, pairing/revocation/privacy schema і device→host telemetry/lifecycle; жоден не є generic workspace sync або durable receipt proof.

**Remote desktop, distributed references та concept lead 25.09.** [Окремий addendum](../../../../research/iroh-reference-projects-update-2026-09-25.md) додає `AfuDesk` (Iroh 1.2 remote desktop для Windows host/Android viewer з mDNS, trusted devices, multiplexed streams і reconnect), `ajj` (Jujutsu/amber CAS + dstore refs через `dstore-transport-iroh` та Iroh 1.2 compatibility patch) і `Ultra-Netz` (Iroh/Nostr encrypted-storage concept, **researched, not built**). VIDA gates: remote-desktop permissions/identity/reconnect, CAS/ref authority та чітке розділення design-only lead від runnable implementation; Ultra-Netz не входить у provider ranking до появи коду, тестів і security evidence.

**Agent bus, collaboration та typed RPC SDKs 27.09.** [Окремий addendum](../../../../research/iroh-reference-projects-update-2026-09-27.md) додає шість нових URL у п'яти project groups: `iroh-acp-go` (Go ACP over go-iroh, EndpointId allow-list, raw JSON-RPC), `Doot` (Router + blobs/gossip/ping desktop/Android messenger), `acidtrip` (host-ordered collaboration без CRDT), `blirp` (SPAKE2 pairing і чотири application ALPNs для agent hub), `Grainlift TypeScript` і `Grainlift Go` (typed ADBC workers через VGI Iroh bridge). Той самий cutoff фіксує linked updates: Antgrid native streams, Codevisor Iroh 1.2 core, rho Collab, remote-device-sync hardening, NexaPipe lifecycle/health, Audia CSP/voting і Godot Iroh 1.2; це не нові URLs. VIDA gates: ACP process/authorization, Endpoint+Router application bus, host-order versus durable multi-writer semantics, hub authority і bridge/version contract parity; SDK/bridge claims не є самостійним transport/provider proof.

**Agent workspace, enrollment, remote execution та blobs 29.09.** [Окремий addendum](../../../../research/iroh-reference-projects-update-2026-09-29.md) додає `Walkie` (signed agent team log, Data Rooms, remote seats і pooled local LLM), `FarSail` (Windows remote desktop design із Iroh channel/TLS relay), `Portal` (go-iroh transport identity + SSH certificate authorization + argv-bound command), `ahole` (stock `iroh-blobs` collections/BLAKE3/resume) і `ErisAuth` (QR/fingerprint/permission enrollment). VIDA gates: signed-log finality/human kill-switch, transport identity versus user authorization, OS command policy, stock-blobs durable commit і pairing/revocation/key custody; жоден README не є production/security proof.

**Iroh-blobs completion boundary.** [Зріз API 0.103](digests/file-transfer-feature-coverage-r5-luna.md#iroh-blobs-0103-completion-boundary-focused-check-2026-09-23) розрізняє верифікований `Complete` blob, тимчасовий захист `TempTag` і окремий durable commit File/manifest/outbox у VIDA. Це не змінює вибір provider; для prototype gate потрібні crash-тести між цими етапами, інакше завершення transfer помилково виглядатиме як «збережено локально».

Узагальнення: більша функціональність репозиторію не означає, що саме потрібний VIDA модуль завершений. Наприклад, Rayfish має багато реального daemon/mobile коду і активні reconnect fixes, але не доводить готовність VIDA групового E2EE; Wyrd має чітку модель snapshot, але відверто позначає незавершений repair/GC. Ранній номер версії тут не є причиною відсіву ([Rayfish manifest](https://github.com/rayfish/rayfish/blob/master/Cargo.toml), [Wyrd status](https://github.com/control-aesir/wyrd/blob/master/README.md)).

## Розвиток, функції, issues — як порівнювати

За рішенням користувача це **перші чотири осі відбору**: траєкторія розвитку, частота змістовних комітів/merged PR, кількість реально реалізованих потрібних функцій та кількість і стан issues. Порівнюємо кандидатів на співставних 30/90-денних календарних вікнах і однакових [VIDA fixtures](../../../specs/spec-vida-signed-log-engine/candidate-evaluation-and-conformance.md); точні UTC cutoff у digest можуть різнитися на години, тому числа не ранжуємо за малою різницею. Версія `<1.0` не є відсівом. Сумісність, ліцензія й безпека залишаються обов'язковими gates, навіть якщо проєкт активно розвивається.

| Вимір | Який доказ брати | Як трактувати |
|---|---|---|
| Розвиток і частота комітів | 30/90-денні змістовні default-branch коміти, активні тижні, merged PR, релізи | Окремо рахувати функції, виправлення й тести; виключати bots/dependency churn із висновку про темп; `pushed_at` не є датою останнього `main` коміту |
| Обсяг потрібного функціоналу | Для кожного provider gate: число реалізованих і перевірених VIDA-сценаріїв / число застосовних сценаріїв; code paths, tests, ОС, migration/recovery | Показувати `готово / частково / відсутнє / невідомо` для кожного сценарію; не підміняти критичний acceptance fixture довгим списком сторонніх функцій |
| Кількість і стан issues/PR | Open і closed окремо, severity, вік backlog, час першої відповіді, частка виправлених або закритих із доказом, linked PR | 0 issues не доводить відсутність дефектів; великий backlog може співіснувати з активною підтримкою; PR не рахувати як issue |
| Сумісність | Lock-resolved tuple, CI build matrix, API/changelog, license | Маніфестний range і сусідні приклади не доводять, що tuple VIDA компілюється |

**Правило порівняння.** Спершу зіставляємо проєкти в межах тієї самої відповідальності (наприклад, signed log з signed log, а не з месенджером). Для кожного кандидата показуємо чотири головні осі поруч, дату зрізу й `невідомо` замість припущеного нуля. Без однакових fixture-результатів числовий сумарний рейтинг не формуємо. Навіть дуже активний проєкт не проходить обов'язковий gate сумісності, ліцензії або безпеки автоматично; версія `<1.0` таким gate не є.

Перевірений [30-денний зріз upstream](digests/upstream-protocols-r1-root.md) і [application sample](digests/development-momentum-r1-root.md) показують різні профілі: Synesis 84, Irokle 481, Kukuri 415 default-branch комітів; iroh-db 0 merged default-branch комітів у вікні, але 10 відкритих PR. Це **не рейтинг**: для iroh-db треба дивитися вік/review PR, для активних — частку тестових і релізних змін. Другий прохід містить датовані [network/mobile activity slices](digests/network-mobile-r2-luna.md), [storage/content slices](digests/storage-sync-r2-luna.md) і [messaging/media slices](digests/messaging-security-r2-luna.md), але issue response times лишаються невідомими.

### Поглиблення за чотирма критеріями користувача — 23.09

Зіставлення нижче розділяє **факт функціональності в коді/документації** та **проходження VIDA fixtures**. Перше можна дослідити в репозиторії; друге ще потребує однакових прототипів. Коміти — сирі default-branch counts, не кількість готових функцій. Issue та PR рахуються окремо за [семантикою GitHub API](https://docs.github.com/en/rest/issues/issues#list-repository-issues); «закрито» не обов'язково означає «виправлено».

**Правило порівняння кандидатів.** Чотири головні осі — (1) розвиток за 30/90 днів: зміст змін, релізи, тести й розподіл активності по тижнях; (2) частота комітів на default branch, окремо від автоматичних, документаційних і масових однотипних змін; (3) кількість **реалізованих потрібних VIDA можливостей** із фіксованого переліку *для одного provider gate*, а не сума всіх функцій різних застосунків; (4) стан issues: open/closed окремо від PR, вік і критичність відкритих дефектів, приклади реакції maintainer та перевірка, чи проблему виправлено. У кожній клітинці розрізняємо `підтверджено кодом`, `частково`, `невідомо` і `не застосовується`; `0 issues` без історії використання не є позитивним балом. Версія `<1.0` не знижує оцінку автоматично. Сумісність із Iroh 1.2, ліцензія, безпека й результати VIDA fixtures залишаються обов'язковими воротами до ADR, навіть якщо всі чотири осі сильні.

**Функціональна ширина в одному gate.** У [матриці signed-log/storage](digests/storage-feature-coverage-r4-luna.md) шість однаково сформульованих потрібних функцій: для двох безпосередньо повторно використовуваних library-кандидатів Irokle має 4 підтверджені API/контракти і 2 часткові, iroh-db — 6 підтверджених. Wyrd — переважно snapshot/file-store, Kukuri — застосунок із власними projections; їхні клітинки залишаються корисними архітектурними патернами, але механічно додавати їх до рейтингу signed-log бібліотек не можна. Для [network/mobile/FFI](digests/network-feature-coverage-r4-luna.md) порівняно шість інтеграційних можливостей; жоден зразок не показує готовий Flutter-плагін, а VPN/TUN-функції Rayfish/Nexa не входять до вимог VIDA. Nexa Android показує Android lifecycle shell, iroh-ffi — binding surface, Rayfish/RDS — ширші endpoint/service патерни: це різні ролі, не один взаємозамінний пакет.

Це поглиблення **не змінює** висновок про provider prototypes перед ADR. Змістовні коміти, точний fixture coverage, severity/вік issues та перша відповідь maintainer у частині кандидатів ще не виміряні повноцінно; у клітинках без доказу залишаємо «невідомо», не нуль. Версія `<1.0` сама собою не є ризиковим балом або відсівом.

## Evidence-driven prototype gates

1. **Core/sync:** однаковий signed operation ID і authority receipt; 2–3 peer offline, crash/restart у точках log/outbox/apply, duplicate/reordered transport, read-only старий клієнт. Порівняти Irokle, iroh-db та власний контракт без переписування VIDA invariant під одну бібліотеку.
2. **Editor:** той самий набір F01–F14 з [conformance spec](../../../../docs/04-specifications/crdt-editor-conformance.md) для Loro/Automerge та UI adaptation; окремо тестувати rich text, file materialization, concurrent same-sentence change й відновлення history.
3. **Files:** BLAKE3/range resume, encrypted manifest, failed disk write, quota, integrity, ACL/revocation і backup/GC; `iroh-blobs 0.103` проходить окремий gate через upstream warning. Альтернативний verified transfer не відкидати.
4. **Security:** OpenMLS/Beekem patterns з однаковими add/remove, epoch, late/offline device, recovery та scoped data fixtures; OWASP [MASVS](https://mas.owasp.org/MASVS/) і [Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) — контроль вимог, не доказ придатності конкретного репозиторію.
5. **Platform:** Release build Android/iOS/Flutter Windows; process kill, reconnect, OS sleep, FFI ownership, cancellation, secure storage, relay-only and direct connectivity. Demo foreground transfer не доводить постійний mobile online.

## Питання, які це дослідження залишає для ADR

- Чи допускаємо `iroh-docs` лише як reconciling adapter, чи simple namespaces потрібні як окремий технічний substrate? Не підміняти ним VIDA authority log.
- Чи витримує `iroh-blobs 0.103` файли VIDA на всіх платформах, або потрібен інший provider; як гарантувати міграцію bytes без зміни object ID?
- Які саме частини Irokle/iroh-db можна використати як library, а які краще наслідувати як pattern заради сумісності VIDA ownership/roles?
- Який group-security provider виконує product model revocation і recovery; ліцензійні межі MPL-2.0/інші зафіксувати до reuse?
- Яка verified version tuple `iroh`/gossip/docs/blobs/FFI компілюється й проходить fixtures на трьох клієнтських ОС?

**Каталожний результат:** [датований addendum](../../../../research/iroh-project-library-inventory-2026-09-23.md) містить стислий індекс. Наступні артефакти — порівняльні spike fixtures і лише після них library ADR; поточний зріз не є production lock.

## Staleness / re-check triggers

- Before library ADR: refresh **all** default-branch heads, releases, manifest+lock tuple, license, security notices and issue/PR samples. Research snapshot is dated 2026-09-23.
- Обчислений [staleness map](claims.json) із [вікнами](staleness-windows.json): guidance, compatibility та activity — re-check до **2026-10-23**; architecture-pattern comparison — до **2027-03-23**. Stale на 2026-09-23: **0**. Нова версія або важлива security issue запускає перевірку раніше. Rapidly changing repos such as Irokle, Kukuri, RDS and Rayfish need version-pinned prototype inputs.
- Physical Android/iOS/Windows build, long-running network tests, security review and OWASP control mapping are **not** supplied by GitHub activity metrics; keep these as explicit acceptance gates.
