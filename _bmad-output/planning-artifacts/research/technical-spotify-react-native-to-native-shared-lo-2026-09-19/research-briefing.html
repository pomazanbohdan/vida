Defines the VIDA boundary between stable product logic, Iroh/runtime infrastructure, and native client implementations.

Executive summary

The remembered case combines two precedents. Shopify, not Spotify, announced that it is moving mobile apps from React Native to native Swift and Kotlin. Its Shop app uses SwiftUI and Jetpack Compose. Shopify says React Native succeeded; coding agents changed the economics of maintaining two native implementations. Parity is maintained through shared specifications, tests, checkpoints, review, and release gates. Business logic is decoupled from UI, runnable headlessly, and exposed through a CLI.[1][2]

Spotify is a separate precedent: independently released platform clients with selected common libraries and historical shared native C++ capabilities. Public evidence does not support a Spotify React Native exit.[3][4][7]

Caveat. Shopify has not published the language or binary boundary of its headless logic. Recommending a Rust core for VIDA is a synthesis of Shopify’s agent-addressable design, 1Password’s deployed Rust core, Mozilla’s packaging/design evidence, and VIDA’s Iroh/Rust direction.

Proposed Architecture Spine

Headless local-first shared core with native/platform shells and ports-and-adapters at external seams.

  1. vida-core is the normative executable implementation of shared domain and protocol semantics.
  2. vida-runtime hosts Iroh, delivery, sync, blob, and storage coordination in Rust.
  3. Iroh core is strategic and mandatory; version integration and optional higher-level libraries remain controlled seams.
  4. Native/platform shells own UI and OS policy and may release independently.
  5. Language-neutral specs, golden vectors, replay fixtures, and parity tests govern every implementation.
  6. Storage, delivery, and discovery providers change only through explicit ports, migrations, and conformance gates.
  7. The headless core/runtime expose a CLI and deterministic test harness for developers and coding agents.

Evidence and precedents

Shopify: native clients, shared behavior contracts

Shopify’s public model is two native implementations aligned by specifications and verification artifacts—not evidence of one retained executable cross-platform core. Its transferable architectural idea is that product behavior becomes executable and reviewable without UI.[1][2]

Spotify: selected shared native capabilities

Spotify currently describes Android, iOS, and Desktop as independent release tracks sharing some libraries.[3] Historical evidence describes a native C++ core shared across most platforms, a shared sequencing module with C++ tests, and a Java/JNI Android boundary.[5][7] Liked Songs modernization changed about 100,000 shared-client lines plus Android/iOS integration.[4]

1Password and Mozilla: Rust below native shells

1Password places server communication, database behavior, permissions, cryptography, search, and other feasible non-UI behavior in a shared Rust Core while keeping native mobile frontends.[8] It also generates shared frontend types and uses Rust/WASM for browser contexts.[9] Mozilla documents Rust-to-iOS packaging through XCFramework/Swift Package artifacts and generated bindings; its Sync Manager document proposes a Rust-low-level/platform-orchestration split.[10][11]

Recommended VIDA boundary

A · Conformance Plane

Normative, language-neutral schemas, IDs, operation envelopes, authorization/sync/migration specs, golden vectors, replay fixtures, security negatives, parity scenarios, and compatibility matrix.

B · vida-core

Headless Rust product kernel: domain types, invariants, deterministic transitions/conflicts, capabilities, signed operations, causal/snapshot semantics, crypto envelopes, serialization, projections, test clock, replay, and CLI.

C · vida-runtime

Shared Rust infrastructure: Iroh Router/Endpoint/VIDA ALPNs, delivery, sync log, blob transfer, storage coordination, telemetry, failures, and platform-neutral background-job graph.

D · Platform shells

SwiftUI, Compose, desktop, and browser UI; accessibility; OS lifecycle; background execution; notifications; deep links; permissions; secure-store handles; packaging; diagnostics; rollout.

Development and migration model

Shopify supports the foundation: headless CLI access, small ordered checkpoints, behavior tests, visual review, adversarial review, human approval, and parity review.[1][2] VIDA adds protocol, determinism, accessibility, and rollback controls:

  1. Approve one behavior/specification slice.
  2. Record approval against an immutable specification revision.
  3. Implement the headless command/state path first.
  4. Run deterministic core and golden-vector tests.
  5. Implement every shell against the same slice.
  6. Run behavior, analytics, accessibility, and visual checkpoints.
  7. Run independent adversarial review and human acceptance.
  8. Release behind flags with staged cohorts and rollback evidence.

Spotify provides precedent for side-by-side paths, phased cohorts, and crash/performance monitoring.[4][12] VIDA should add artifact and behavior-differential checks.

Risks and unresolved decisions

  • Shopify’s result is contextual; it does not prove React Native is generally inferior.
  • A shared native core adds boundary, packaging, debugging, threading, cancellation, and versioning costs.
  • UI, permissions, lifecycle, and OS integrations should stay native even when that duplicates orchestration.
  • Browser/WASM needs a separate conformance profile; full native-runtime reuse is not assumed.

Decisions still required

  1. Canonical binding strategy: UniFFI, narrow C ABI with generated wrappers, or another IDL?
  2. Does vida-core own storage semantics only, or a portable embedded implementation?
  3. Which runtime capabilities compile to browser WASM, and which need a gateway?
  4. Which desktop shell strategy applies per platform?
  5. Which behavior belongs in executable shared code versus specification only?
  6. What ABI/schema window permits independent client releases?
