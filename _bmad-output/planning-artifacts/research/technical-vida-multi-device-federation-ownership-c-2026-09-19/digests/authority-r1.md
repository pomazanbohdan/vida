# Authority, quorum, receipts, ambiguous booking outcomes — source digest

Scope: public primary sources only; accessed 2026-09-19. Facts below describe source systems, not VIDA requirements. “Inference” marks design interpretation.

## Findings landed, round 1

1. **Replica agreement is not user authorization.** Fact: Raft commits a current-term log entry after storage on a majority of servers; leader election also requires a majority, with log freshness restrictions. Its failure model is crash/recovery, not malicious or unauthorized signers. Source: [In Search of an Understandable Consensus Algorithm](https://raft.github.io/raft.pdf), Diego Ongaro and John Ousterhout / USENIX, 2014, accessed 2026-09-19. Confidence: high; class: original paper. Inference: Raft-style `2+1` is appropriate only when a resource truly needs a replicated state machine with a designated membership and failure model; replica votes alone do not demonstrate that a human owner approved an operation.

2. **Threshold signatures express a signer policy, not durable acceptance.** Fact: FROST produces a signature after a threshold number of key-share holders cooperate; the RFC is informational and explicitly not an Internet Standard. Source: [RFC 9591](https://www.rfc-editor.org/rfc/rfc9591.html), IRTF CFRG / RFC Editor, 2024, accessed 2026-09-19. Confidence: high; class: primary protocol specification. Inference: `2-of-3` co-owner approval can be a suitable high-impact authorization policy, but must be distinguished from server commit and downstream booking confirmation.

3. **Federated event authorization and acceptance are separate checks.** Fact: Matrix receiving homeservers test an event against auth state; an event that passes auth at its historical point but fails against current state can be soft-failed. In the join handshake, a signed join event is submitted to a resident server; a `200` response means that server accepted it into the room graph. Source: [Matrix Server-Server API, latest](https://spec.matrix.org/latest/server-server-api/), Matrix.org Foundation, undated living specification, accessed 2026-09-19. Confidence: high for specified behavior; class: primary specification. Inference: a valid signature or locally formed event should not be represented as federated acceptance without an accepting server's response and durable event reference.

4. **Account authority may be a named server plus verifiable signed state, without a fixed quorum.** Fact: AT Protocol identifies the associated PDS (declared in the account DID document) as the authoritative location of an account repository; repo commits are signed and content-addressed. Source: [AT Protocol Repository specification](https://atproto.com/specs/repository), Bluesky PBC / AT Protocol, undated living specification (contains February 2026 status note), accessed 2026-09-19. Confidence: high for described model; class: primary specification. Inference: an ordinary single-owner resource can use one authoritative server plus owner-signed intent, version checks, and verifiable commit/receipt; ubiquitous `owner+server` co-signature or `2+1` replica quorum is not established by this precedent.

## Findings landed, round 2

5. **Concurrency control is not quorum.** Fact: HTTP `If-Match` requires strong entity-tag comparison before a state-changing method; a false precondition prevents application (normally `412`). `If-None-Match: *` can prevent overwriting a resource that already exists. RFC 9110 explicitly allows a successful prior update whose response was lost. Source: [RFC 9110, §§9.2.2 and 13.1](https://www.rfc-editor.org/rfc/rfc9110.html), IETF HTTP Working Group / RFC Editor, June 2022, accessed 2026-09-19. Confidence: high; class: Internet Standard. Inference: use expected-version/precondition checks for ordinary concurrent writes; a timeout is an **unknown outcome**, not proof that the write failed. A blind repeat of non-idempotent `POST` is unsafe unless the endpoint explicitly supplies idempotent semantics.

6. **Same-key retry is a bounded duplicate-suppression contract, not an unlimited exactly-once guarantee.** Fact: Stripe returns the first execution's saved status and body for retries with the same idempotency key, including `500`; it compares parameters and can prune keys after at least 24 hours, after which reuse creates a new request. It does not save results for pre-execution validation failures or concurrent conflicts. Source: [Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests), Stripe, undated living API reference, accessed 2026-09-19. Confidence: high for Stripe API; class: primary provider documentation. Inference: persist one operation ID, payload hash, provider idempotency key, attempt history, and any provider object ID **before** calling the booking/payment provider; after timeout, retry only with the same key and identical payload inside the provider's retention window, then query/reconcile by operation or provider ID where supported. Never generate a new key merely because the response vanished.

7. **Delivery acknowledgement differs from booking existence.** Fact: Booking.com Reservations API sends new, modified, and cancelled reservation messages; unacknowledged OTA bookings recur on `GET OTA_HotelResNotif`, and the docs explicitly warn consumers to handle repeats without creating duplicate local bookings. Reservation IDs are available for lookup/reconciliation. Source: [Booking.com Reservations API overview](https://developers.booking.com/connectivity/docs/reservations-api/reservations-overview), Booking.com, living documentation reporting “last updated 4 days ago” at access (no absolute publication date), accessed 2026-09-19. Confidence: high for this inbound API; class: primary provider documentation. Inference: ingestion needs dedupe by provider reservation ID/message type or revision, durable processing before ack, and a status that distinguishes “provider booked” from “locally ingested/acknowledged.” This API is inbound delivery, not evidence that Booking.com's outbound creation API accepts an idempotency key.

8. **Approval, hold, and confirmed booking can be distinct states.** Fact: Booking.com Request-to-Book documents a `bookingRequestId` distinct from a `reservationId`; in its `INQUIRY` mode, partner approval precedes guest finalization, and no reservation exists if the guest does not complete the booking. Its newer `RTB` mode differs: preauthorization and partner approval can be final, with provider-side inventory held from request creation. Source: [Booking.com Request to Book API](https://developers.booking.com/connectivity/docs/request-to-book/overview), Booking.com, undated living documentation, accessed 2026-09-19. Confidence: high for the documented modes; class: primary provider documentation. Inference: neither owner approval nor server acceptance should be labeled “booked” until the provider's corresponding reservation identifier/status is known; model provider-specific intermediate states.

## Contrary points and unknowns so far

- Contrary: Raft's majority protocol is specifically valuable when availability through crash failures and one ordered replicated log are required; single-authority design sacrifices that property. The source does not prescribe how to authorize business actions.
- Contrary: Matrix shows a server may accept an event but another server may later soft-fail it under current state; one acceptance receipt is not universal federation agreement.
- Contrary: Multi-party human approval may be essential for co-owned critical acts (e.g., transferring shared ownership, deleting irreplaceable joint data, spending shared funds), even though none of these sources mandates a universal threshold. Distinguish policy quorum from crash-tolerant replica majority.
- Contrary: Stripe caches an initial `500`; repeating the same key can return the same `500` without clarifying an external side effect. Key expiry also ends deduplication protection. Reconciliation remains necessary.
- Unknown: which VIDA operations truly need co-owner approval, what parties own signing keys, and which server can authoritatively commit each resource; public protocols cannot set those product policies.
- Unknown: exact booking provider create/cancel idempotency, lookup, retention, webhook, and compensation contracts. Do not promise exactly-once booking across an unverified provider boundary.

## Decision-use synthesis (inference, not source mandate)

- Keep four evidence layers: (1) **intent/approval**: actor identity, signed command, resource/version, policy approvals; (2) **agreement** only if replicated: membership/term/index/commit proof; (3) **authority acceptance**: server event or revision ID and durable status; (4) **external outcome**: provider reservation/payment ID and authoritative status. A receipt should name its layer, issuer, operation ID, timestamp, payload hash, and version; no layer silently upgrades another.
- Default ordinary resource write: current owner authorization + authoritative server validation and conditional commit; replicate asynchronously if desired. Treat `owner+server` as two different roles (authorization + acceptance), not necessarily a cryptographic two-signature quorum. Require explicit co-owner threshold for named high-impact operations; use consensus majority only for a resource whose authoritative state actually spans crash-tolerant replicas.
- Timeout path: persist `pending/unknown` → inspect/retry same idempotency key if supported → query authoritative provider/status and dedupe callbacks by stable IDs → only transition to `confirmed` on provider evidence; if provider lacks safe retry/reconciliation, escalate to manual resolution before any second create attempt.
