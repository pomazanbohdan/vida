# Multi-device/local-first — primary-source digest (2026-09-19)

Scope: same signed input event reaches 2–3 devices; deterministic app logic derives data; an earlier edit may remain offline when the same user edits elsewhere. Eight distinct primary sources read, two search rounds. `Fact` is a source claim; `Inference` is a design implication, not a vendor guarantee.

## Findings

1. **Replicated updates can converge without a single primary, but this is data-structure convergence, not domain-operation uniqueness.** Fact: Automerge permits independent offline edits on several devices (including one user's devices), syncs later, and merges concurrent changes; Yjs document updates are commutative, associative and idempotent, so replay/order do not alter the final shared document once all updates arrive. Sources: [Automerge Welcome](https://automerge.org/docs/hello/) — Automerge contributors, publication date not stated, accessed 2026-09-19; [Yjs Document Updates](https://docs.yjs.dev/api/document-updates) — Yjs, publication date not stated, accessed 2026-09-19. Confidence/class: high/direct documentation. Inference: a repeated *same CRDT update* is harmless to that document, but two devices independently turning one signed event into two newly generated record IDs can still create two domain objects; the input event needs stable identity and derived output IDs/keyed upsert or separate ownership/deduplication.

2. **Idempotent append and idempotent handler are different boundaries.** Fact: EventStoreDB/Kurrent suppresses duplicate appends for the same `EventId` and stream when an expected version is supplied; its docs warn that `ExpectedVersion.Any` does not guarantee idempotence. EventSourcingDB says reconnecting handlers can see duplicate deliveries and must make handling idempotent or persist handled event IDs. Sources: [Kurrent Appending Events](https://docs.kurrent.io/clients/tcp/dotnet/21.2/appending) — Kurrent/EventStoreDB, publication date not stated (versioned 21.2 docs), accessed 2026-09-19; [EventSourcingDB Building Event Handlers](https://docs.eventsourcingdb.io/best-practices/building-event-handlers/) — EventSourcingDB, publication date not stated, accessed 2026-09-19. Confidence/class: high/direct documentation. Inference: persist `(sourceEventId, handler/version or domain-operation kind)` as a unique processing key, and derive stable output IDs from that key; a signature proves origin/integrity but is not the processing key or a claim that processing occurred once. If peers each have private logs, local dedupe alone cannot grant globally exclusive execution.

3. **Offline subsequent edits are ordered by causality only when the later device has observed the earlier edit.** Fact: Automerge models concurrent versions as changes since a common ancestor; distinct-key map changes merge, whereas concurrent assignments to the same property yield one deterministic visible value while all alternatives remain available via `getConflicts`. Its list operations reference element IDs, not current numeric indices. Sources: [Automerge Merge Rules](https://automerge.org/docs/reference/under-the-hood/merge-rules/) — Automerge contributors, publication date not stated, accessed 2026-09-19; [Automerge Conflicts](https://automerge.org/docs/reference/documents/conflicts/) — Automerge contributors, publication date not stated, accessed 2026-09-19. Confidence/class: high/direct documentation. Inference: if edit A is unsynced on phone and same user makes edit B on laptop from an older snapshot, A and B are concurrent despite common user identity or B's later wall-clock time. Same-device B-after-A has a causal dependency. To enforce *user-intended* replacement across devices, carry base heads/parent revision, show/resolve conflict, or require online serialization; do not equate account identity with causal order.

4. **Causal metadata is a safer semantic basis than bare wall-clock LWW.** Fact: the original CRDT paper requires reliable causal delivery for operation-based CRDT convergence; it distinguishes LWW (one concurrent value wins) from multi-value registers (both retained). Its LWW timestamps must be unique, totally ordered, and consistent with causality; a per-replica counter plus replica ID is offered as an implementation. Source: [Shapiro et al., *Convergent and Commutative Replicated Data Types*](https://pages.lip6.fr/Marc.Shapiro/papers/CRDTs-beatcs-2011-06.pdf) — Bulletin of the EATCS 104, June 2011, accessed 2026-09-19. Confidence/class: high/original research. Inference: device wall clocks alone are not guaranteed causality-consistent; choosing the numerically latest clock can erase an unsynced edit or mask a true concurrent conflict. Prefer causal version vectors/heads plus field-specific semantics; use a total-order tie-break only where losing one concurrent value is acceptable.

5. **Pure deterministic replay must be separated from external effects.** Fact: Fowler's event-sourcing account says replay of events can wrongly repeat external updates and proposes a gateway aware of replay; it also notes external query responses can change replay results. Source: [Martin Fowler, *Event Sourcing*](https://www.martinfowler.com/eaaDev/EventSourcing.html) — Martin Fowler, 2005-12-12, accessed 2026-09-19. Confidence/class: high/author's original pattern, though explicitly a draft. Inference: each device may compute a local projection from the same signed event; only a committed, deduped operation should trigger non-idempotent effects (payment/email/federated publish). For true global once-only effects while offline, no CRDT merge alone can elect a sole executor; choose a coordinated owner/lease or an idempotent downstream endpoint, with availability tradeoff.

## Strongest contrary point / boundary

Automerge and Yjs already solve substantial multi-device *state* reconciliation without a central writer: their merge/idempotence may suffice if the derived result is itself one shared CRDT value and there are no unique domain creation or external effects. A central owner would needlessly reduce offline availability in that narrower case. Conversely, the original CRDT model explicitly assumes non-Byzantine replicas and per-object operations, not signed adversarial event processing or cross-object transactions; its convergence proof does not establish authorization, deduped business actions, or global invariants. Source: [Shapiro et al.](https://pages.lip6.fr/Marc.Shapiro/papers/CRDTs-beatcs-2011-06.pdf) — Bulletin of the EATCS 104, June 2011, accessed 2026-09-19. Confidence/class: high/direct boundary plus medium/design inference.

## Decision-relevant unknowns

- Is derived data a recomputable projection, or a durable domain action with an externally visible effect?
- Must output IDs be stable across app versions, and can old/new code process the same event simultaneously?
- Are independent same-user edits to the same field allowed to coexist for UI resolution, or must one be authoritative?
- Is there an online writer/stream with conditional append, or must all devices accept writes throughout partitions?
- What is the per-aggregate invariant and conflict policy (commutative set/counter, multi-value, manual merge, or serialized command)?
