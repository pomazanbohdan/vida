# VIDA UI/platform selection: project case map

Scope: test the proposed **Flutter mobile + shared Rust core/runtime + Tauri Windows + browser** configuration against existing VIDA product and platform commitments. This is a requirements/fixture inventory, **not** external evidence that any framework can satisfy a case. **65 cases total:** first layer 50 (29 `MUST`, 16 `SHOULD`, 5 `OPEN`); second corpus-derived layer 15 (4 primary `MUST`, 1 `MUST NOT`, 7 `SHOULD`, 3 `OPEN`; some rows also note unresolved subdecisions). First-layer `MUST` reflects an approved source requirement; second-layer status has its own provenance and does not promote historical proposals to approved decisions. The candidate stack remains unselected here. Android and iOS need distinct results; “Flutter mobile” does not merge their OS obligations.

Source abbreviations below refer only to the named local documents: `PB` = `docs/01-product/product-boundary.md`; `V1` = `docs/01-product/v1-replacement-bundle.md`; `CW` = `docs/01-product/composable-workspace-model.md`; `NFR` = `docs/02-requirements/platform-nfr.md`; `NH` = `docs/04-specifications/vida-node-host-contract.md`; `IR` = `technical-iroh-ecosystem-and-project-patterns-for-2026-09-18/research.md`; `SC` = `technical-spotify-react-native-to-native-shared-lo-2026-09-19/research.md`; `ID` = `technical-vida-identity-modes-2026-09-18/research.md` (the three research files are under `_bmad-output/planning-artifacts/research/`). Section numbers/heading names are source locations, not framework claims. A fixture should exercise the **same semantic command/event contract** on Flutter Android, Flutter iOS, Tauri Windows and browser where the platform supports that operation; platform-specific exclusions must be explicit.

## Selection gate implied by these cases

The candidate is viable only if a thin vertical slice proves the Rust command/event boundary and binding mechanics on real Android/iOS devices, Tauri Windows and browser; the same product fixture must then pass platform-specific lifecycle, accessibility, privacy and release checks. The browser may have a separately bounded capability profile, but any omitted case must be explicit. The unresolved `OPEN` rows are decision inputs, not permission to present unsupported behavior as implemented. Research precedents (`IR`, `SC`, `ID`) supply hypotheses and test shapes; the approved product/spec/NFR documents supply normative obligations.
