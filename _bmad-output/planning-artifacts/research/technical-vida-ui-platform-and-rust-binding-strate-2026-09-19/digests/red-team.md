# Red-team: Flutter mobile + Rust core + Tauri 2 Windows

Date: 2026-09-19. Independent challenge to a **provisional** choice, not a rejection of it. Internal VIDA documents define acceptance needs; linked vendor/project sources establish technical constraints. No prototype results exist in this digest.

## Overall verdict

The proposed mix is plausible, but **not yet a defensible committed platform decision**. The strongest counterargument is that UI reuse and a shared Rust crate do not guarantee runtime parity across mobile, browser and Windows. Flutter Windows is a genuine desktop counterfactual: Flutter supports Windows and Dart FFI; Tauri is not required merely because the core is Rust. Choose Tauri only after a head-to-head workflow/release/security test. Mobile background delivery is a product/topology decision that no UI toolkit can waive.

## Five strongest failure modes

| # | Failure mode and contrary evidence | Severity | Decision gate / exit |
|---|---|---|---|
| 1 | **Assumed always-on Iroh node on phones.** `VidaNodeHost` owns start/suspend/resume/network-change and cancellable transport commands; mobile NFR requires process-death/reconnect tests. Yet iOS normally suspends background apps and may defer scheduled tasks for hours; Android Doze/App Standby defers background network and restricts foreground-service starts. Flutter background isolates/plugins enable some work, but do not override OS policy; Flutter also documents that background-isolate platform channels cannot receive unsolicited host messages. A Rust runtime embedded in Flutter cannot promise direct real-time reachability after suspension. [Internal: `docs/04-specifications/vida-node-host-contract.md`, `docs/02-requirements/platform-nfr.md`; external: Apple background modes and task scheduling, Android background restrictions, Flutter isolate docs below.] | **Potentially fatal to product guarantee**, not to Flutter itself. | Prototype with physical Android/iOS devices: foreground → suspend → OS kill → reboot, network handover, no-push/push wake, delayed direct and durable delivery, locked key store. Record latency/battery and distinguish `accepted`, `stored`, `applied`. If product requires uninterrupted phone-to-phone direct service while backgrounded, revise product/topology; switching Flutter to native UI alone will not solve it. |
| 2 | **Shared Rust core becomes three incompatible application behaviors.** Flutter native calls Rust through Dart FFI/FRB; Tauri uses JS→Rust commands/channels; browser cannot use Dart native FFI and has different storage/network/concurrency constraints. FRB's cancellation guide offers an example custom token or Tokio token rather than a bridge-wide transparent guarantee. Tauri documents JSON serialization overhead for large values and channels for streams. The same `vida-core` crate therefore does not itself prove identical cancellation, backpressure, idempotency, error classification, migration or secret handling. VIDA NFR explicitly demands separate platform conformance and mixed-version rollback. [Internal: `platform-nfr.md`, `vida-node-host-contract.md`; external: Flutter FFI/web FAQ, FRB cancellation, Tauri commands below.] | **Fatal to the proposed stable-core claim if unaddressed**; technically mitigable. | Define a semantic command/event protocol *above* FRB and Tauri IPC: typed errors, operation IDs, cancellation/ack rules, bounded stream/replay, version/features. Run identical golden vectors and adversarial lifecycle fixtures through Flutter, Tauri and browser profile, including mixed N/N−1 release and persisted-state rollback. If browser cannot satisfy a behavior, publish a capability difference instead of claiming parity. If binding cannot uphold semantics, replace binding or move function into an OS-specific host without forking domain logic. |
| 3 | **Tauri webview expands the security boundary around sensitive local data.** Tauri's runtime authority/capabilities constrain which webview origin can call Rust, but those controls must be deliberately configured. Tauri warns that CSP protection applies only when configured, and untrusted local/remote content introduces attack vectors. VIDA includes rich documents, chats, forum content and City Portal integrations—thus potentially attacker-controlled content rendered next to commands accessing local DB, keys, and network. An XSS-to-IPC path could turn a presentation bug into privileged local action. This is a *different* attack surface from Flutter Windows, though Flutter also has its own risks. [Internal: `docs/01-product/v1-replacement-bundle.md`, `platform-nfr.md`; external: Tauri runtime authority/CSP below.] | **Potentially fatal for Tauri desktop** if arbitrary content reaches privileged commands; mitigable with architecture and tests. | Treat document/forum/portal content as hostile; no remote scripts in privileged view. Ship deny-by-default capabilities per window, restrictive CSP, scoped commands, opaque file handles, no raw arbitrary-path or key commands, sanitized rich content. Red-team an XSS fixture that attempts every Rust command and exfiltration path. If a safe content boundary cannot be demonstrated, prefer Flutter Windows or a separately sandboxed webview/content process. |
| 4 | **Tauri Windows is chosen for conceptual neatness while doubling UI/operational work.** Flutter officially supports Windows and Dart FFI; one Flutter UI may let the mobile team share components/design behavior. Tauri uses WebView2, with runtime installation/update/OS-version implications. Its Windows installer defaults to fetching a bootstrapper; offline installer/fixed runtime materially increases installer size. Conversely, a DOM UI in Tauri may reuse browser UI and improve keyboard/editor/a11y behavior. None of these tradeoffs are resolved by “Rust core.” [External: Flutter supported platforms and FFI, Tauri WebView2/installer below.] | **Mitigable**, but can cause years of avoidable maintenance or deployment trouble. | Build the same representative Windows workflow in Flutter Windows and Tauri 2: encrypted offline project, 100k-item search, rich document↔task↔chat navigation, multiwindow/notifications/deep links, NVDA/keyboard, installer on clean offline Windows, auto-update/rollback, memory/startup/idle energy. Compare total engineering effort and defect rate as well as performance. Adopt Tauri only if its measured advantage offsets second UI stack and webview operations. |
| 5 | **The super-app’s hardest UI is not a framework demo.** VIDA v1 composes message/group/forum, notes/knowledge, tasks/projects, cross-links, privacy and sharing; custom complex editors, virtualized feeds, drag/drop, keyboard navigation and screen-reader semantics are the stress case. Flutter documents semantics support but custom widgets require explicit roles; its web UI needs a separate semantics-to-DOM layer. A framework support matrix is not proof that this workflow is accessible, responsive or text-input-correct on phones. A web UI in Tauri might excel at document editing, but this would strengthen a split UI decision rather than prove a universal toolkit. [Internal: `v1-replacement-bundle.md`; external: Flutter accessibility/web accessibility below.] | **Potentially fatal to Flutter mobile UX** for the intended audience; mitigable via native escape hatches only if bounded. | Prototype a complete message→document→task workflow with Ukrainian IME, copy/paste, screen reader (TalkBack/VoiceOver), switch control, dynamic text, RTL, reduced motion, offline state change, and large data. Establish hard usability/a11y criteria with users. If repeated core workflows need platform views/native rewrites, choose native Swift/Kotlin shells over the same Rust facade before broad feature build-out. |

## Decision framing

1. **Do not mark Flutter mobile or Tauri Windows as final from literature alone.** Use conditional ADR status and track gates separately. The question is not whether these technologies can call Rust; they can. It is whether the required VIDA lifecycle, security, accessibility and release semantics survive the actual bridges.
2. **Separate desktop from mobile approval.** A Flutter mobile win does not imply Tauri Windows. A Tauri Windows win does not imply Tauri mobile or browser parity.
3. **A failed background gate is not automatically a Flutter failure.** It may require store-and-forward infrastructure, push-mediated wake, revised delivery promises and observable `accepted` vs `applied` states.
4. **A failed Tauri security/desktop gate has a contained exit:** Flutter Windows or a native Windows shell over the same versioned Rust application facade.
5. **A failed FRB gate has a contained exit only if the semantic contract is independent of generated bindings:** manual C ABI/UniFFI or native shell. Do not expose FRB-specific types as product contracts.
