## Package feasibility gate from live Flutter primary docs

`(3).txt:194–219` and `(9).txt:1022–1055, 1155–1185` discuss installable app packages, but these must be split into **(a) installable declarative schemas/layouts/assets and data**, **(b) precompiled Flutter/Dart/native plugins shipped with a client release**, and **(c) separately evaluated sandboxed business logic**. [Flutter's package documentation](https://docs.flutter.dev/packages-and-plugins/using-packages) says native plugin code is built into the app (lines 109–111). [Flutter's deferred-component documentation](https://docs.flutter.dev/perf/deferred-components) says Android/web deferred code/assets require predeclared Dart imports, and Android requires rebuilding and uploading the whole AAB for new code (lines 60–70). Thus Flutter's deferred loading **does not establish arbitrary post-release executable marketplace plugins**. **OPEN/MUST-GATE:** prove a signed declarative VIDA package can be downloaded, permission-reviewed, rendered on Flutter and Tauri, updated and rolled back without client recompilation; prove that any code-bearing capability respects each platform's distribution/security policy before promising it. Do not conflate WIT/plugin ABI with Flutter plugin installation or the Rust shell binding.
