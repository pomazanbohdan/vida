# VIDA: UI platforms and Rust interoperability

## Executive finding — research, not architecture approval

The user's **Flutter for Android/iOS + shared Rust core/runtime + Tauri for Windows** proposal is technically coherent, but the evidence does not yet justify approving Tauri over Flutter for Windows. Flutter is a credible mobile shell with native-code interop and escape hatches; Tauri is a credible installed Windows shell whose Rust host can call VIDA's Rust facade directly. The combination introduces **two UI implementations** (Flutter/Dart and HTML/CSS/TypeScript) and **two shell-boundary mechanisms** (Dart↔Rust generated FFI and WebView↔Rust IPC). Flutter Windows is the strongest paired baseline because it can reuse the mobile presentation stack. A **same-core, same-fixture, release-build comparison** of Flutter Windows and Tauri Windows is therefore a decision gate. [Flutter platforms](https://docs.flutter.dev/reference/supported-platforms), [Flutter Windows](https://docs.flutter.dev/platform-integration/windows/building), [Tauri architecture](https://v2.tauri.app/concept/architecture/), [Tauri commands](https://v2.tauri.app/develop/calling-rust/).

The stable architectural center is **not** a universal generated ABI. It is a toolkit-neutral Rust application contract: commands, owned DTOs, typed errors, operation IDs, bounded sequenced events, snapshots, lifecycle and compatibility rules. A Flutter adapter may use `flutter_rust_bridge` (FRB); a Tauri adapter should call the facade directly inside Rust and expose narrow commands/channels; a browser adapter needs a distinct Rust/Wasm and/or gateway profile. UniFFI is a credible native Swift/Kotlin fallback, not a reason to choose those UIs now. [FRB](https://cjycode.com/flutter_rust_bridge/), [Tauri commands](https://v2.tauri.app/develop/calling-rust/), [UniFFI](https://mozilla.github.io/uniffi-rs/latest/), [wasm-bindgen](https://wasm-bindgen.github.io/wasm-bindgen/).

The browser must be specified as a **separate delivery/capability profile**, even if it shares DOM UI with Tauri. Flutter's native `dart:ffi` route does not apply to web plugins; browser Wasm lacks normal native filesystem/network facilities; Iroh's first-party browser/Wasm example currently uses a relay-only path. Browser persistence, background delivery, transport cost and security cannot inherit native claims by association. [Flutter FFI](https://docs.flutter.dev/platform-integration/bind-native-code), [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview), [Rust/Wasm target](https://wasm-bindgen.github.io/wasm-bindgen/reference/rust-targets.html), [current Iroh browser example](https://github.com/n0-computer/iroh-esp32-examples/blob/main/wasm-gui/README.md).

**Provisional experiment direction:** build the Flutter mobile/Rust vertical slice; test FRB as its first bridge; build **both** Windows shells against the same Rust revision; prove the browser capability profile separately. Do not record a final platform ADR, version promise, performance SLO or browser parity until the gates below pass. The user's statement is a working hypothesis, not an approved platform selection.

## VIDA cases that determine the platform choice

The approved [product boundary](../../../../docs/01-product/product-boundary.md) defines VIDA as an open-core super-app with local data/synchronization and an integrated but separately developed City Portal App. [The v1 replacement bundle](../../../../docs/01-product/v1-replacement-bundle.md) requires communication (personal/group/forum), knowledge (notes, linked documents, shared base) and personal/team work management together, not as three unrelated applications. [The composable workspace model](../../../../docs/01-product/composable-workspace-model.md) makes Messenger, Knowledge and Projects schema-driven AppInstances in a Space. A Space is a security/ownership/sync boundary, **not necessarily a mandatory top-level navigation boundary**: authorized global Messages, Today, Search and Activity may aggregate across Spaces.

The same message may be linked to a document, task, project or forum context; opening a link must respect the target's independent access policy. A link or mount **does not grant access**. Scoped role presets, per-resource/field/action grants, expiry and hard denies must be evaluated in Rust; disabled buttons are only UX. Global search, previews, notifications and deep links must not leak unauthorized target metadata, including after offline revocation. A shell can render schema-driven forms/views but must not reimplement policy or domain transitions. These are VIDA requirements, **not** claims that Flutter, Tauri or browser already satisfy them.

The [platform NFR](../../../../docs/02-requirements/platform-nfr.md) requires crash recovery, exactly-once domain apply despite duplicate direct/mailbox delivery, reconnection convergence, privacy-safe diagnostics, negative security tests, mixed-version upgrade/rollback/restore and separate browser/Android/iOS/desktop conformance. Quantitative SLOs remain deferred pending measurement. The [NodeHost contract](../../../../docs/04-specifications/vida-node-host-contract.md) requires cancellable typed commands, start/suspend/resume/shutdown, network-change response, endpoint profiles, path diagnostics and secret-safe ports. A UI bridge must preserve this taxonomy instead of flattening failures.

Prior [Iroh research](../technical-iroh-ecosystem-and-project-patterns-for-2026-09-18/research.md), [shared-core research](../technical-spotify-react-native-to-native-shared-lo-2026-09-19/research.md), and [identity research](../technical-vida-identity-modes-2026-09-18/research.md) provide **hypotheses and test shapes**, not vendor proof. In particular, an Iroh relay is not the durable mailbox; autonomous/local, federated and public identity behaviors are not mutually exclusive account types; identity scope, hosting, discoverability, verification, network privacy and authorization are independent axes. Shell settings must not silently couple them.

### Installable VIDA packages are not executable Flutter plugins

The user-facing “install an app inside the super-app” requirement must separate **downloadable declarative schemas/layouts/assets/data**, **Flutter/Dart/native plugin code built into a client release**, and any **sandboxed executable extension tier** still to be designed. Flutter's official package guide says platform-specific plugin code must be built into the app. Its deferred-component guide permits predeclared Android/web code/assets to download later, but Android requires rebuilding and uploading the whole AAB for new code; deferred loading therefore does **not** establish arbitrary post-release executable marketplace plugins. [Flutter packages](https://docs.flutter.dev/packages-and-plugins/using-packages), [Flutter deferred components](https://docs.flutter.dev/perf/deferred-components).

The immediate feasibility gate is a **signed declarative VIDA package**: download, inspect capabilities/consent, instantiate schema and presentation, render equivalent supported form/page/view constructs on Flutter and Tauri, update/rollback, and reject unsupported declarations on an older shell without corrupting stored resources. Code-bearing plugins, WIT/Wasm extensions, dynamic native modules and store-policy compliance are a distinct decision. Do not conflate an App package ABI with FRB/FFI, Tauri IPC or NodeHost transport; no current source proves arbitrary executable plugins can be shipped post-release on every target.

## Flutter mobile: plausible first spike, bounded promises

Flutter documents Android/iOS support and a mobile/desktop FFI path that can call Rust C ABI. Official guidance still requires platform-specific plugins or native code for uncovered OS capabilities. Flutter does not replace Keychain/Keystore, OS schedulers, notification permissions or native accessibility testing. [Flutter support](https://docs.flutter.dev/reference/supported-platforms), [current FFI guide](https://docs.flutter.dev/platform-integration/bind-native-code), [platform integration](https://docs.flutter.dev/platform-integration).

FRB offers generated Dart/Rust async calls, streams, errors and opaque values; the registry showed stable 2.13.0 and a 2.14 prerelease during this research. It is a **candidate bridge**, not the VIDA contract or a promise that its generated stream automatically preserves ordering, cancellation, crash recovery or memory ownership. FRB's cancellation guide calls for an application token. Native allocations behind opaque handles need deterministic `dispose/close`; foreign GC/finalization cannot own durable job lifecycle. [FRB versions](https://pub.dev/packages/flutter_rust_bridge/versions), [FRB](https://cjycode.com/flutter_rust_bridge/), [FRB cancellation](https://cjycode.com/flutter_rust_bridge/guides/how-to/cancel).

Flutter isolates have independent memory and message passing. Official guidance says web has no Dart isolates in this model, and background isolates cannot receive unsolicited platform-channel messages. Therefore “run Iroh in a Dart isolate” is not a mobile background architecture. Rust needs explicit pause/resume and persistent job state; each shell schedules only OS-permitted work. Android documents background-task restrictions, and Apple warns background pushes can be throttled or not delivered. A 24/7 phone endpoint or timely background-delivery promise requires real-device evidence and fallback UX. A failed always-on test may require store-and-forward topology or revised product promises; switching to native UI alone cannot waive OS policy. [Flutter isolates](https://docs.flutter.dev/perf/isolates), [Flutter background](https://docs.flutter.dev/packages-and-plugins/background-processes), [Android limits](https://developer.android.com/develop/background-work/background-tasks/bg-work-restrictions), [Apple background push](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app).

Flutter exposes semantics to assistive technology, but custom controls, complex rich text, selection, focus, dynamic type, Ukrainian IME, reduced motion and multilingual/RTL behavior require VoiceOver/TalkBack trials on VIDA's complete message→document→task workflow. A supported Semantics API is feasibility evidence, not product conformance. [Flutter accessibility](https://docs.flutter.dev/ui/accessibility), [Flutter web accessibility](https://docs.flutter.dev/ui/accessibility/web-accessibility).

## Windows: Flutter baseline against Tauri hypothesis

Both can call the same Rust core. Flutter Windows reuses Dart widgets, routing/state architecture, localization and mobile UI skills, while allowing a customized native runner and FFI/plugins. It still needs Windows-specific layout, installer/update and accessibility work. Tauri renders HTML/CSS/TypeScript in WebView2 and calls Rust commands/channels in the host; it may reuse browser UI, DOM editor/grid libraries and desktop plugins, but adds a second VIDA UI implementation. [Flutter Windows](https://docs.flutter.dev/platform-integration/windows/building), [Tauri frontend](https://v2.tauri.app/start/frontend/), [Tauri commands](https://v2.tauri.app/develop/calling-rust/).

| Axis | Flutter Windows baseline | Tauri 2 Windows hypothesis | Spike question |
|---|---|---|---|
| UI reuse | Dart widgets/state from mobile; desktop layouts distinct | Browser DOM UI if browser product truly shares frontend | Which reduces total implementation and parity QA for schema-driven editor/grid? |
| Rust boundary | Dart FFI/FRB as on mobile | Direct Rust facade; serialized WebView IPC | Is second bridge worth desktop-specific advantage? |
| Desktop integration | Native runner/Win32/plugins; release tooling chosen by team | Tray/autostart/notification/updater/single-instance plugins | Which reliably meets actual user workflows? |
| Accessibility/text | Flutter semantics | DOM/ARIA via WebView2/UI Automation | Which passes Narrator/NVDA, keyboard, contrast, IME and scaling? |
| Security | FFI/plugin and plaintext UI-memory risks | XSS, CSP, command scope, IPC attack surface | Can untrusted content be isolated from privileged commands? |
| Deployment | Bundle engine/data; own install/update choices | WebView2 floor; bootstrap/offline modes | Which works on clean/offline Windows images? |
| Performance | Measure release app/process | Measure all WebView2 browser/renderer/GPU processes | Which meets predeclared app-specific thresholds? |

Tauri offers MSI/NSIS; WebView2 is a deployment dependency with bootstrap/offline/fixed modes. Offline modes increase package size; “Tauri is smaller” is unproven from a tiny dev binary. WebView2 is multi-process, so count the process tree. [Tauri installer](https://v2.tauri.app/distribute/windows-installer/), [WebView versions](https://v2.tauri.app/reference/webview-versions/), [WebView2 process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model).

Tauri capabilities/CSP reduce webview blast radius **when narrowly configured**, but Tauri says capabilities do not protect against insecure Rust commands and CSP only applies when configured. VIDA rich documents, chats, forums and portal content may be attacker-controlled. Treat all rendered content as hostile; disallow remote scripts in privileged views; use deny-by-default window capabilities, narrow intent-level commands, safe rich-text rendering, opaque file handles and an XSS fixture attempting every privileged command/exfiltration path. If containment cannot be proved, prefer Flutter Windows or a separately sandboxed content view. [Tauri runtime authority](https://v2.tauri.app/security/runtime-authority/), [Tauri capabilities](https://v2.tauri.app/security/capabilities/), [Tauri CSP](https://v2.tauri.app/security/csp/).

Neither shell is automatically a pre-login Windows Service. Tauri autostart/tray is an application-at-login pattern; if VIDA requires sync before login, make that a distinct service decision with authenticated ACL-scoped local IPC and one vault writer. Windows services can run without a user login but cannot directly interact with a user desktop. [Tauri autostart](https://v2.tauri.app/plugin/autostart/), [Windows services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services).

Tauri updater signatures, Windows application code signing, pre-exit durable flush, schema compatibility and rollback are distinct obligations. Its Windows updater may exit the app during install; notifications must be tested from an **installed** app, not only dev mode. Flutter likewise needs an installer/updater choice. Tauri 3 alpha existed in the September 2026 feed; evaluate stable Tauri 2 and separately decide any major migration. [Tauri updater](https://v2.tauri.app/plugin/updater/), [Windows signing](https://v2.tauri.app/distribute/sign/windows/), [notification](https://v2.tauri.app/plugin/notification/), [releases](https://github.com/tauri-apps/tauri/releases).

## Rust boundary: one meaning, platform-specific adapters

```text
Flutter Android/iOS ─ FRB/Dart FFI adapter ─┐
Flutter Windows spike ─ same adapter ──────┤
Tauri Windows spike ─ Rust commands/IPC ───┼─ VIDA application facade
Browser ─ worker + Wasm/API adapter ──────┘    ├─ vida-core: domain, policy, codec, transitions
                                                └─ vida-runtime: storage/jobs, Iroh/sync, crypto, platform ports
```

The facade is **semantic**, not a claim that FRB, Tauri, UniFFI and Wasm share one physical ABI. UniFFI's first-party languages are Kotlin, Swift and Python, not Dart; it does not provide a first-party browser generator. Tauri commands are serde/IPC; Dart FFI is C ABI; browser Rust needs JS bindings. Forcing all through public C ABI increases manual memory/async/callback work without increasing domain reuse. Keep a tiny versioned C ABI only if an actual embedding consumer/fallback demands it. [UniFFI](https://mozilla.github.io/uniffi-rs/latest/), [UniFFI Wasm](https://mozilla.github.io/uniffi-rs/latest/wasm/configuration.html), [Dart FFI](https://dart.dev/interop/c-interop), [Tauri commands](https://v2.tauri.app/develop/calling-rust/), [wasm-bindgen](https://wasm-bindgen.github.io/wasm-bindgen/).

Facade I/O should use owned DTOs and stable IDs, bounded strings/bytes, explicit units, versioned variants, machine-readable error code/retryability/safe message key/correlation ID. Do **not** export Rust references, allocator-owned raw buffers without paired release, locks, executors, DB handles, transport secrets, arbitrary UI closures, platform contexts, Dart/Tauri/Wasm types or chatty getters/setters. Prefer coarse use-case commands; page/batch result sets; use measured binary/resource paths for bulk data. Tauri supports binary responses/channels and FRB supports streams/codecs, but VIDA must define ordering and memory rules. [Tauri commands](https://v2.tauri.app/develop/calling-rust/), [FRB streams](https://cjycode.com/flutter_rust_bridge/guides/types/translatable/stream), [FRB codecs](https://cjycode.com/flutter_rust_bridge/guides/miscellaneous/codec).

### Proposed operation/event contract — to validate, not yet approved

1. `start(command, idempotency_key, scope) -> operation_id` returns promptly; Rust owns durable transitions and one vault writer.
2. `snapshot(scope, generation)` gives an authorized paged view; `events(after_seq, max_items)` gives ordered bounded batches or an adapter-native stream with the **same sequence semantics**.
3. Every event carries contract version, sequence/generation, scope, operation ID, type and safe payload. Overflow has declared coalescing/backpressure or `resync_required`; dropped observation never means lost durable state.
4. `cancel(operation_id)` is idempotent/cooperative, with one terminal outcome (`completed`, typed `failed`, or `cancelled`). Explicit `unsubscribe/close` is required. Dropped Dart Future, closed WebView or finalizer cannot determine correctness.
5. `suspend/resume/shutdown` checkpoints/reopens jobs, handles network change and rejects stale handles; it does not change Persona/Space semantics. Never call UI code while holding Rust locks.
6. Shells distinguish **local save, queued, remotely stored, domain-applied and read** where relevant. Relay connectivity is not durable delivery acknowledgment.

UniFFI explicitly lacks built-in future cancellation; FRB documents application-owned tokens; a Tauri command/task's existence does not decide what happens after its window closes. These facts motivate, but do not themselves validate, the proposed contract. [UniFFI async](https://mozilla.github.io/uniffi-rs/next/futures.html), [FRB cancellation](https://cjycode.com/flutter_rust_bridge/guides/how-to/cancel), [Tauri commands](https://v2.tauri.app/develop/calling-rust/).

### Toolchain, release and diagnostics

Pin/test a **tuple**: Rust revision, contract/schema, persistence migration, Iroh/adapter/ALPN/features, Flutter/Dart, FRB codegen/runtime, Android NDK/ABI, Xcode/iOS, Tauri/plugins, WebView2 floor and browser Wasm hash. Embed artifact identities at startup and reject mismatch with typed error rather than invoking mismatched symbols. Flutter/Dart does not promise ABI compatibility across compiler releases; generated binding and native binary should be built as one tested artifact set. [Flutter FAQ](https://docs.flutter.dev/resources/faq), [FRB versions](https://pub.dev/packages/flutter_rust_bridge/versions), [WebView versions](https://v2.tauri.app/reference/webview-versions/).

Shells may release independently **within a declared compatibility window**, not arbitrary binary mix-and-match. Keep golden codec/protocol vectors, N−1/N migration and rollback, unknown mandatory feature rejection and per-shell conformance. Mozilla Application Services packages generated Kotlin/Swift bindings with Rust libraries; Signal exposes Rust through language-specific bridges without treating internals as stable public API. These are transferable patterns, not proof of VIDA's particular bridge. [Mozilla pipeline](https://mozilla.github.io/application-services/book/build-and-publish-pipeline.html), [Signal bridge](https://github.com/signalapp/libsignal/blob/main/rust/bridge/README.md).

Retain Android ABI-specific unstripped symbols, Apple XCFramework slices/dSYMs, Windows PDBs and browser Wasm sourcemaps/debug identity. Pair crash traces with exact manifest and privacy-safe correlation ID, not user-data-bearing logs. [Apple XCFramework](https://developer.apple.com/documentation/xcode/creating-a-multi-platform-binary-framework-bundle), [Apple debug info](https://developer.apple.com/documentation/xcode/building-your-app-to-include-debugging-information), [Android JNI](https://developer.android.com/ndk/guides/jni-tips).

## Browser is a separate runtime and promise

Even if Tauri reuses a browser frontend, browser UI and Rust runtime are **not** the installed Tauri product. Native `dart:ffi` cannot carry a Flutter plugin to web; `wasm32-unknown-unknown` cannot assume native filesystem, sockets or threads; service workers/storage/background scheduling are browser-controlled. Iroh's first-party browser/Wasm example uses relays because browsers cannot open raw UDP/QUIC sockets; a hypothetical alternative transport does not establish native direct-path economics or delivery parity. [Flutter architecture](https://docs.flutter.dev/resources/architectural-overview), [wasm-bindgen target](https://wasm-bindgen.github.io/wasm-bindgen/reference/rust-targets.html), [PWA background](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation), [current Iroh browser example](https://github.com/n0-computer/iroh-esp32-examples/blob/main/wasm-gui/README.md), [Iroh browser design history](https://www.iroh.computer/blog/iroh-0-32-0-browser-alpha-qad-and-n0-future).

Two candidates remain: (A) worker-hosted Rust/Wasm subset with browser storage/network ports and explicit relay/service binding; (B) thinner web client against gateway/companion where browser policy precludes local runtime. A gateway may weaken anonymous/local autonomy or move trust boundaries; that requires product/security approval, not a silent implementation fallback. Test offline autonomy, identity/key policy, quota/eviction, relay egress, multi-tab locking and City Portal reach. Publish separate browser conformance and honest degraded-mode UX.

## Scenario-sensitive decision matrix

This is a **provisional ordinal screen**, not empirical scoring: `++` strong fit, `+` plausible, `?` conditional, `−` material mismatch. Hard VIDA gates (one Rust semantics, security, offline integrity, accessible journeys) cannot be traded away by scores. M = Flutter mobile; Wf = Flutter Windows; Wt = Tauri Windows; B = separate browser profile.

| Scenario; current v1 priority unknown | M + Wf + B | M + Wt + B | Native mobile + Wt + B | Universal Web/Tauri/PWA |
|---|---:|---:|---:|---:|
| Mobile-first, one mobile UI team | ++ | + | + if native staffing | − |
| Smallest team / fewest UI systems | ++ | ? (Dart + TS) | − | + on paper, mobile gate unproven |
| Rich Windows productivity UI plus same browser DOM | ? | ++ if reuse real | + | ? |
| Maximum native mobile control | + | + | ++ | − |
| Browser-independent release/DOM semantics | + (separate UI) | ++ if reuse real | ++ if reuse real | ++, but weaker runtime |
| Low UI lock-in / future migration | + via Rust facade | + via Rust facade; two UIs | + via Rust facade | ? browser policy |
| One Rust domain/protocol implementation | ++ if gates pass | ++ if gates pass | ++ if UniFFI passes | ? without profile split |

Windows flips mainly on **real browser-UI reuse and desktop editor/grid/accessibility**, not Rust affinity. If browser is a later companion, Tauri/browser reuse may be worth less than Flutter Windows reuse. If browser and dense desktop are near-term, Tauri may win. These are architecture inferences, not measured productivity claims. [Flutter Windows](https://docs.flutter.dev/platform-integration/windows/building), [Tauri frontend](https://v2.tauri.app/start/frontend/).

## Prototype programme and acceptance gates

Build a **single thin vertical slice** through one Rust facade, with the same seeded fixtures and tracing IDs on Android, iOS, both Windows shells and browser where applicable: message→note→task link, schema-defined field/workflow, two Spaces with grants/revoke, offline edit, search/notification and City Portal booking stub. Extend it with the raw-corpus cases: preserve per-app navigation stacks during account/Space switching; render capability-driven and public/moderator/read-only package views; include a reminder that becomes due after process shutdown; exercise the same business/booking identity through two city entry points, direct app and public website. The browser may explicitly mark unsupported operations. No shell may contain a second authorization engine or domain mutation implementation.

## Independent red-team findings and decision changes

The independent [red-team digest](digests/red-team.md) challenged the emerging recommendation against five failure modes. Its source-backed constraints change this report's exit rules:

1. **Always-on phone Iroh is a product/topology risk, not a Flutter-specific bug.** iOS/Android can suspend/defer work, and Flutter isolates cannot bypass this. G3 must measure direct vs durable delivery and accepted/stored/applied states on physical devices, including OS kill/reboot; failing the always-on aspiration triggers topology/promise revision, not an automatic switch to Swift/Kotlin. [Apple background modes](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes), [Android Doze](https://developer.android.com/training/monitoring-device-state/doze-standby), [Flutter isolates](https://docs.flutter.dev/perf/isolates).
2. **One Rust crate may still produce three different app behaviors.** FRB, Tauri IPC and browser worker/Wasm have different cancellation, backpressure, serialization and storage. G1/G2/G8 therefore require identical semantic fixtures and N−1/N release/persisted-state results; unsupported browser behavior is declared, never silently simulated. [FRB cancellation](https://cjycode.com/flutter_rust_bridge/guides/how-to/cancel), [Tauri commands](https://v2.tauri.app/develop/calling-rust/), [Flutter web FAQ](https://docs.flutter.dev/platform-integration/web/faq).
3. **XSS could become privileged IPC in Tauri.** G8 must use hostile rich-text/forum/portal content to attempt every Rust command and exfiltration route. Failure to demonstrate a safe content boundary rejects Tauri Windows even if desktop UX looks good. [Tauri authority](https://v2.tauri.app/security/runtime-authority/), [Tauri CSP](https://v2.tauri.app/security/csp/).
4. **Tauri must beat a real Flutter Windows build.** G5 now uses the hardest representative workflow, offline installer and update/rollback—not a framework sample—and includes engineering effort/defect rate as well as performance. Flutter Windows remains baseline until evidence shows Tauri's incremental value. [Flutter platforms](https://docs.flutter.dev/reference/supported-platforms), [Tauri installer](https://v2.tauri.app/distribute/windows-installer/).
5. **Composable super-app UX/a11y is the stress case.** G6 must use full message→document→task navigation, custom editor/input, large data and OS accessibility tech. If repeated core flows need native rewrites, select native mobile shells over the same Rust facade before broad build-out. [Flutter assistive technology](https://docs.flutter.dev/ui/accessibility/assistive-technologies), [Flutter web a11y](https://docs.flutter.dev/ui/accessibility/web-accessibility).

These are adversarial research findings, **not measured prototype failures**. They reinforce conditional approval and identify contained exits: native mobile+UniFFI if Flutter mobile fails UX; Flutter/native Windows if Tauri fails security/desktop; alternate bridge if FRB fails but neutral facade holds; product/topology change if OS background policy defeats an always-on promise.

## Risks, reversibility and open questions

| Risk | Early signal | Hedge/kill criterion |
|---|---|---|
| Two UI systems overwhelm a small team | Feature/a11y parity lag | Measure implementation hours/defects in Windows pair; prefer Flutter Windows absent material Tauri win |
| FRB community/codegen churn | Incompatible generator/build changes | Pin tuple, generated-code CI, neutral facade and small C-ABI contingency |
| Flutter custom rendering misses UX/a11y | Repeated native-view rewrites | Real-device full-flow test; native Swift/Kotlin+UniFFI fallback |
| Tauri XSS/WebView variation | Privileged IPC or offline install failure | Strict CSP/capabilities, hostile-content test, clean/offline VM; reject if containment fails |
| Browser cannot meet autonomy/offline promise | Storage loss or costly relay-only path | Separate browser capability ADR and gateway trust decision |
| Identity modes conflated by UI | Irreversible metadata correlation | Orthogonal controls, publication preview, cross-persona traffic/log fixture |

Unresolved decision backlog: v1 platform order and browser capability level; Windows pre-login service need; desktop workload/quality thresholds; declarative versus executable AppInstance extension tier; City Portal booking/profile/availability/notification authority and offline actions; compatibility/recovery window; sustainable Dart+TypeScript+Rust staffing. These materially change the platform choice and should be discussed one contour at a time. The raw corpus's historical suggestions do not answer them.

## Disposition and source freshness
