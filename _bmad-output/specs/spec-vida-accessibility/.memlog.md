- (direction) Headless express distillation of approved Windows accessibility NFR-PLAT-006/REQ-CLIENT-006/ADR-0020 plus PRD draft NFR-6 and UX discovery Accessibility Floor; distinguish approved mandate from candidate all-platform floor and do not claim tested builds.
- (capability) CAP-1: Windows user completes three Core App journeys, errors and dialogs using keyboard alone; success is an installed release build with visible focus, no pointer-only action or keyboard trap, including system menu and tray.
- (capability) CAP-2: Windows screen-reader user understands and operates Core Apps and sync/conflict/error state; success is actual assistive-technology inspection of names, roles, values, actions, reading order and announcements.
- (capability) CAP-3 candidate from UX/PRD: Android and iOS users operate the same Core journeys using touch, platform screen readers and applicable keyboard input; success is installed-build TalkBack/VoiceOver scenario matrix, not Flutter widget semantics alone.
- (capability) CAP-4 candidate from UX discovery: dynamic state changes remain understandable without color/animation, focus returns predictably, and privacy-safe announcements do not reveal inaccessible content; success is scenario evidence across save/delivery/conflict/share/call errors.
- (capability) CAP-5 candidate from UX discovery: enlarged text, display scaling, locale direction and reduced motion preserve primary actions and Resource/Space context; success is representative small/large/RTL/resized-device fixtures with no clipped essential action.
- (constraint) Approved Windows gate requires full installed Flutter client, keyboard, system menu/tray and screen-reader proof; shared Rust core or framework feature alone is not acceptance evidence.
- (constraint) WCAG 2.2 is an official web-content standard with technology-neutral testable criteria but is not automatically a selected conformance level for native VIDA; W3C/Flutter/Microsoft references guide mapping and actual installed-build tests.
- (constraint) Cross-platform floor in PRD/UX is draft/discovery, not user-approved; candidate fixtures do not silently convert it to approved requirement.

- (question) Select formal accessibility baseline and evidence scope: WCAG 2.2 mapped criteria, platform rules, assistive-technology/OS version matrix, and exception process?
- (question) Define live-call accessibility requirements such as captions or alternatives for audio/video communication; present product docs approve E2EE calls but not these modalities.
