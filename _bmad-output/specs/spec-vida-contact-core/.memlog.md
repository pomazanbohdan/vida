- (decision) Distill approved REQ-CONTACT-001..015 and PRD FR-4 into mandatory Contacts Core spec; adopt contact requirements, identity contract and ACL contract as load-bearing companions. OQ-0003 placement remains open.
- (capability) CAP-1 intent: user can create and retain a canonical VIDA ContactCard independent of OS/cloud address book; success: stable VIDA ID survives connector denial, disconnect and provider token expiry.
- (capability) CAP-2 intent: user can maintain rich contact fields with provenance, visibility and several typed VIDA identity bindings; success: card represents anonymous/private/public/federated bindings without implicit linking or export.
- (capability) CAP-3 intent: user can connect an address book in selected read/import, export or two-way mode; success: initial mode read/import, other modes require explicit choice and preview before external write, local contacts work on denial.
- (capability) CAP-4 intent: user can exchange only supported contact fields through platform and standard connectors; success: vCard 4.0 baseline round-trips compatible fields, unsupported/private identifiers do not leave VIDA, provider records are not canonical.
- (capability) CAP-5 intent: user can share selected card fields as default snapshot or explicit live share; success: recipient sees only previewed fields/bindings, snapshot freezes, live changes stop at revoke and recipient annotations remain separate.
- (capability) CAP-6 intent: user can manage card, connector link and provider record lifecycles separately; success: unlink never deletes other records, each destructive action names its target, token expiry reconciles without losing canonical card.
- (constraint) Contacts is mandatory Core service, not optional AppPackage; OS or Google records never own canonical VIDA card identity.
- (constraint) No automatic deduplication, merge or merge suggestion from name, phone, email, profile URL or provider record; manual edit is not dedup subsystem.
- (constraint) Anonymous/private identity bindings remain VIDA-local, never enter system/platform contacts or vCard; context isolation follows identity and ACL contracts.
- (constraint) Connector permissions are explicit, minimal and revocable; preview precedes every external write, denial does not disable local Contacts.
- (constraint) Android, Apple, Windows and Google connectors use only supported provider fields, consent and version/change-token semantics; CardDAV may transport but does not define VIDA canonical sync.
- (constraint) OWASP MASVS-PRIVACY-1 and MASWE-0066 govern permission minimization, informed consent, just-in-time requests and graceful denial; privacy failures are release blockers.
- (decision) Non-goals: generic notes/tasks/chat/file imports, automatic contact matching/deduplication, and choosing exact provider conflict or UI mapping before prototypes.
- (question) OQ-0003: Does canonical ContactCard belong to each Persona Personal Space or a separate encrypted Persona Contacts vault? Do not select until user confirms.
- (question) For each platform connector, which field mapping, partial authorization UX and concurrent provider edit policy passes prototype conformance? Requirement mandates test but not exact algorithm.
- (question) For live shared card across Spaces, what is recipient projection identity and replication authority? Respect field-scoped grant without inventing cross-Space Relation semantics.
