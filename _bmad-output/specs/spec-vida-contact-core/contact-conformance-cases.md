# Contacts Core conformance cases

These cases preserve the behavioral detail in [REQ-CONTACT-001–015](../../../docs/02-requirements/contact-card-requirements.md) and PRD FR-4. They are acceptance scenarios, not evidence that any connector has been implemented. Run each applicable connector case on Android, iOS and Windows with the supported provider/API profile; mark unsupported provider features explicitly.

In the Source column, a bare number such as `001` means `REQ-CONTACT-001` in the linked requirements; other prefixes name their own source contract.

## Provider evidence gate

- For each connector and direction (`read/import`, `export`, `two-way`), record supported fields, permission state, external-write preview, record version/change token, retry/reconcile outcome and any unsupported case. Provider docs alone are insufficient: the platform prototype must demonstrate the behavior.
- Apply the [connector contract](contact-connector-contract.md) to all three modes; `CONTACT-F17–F23` are source-backed candidate tests, not executed proof or an approved provider conflict algorithm.
- For vCard, record accepted format versions, any candidate UID mapping and conversion loss. A source UID is not a verified-human match or a permission to associate otherwise separate Personas; `CONTACT-F15/F16` are candidate tests, not an approved import/export-ID algorithm.
- Apply the [OWASP permission-minimization control](https://mas.owasp.org/MASVS/controls/MASVS-PRIVACY-1/) and [permission-management weakness](https://mas.owasp.org/MASWE/MASVS-PRIVACY/MASWE-0066/) as release gates. Test just-in-time permission request, clear rationale, denial, partial access and revocation without collecting more contacts than the selected flow needs.
- Parameterize storage and live-share tests by the still-open ContactCard owning scope. Do not treat option A in the [placement brief](../spec-vida-resource-domain/contact-card-placement-options.md) as approved merely because it is recommended.

## Preservation boundary

REQ-CONTACT-001–015 and PRD FR-4 are represented above and in the adopted requirements companion. The prior research's generic preview example of automatic merge is **superseded** by the later approved REQ-CONTACT-004 no-deduplication rule; no merge behavior is imported from it. Research narrative, platform histories and discovery lists are not requirements. Exact provider conflict algorithms, permission UX and cross-Space projection ownership remain open rather than being filled with a guessed implementation.
