# Owner-controlled recovery bundle — approved boundary, open byte profile

**Погоджено 2026-09-26:** комплект має дві незалежно збережені частини: випадковий recovery secret і зашифрований версійний bundle. Доступна копія зашифрованих ресурсів є третьою передумовою повернення історії, але не частиною секрету. Обов'язкового VIDA/федеративного вузла чи server escrow немає. [Дослідження і джерела](../../planning-artifacts/research/technical-vida-persona-recovery-crypto-and-bundle-2026-09-26/research.md).

| Компонент | Призначення | Заборона |
|---|---|---|
| Recovery secret | Власник зберігає поза VIDA; відкриває лише належний bundle. Кандидат: 256-бітний CSPRNG secret; людське представлення ще не затверджене. | Автоматично відправляти вузлу, включати в bundle, telemetry чи logs. |
| Encrypted bundle | Версійний portable export: окремий recovery-authority credential, необхідні data-key envelopes і signed controller checkpoint; authenticated metadata й покриття backup. | Копіювати приватні signing keys звичайних Devices або вважати зашифрований файл самодостатнім доказом актуальних прав. |
| Encrypted resource copy | Доступна репліка або власний export для повернення фактичних Note/File bytes. | Обіцяти відновлення історії за одним секретом чи за комплектом без ciphertext. |

Новий Device генерує новий keypair/`DeviceId`; тільки актуальний `ControllerState` приймає versioned signed `DeviceGrant`. Trusted-device add і lost-all-devices recovery — різні шляхи. Старий/stale checkpoint не доводить чинність authority; порядок конкуруючих переходів і ротація залишаються `OQ-0022/0024`.

UX відрізняє `secret_saved_claimed`, `bundle_available_verified`, `authority_restored`, `data_keys_restored` і `content_restored`. Позначка «історію можна відновити» потребує перевіреної доступної ciphertext-копії та достатнього coverage; окреме підтвердження користувача не є proof of storage. Кандидат production gate — fresh-profile restore, новий grant і звірка хоча б одного Note ID/content/attachment. Це не твердження, що тест уже пройшов.

**Погоджено 2026-09-29:** локальні зміни не блокуються недоступним backup; «збережено локально» не дорівнює «захищено після втрати пристрою». Для кожної перевіреної копії VIDA зберігає покритий operation frontier: зміна після нього не видається за відновлювану, якщо її не має інша доступна авторизована репліка. Після запису копію повторно читають, автентифіковано відкривають і звіряють manifest/покриття; лише тоді нова копія змінює попередню відому справну в тому самому класі зберігання. Перевірена цілісність локального файла не доводить доступність незалежної копії після втрати Device. Якщо місце export не дає повторно відкрити файл, результат — «експортовано», а не «backup перевірено». Окремий тест у свіжому профілі проводиться після першої копії з даними та ротації комплекту, але не після кожної зміни й не як умова активації Persona за Story 1.2. Конкретний causal-cut доказ покриття й протокол атомарної заміни/ротації — `OQ-0024`.

**Звичайна ротація погоджена 2026-09-29:** підготувати нові secret і bundle, перевірити export там, де його можна повторно відкрити (інакше чесно позначити тільки export), отримати підтвердження власника про їх окреме зберігання, і лише тоді зафіксувати підписаний controller transition, що відкликає старий комплект для нової shared-accepted authority. До commit старий комплект залишається чинним; crash до commit відновлює pending-ротацію. Ізольований peer зі старою історією може відновитися лише provisional до звірки. Звичайна робота не блокується. Підозрюваний витік використовує окремий терміновий revoke-flow. Атомарність commit, epoch binding і доказ поширення серед Devices — `OQ-0022/0024`.

**Уточнення 2026-09-29:** «нова копія змінює попередню» вище означає лише актуальний статус; попередній перевірений snapshot ресурсів фізично зберігається до окремого явного очищення. Добровільний розклад backup вмикають для Persona на налаштованому Device з обраним destination; secret не завантажується автоматично. За відсутності незалежної перевіреної копії або відставання backup frontier налаштування Persona показують сталий ненав'язливий ризик. Зміна controller frontier чи data-key epoch до signed commit ротації вимагає перебудувати bundle й повторно підтвердити окреме зберігання. Невдалий fresh-profile test після commit — критичний ризик; чинний trusted Device може створити виправлений kit без повернення старого authority. Автоматизований test після першої копії з даними й ротації — release gate; особистий guided test добровільний. Непідтримуваний mandatory bundle лишається незмінним до оновлення клієнта, без partial import.

**Відкрито до production:** canonical encoding/header/AAD, KDF/AEAD/nonce, human representation, bundle export/import atomicity, точний commit-time frontier/epoch guard, manifest privacy, current-controller anti-replay, конвергенція двох одночасних restore, compromise/repair proof, cross-platform golden fixtures і точний restore proof (`OQ-0022/0024`). [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html) є design/check gate, не готовою криптосхемою VIDA.

Відкликання старого kit припиняє його право на нову shared-accepted controller authority; воно не стирає вже отриманий plaintext і не гарантує ретроспективну конфіденційність старих snapshot, якщо старі data keys скомпрометовані.
