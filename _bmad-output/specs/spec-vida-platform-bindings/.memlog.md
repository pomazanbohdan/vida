- (direction) Create a decision-gated OQ-0035 BMad spec for one semantic Rust facade used by Flutter Android, iOS and Windows; do not select a physical FFI generator or production ABI without prototype proof.
- (capability) CAP-1 intent: each installed shell invokes the same authorized domain command/query contract; success: the same seeded action yields equivalent IDs, state and denial on three platforms and in a headless reference harness.
- (capability) CAP-2 intent: shells can submit and track durable asynchronous work without relying on a widget or process lifetime; success: crash, cancellation and reconnect preserve at-most-one accepted domain operation and recoverable outcome.
- (capability) CAP-3 intent: shells can observe bounded ordered changes and resynchronize after observer loss; success: gap, overflow and restart lead to explicit snapshot/reconcile, never silent event loss presented as current state.
- (capability) CAP-4 intent: boundary values, failures and resources have safe ownership and stable meaning; success: no borrowed Rust memory, leaked secret, uncaught panic, UI-thread stall or wrong-domain error mapping in conformance.
- (capability) CAP-5 intent: OS-specific lifecycle adapters can pause/resume one Rust runtime without changing product semantics; success: mobile suspend/kill/network switch and Windows multiwindow/restart recover durable state with one writer.
- (capability) CAP-6 intent: installed artifacts identify compatible API and native binary tuples; success: mismatched or unknown mandatory contract versions fail explicitly before unsafe calls, while declared compatible builds pass mixed-version fixtures.
- (constraint) Release 1 targets full Flutter Android, iOS and Windows installed clients with shared Rust core; WinUI, Tauri and browser bindings are outside this release decision.
- (constraint) Architecture AD-11/AD-12: first-party shell calls one vida-sdk facade; domain authorization, operation validation and transitions live in headless Rust core; boundary DTOs/IDs/errors are versioned in vida-contracts.
- (constraint) The bridge must preserve distinct local durability, replication, recipient delivery, domain authority and external effect axes; transport ACK and dropped observer cannot imply completion.
- (constraint) Owned bounded DTOs, explicit handle close, safe typed errors and no secrets or borrowed Rust references at the Dart boundary; platform secure-store/notification/push/lifecycle ports stay OS-specific.
- (constraint) Mobile background availability is OS-governed: the bridge and Flutter isolates cannot promise 24/7 reachability; durable reconcile and visible degradation remain required.
- (constraint) NodeHost remains the owner of Iroh endpoint lifecycle and typed transport failures; endpoint secrets never cross its port boundary. Physical FFI may not flatten those outcomes.
- (constraint) Conformance Plane owns stable ContractId, version, field/default/unknown behavior and release compatibility tuple. OQ-0037 still decides supported mixed-version window; OQ-0028 still decides signed wire bytes.
- (constraint) FRB is first prototype candidate, not VIDA contract; current Flutter package_ffi/build-hook path is an alternative packaging baseline, not proof that either bridge passes VIDA lifecycle tests.
- (question) Which tested bridge implementation and generated-code/toolchain tuple pass the same Android/iOS/Windows release-build conformance?
- (question) Which exact command/event DTO schema, handle/cancellation API and bulk-data path does the prototype validate without leaking secrets or duplicating domain semantics?
- (question) What supported host/API/FFI compatibility window and activation policy does OQ-0037 approve for mixed-version releases?
