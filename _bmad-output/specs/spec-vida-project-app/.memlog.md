updated: 2026-09-23T10:45

- (decision) Distill approved PROD-V1-BUNDLE-001, PROD-COMPOSITION-001, REQ-CLIENT-004/007/015/017/018 and ADR-0017 into a BMad Project App kernel. Keep resource-domain layout and authority proof open.
- (capability) CAP-1 intent: user creates personal and team projects in correct Space; success: personal project remains private and team project uses separate Shared Space without implicitly sharing Personal Space.
- (capability) CAP-2 intent: user manages tasks and subtasks with status assignee and dates in list and board views; success: both views present same authorized task state.
- (capability) CAP-3 intent: user links tasks to notes chats forum topics and files within project context; success: links navigate authorized targets without duplicating resource payload or granting access.
- (capability) CAP-4 intent: team discusses work in chat streams forum topics and resource-specific discussions; success: same communication resources are reusable from Project, not separate incompatible messenger stack.
- (capability) CAP-5 intent: user works on projects offline and reconciles; success: durable pending changes survive restart, accepted and conflicted states are distinguished and equal devices do not silently win.
- (capability) CAP-6 intent: authorized user resolves conflicting task status based on visible variants; success: comparable first accepted value holds, incomparable accepted values expose explicit conflict and resolution is a new authorized operation.
- (constraint) Project App is bundled and schema-driven; it composes standard Messenger Notes and Files in a Space rather than owning separate identity ACL sync or duplicate domain implementations.
- (constraint) Every task and related resource has current Space and action authorization; links and AppInstance dependencies never grant access by themselves.
- (constraint) Offline local commit is not remote acceptance; shared-read follows approved seven-day rights-check boundary and conflict semantics follow ADR-0017.
- (constraint) Android iOS and full Flutter Windows client must support Project v1 journey, keyboard and accessibility gates; no device priority for task status.
- (decision) Non-goals for Release 1: CRM, Gantt/timeline, time tracking, budgeting, advanced analytics, City Portal or business booking.
- (question) OQ-0003: Exact Project Container structure, move/copy/revision inheritance and relation ownership remain unapproved.
- (question) OQ-0033/0034: Serverless authority proof, accepted frontier and equivalence predicate for task/status conflicts are not yet selected.
- (question) OQ-0070: Exact dependent AppInstance manifest and cross-App default grants remain open, though actor ACL is mandatory.
- (event) No library is selected by this product kernel; Iroh transport and CRDT tests cannot by themselves decide exclusive task-status or project authorization semantics.
- (event) Validation pass 1 (Spec Law coherence): PASS. Six unique CAPs each state intent and observable success; constraints guard Space, ACL, offline/finality and equal-peer boundaries; non-goals and three open questions explicit; twelve PROJECT cases and companion paths checked.
- (event) Validation pass 2 (source preservation): PASS. Approved tasks/subtasks/status/assignee/dates/list-board, Personal versus Shared Space placement, bundled App composition, chat/forum/file relations, offline durable recovery and ADR-0017 conflict outcomes all mapped to CAPs and PROJECT-F01-F12. CRM/City/business and advanced planning explicitly excluded. Container topology and authority proof not invented.
- (decision) Adopt transport-sync requirements as companion because task status and conflict cases depend on REQ-SYNC-004/008/009.
- (event) Revalidation after companion update: PASS coherence and preservation. Transport-sync requirements are now adopted for status ordering, equal peers and conflict branches; CAP IDs and twelve PROJECT cases unchanged.
