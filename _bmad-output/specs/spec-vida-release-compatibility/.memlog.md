- (capability) CAP-1: Client can discover and classify a package release without activating it; success: discovered update leaves active AppInstance and grants unchanged and shows compatible, manual or incompatible outcome by declared profile.
- (capability) CAP-2: Client can verify a package and its dependency/host contract before activation; success: stale, substituted, unknown mandatory or wrong-ABI input is rejected before unsafe calls or migration.
- (capability) CAP-3: An authorized Space can activate a compatible package and schema without partial state; success: preflight failure retains previous active version or inactive first install, while successful accepted activation converges once across Devices.
- (capability) CAP-4: Mixed-version clients can read and write only when semantic round-trip is safe; success: an older client preserves unknown data or returns explicit pending/incompatible/read-only for affected AppInstance without losing writes or blocking other Apps.
- (constraint) Native host binary and AppPackage update channels are distinct; package retrieval and update discovery do not mutate Space state.
- (constraint) Current approved AppPackage modes are compatible-auto, security-auto, manual and pinned; exact security-auto eligibility remains open.
- (constraint) Compatible-auto excludes new mandatory capabilities, breaking conversion, expanded dependency contract or new data scope; existing authorized outcomes must remain forward-compatible.
- (constraint) Trust/freshness and artifact digest/signature verification precede isolated deterministic migration preflight; TUF-style anti-rollback is required, but does not prove converter correctness.
- (constraint) Package/schema activation is an authorized accepted Space operation; physical local-store migration is not shared authority. Exact activation actor/topology remains OQ-0039.
- (constraint) Pre-activation failure preserves prior active version, or leaves first activation inactive, and reports explicit cause; post-activation downgrade/rollback/fallback is outside current baseline.
- (constraint) Unknown mandatory protocol/host/FFI capability fails closed before unsafe call; old clients must not silently discard unknown schema fields or downgrade wire semantics.
- (question) Which exact host/API/FFI/schema/protocol mixed-version support window and cutoff policy are acceptable for Release 1?

- (question) Which old offline writes can be converted losslessly and which remain pending/incompatible until update?
