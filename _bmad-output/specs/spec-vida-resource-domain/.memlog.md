- (note) Headless express distillation from approved composable-workspace model, ADR-0001, PRD glossary and FR-19..21, ACL, app-package, schema-evolution, blob and collaborative-document contracts; sources stay adopted companions.
- (decision) Space is top-level ownership, membership, keys, policy and sync boundary; AppInstance is a package activation within one Space; Project is normally a container, not an automatic separate Space.
- (decision) Resource is addressed schema-defined record in a Space; Message, Forum Topic, Note, Task, File and ContactCard are product examples. Author of record is not Space Owner.
- (decision) Relation is a typed link between Resources without copying content or granting access. Attachment to File is a Relation; repeated attachment does not duplicate File identity/payload.
- (capability) CAP-1 stable Resource identity bound to owning Space, AppInstance and schema, with recoverable offline history and no duplicate on replay.
- (capability) CAP-2 Container grouping and inherited permissions at AppInstance, Container, ResourceType and Resource levels with hard-deny precedence, without deciding whether Container is itself a Resource.
- (capability) CAP-3 typed Relations and backlinks navigate only with independent target authorization; inaccessible titles/snippets never leak.
- (capability) CAP-4 one File Resource can be reused through multiple authorized attachment relations and retain versions/availability without copied payload.
- (capability) CAP-5 current schema write and versioned historical read preserve field identity, converters and unknown data; legacy edit materializes defaults or blocks missing required field.
- (capability) CAP-6 local search and portable export respect current Resource visibility, provenance and authorization across Apps and Spaces.
- (constraint) No relation, backlink, package dependency or search hit grants target read/write; Core validates every actor action, grants and key epoch.
- (constraint) A lower ACL scope cannot widen beyond upper maximum capabilities; hard deny wins. Space Owner governance is separate from the Resource ACL hierarchy.
- (constraint) Resource operations bind SchemaId/version and immutable history; changing schema does not silently delete fields; physical File payload belongs to BlobStore contract.
- (question) Is Container itself a Resource with an ID/schema/history, or a separate structural ACL scope; can one Resource belong to more than one Container?
- (question) Where does canonical ContactCard live relative to Persona and Personal Space, especially when a card is field-scoped shared?
- (question) What is Relation identity/ownership and cross-Space behavior: who may create/delete an edge, where is it replicated, and which side may see a backlink?
- (question) How do move/copy/revision operations choose target Space, metadata and ACL inheritance without widening access or losing history?
- (insight) Correction: not every Resource is owned by an AppInstance. File and ContactCard are Core resources; CAP-1 binds stable ID to owning scope and schema, while optional AppInstance provenance and ContactCard placement remain explicit.
- (constraint) OWASP IDOR and Authorization cross-check: a known, guessed or relation-exposed Resource ID must never substitute for object-level authorization on read, write, backlink, preview, search or export; deny by default and check each action.
