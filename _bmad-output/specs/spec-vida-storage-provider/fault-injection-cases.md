# OQ-0036 storage fault-injection recipes — draft

These recipes refine `STO-01..19` in [storage-behavior.md](storage-behavior.md). They are **planned conformance tests**, not executed results or a choice of provider, encryption, journal mode or safe compaction frontier. Approved [native client requirements](../../../docs/02-requirements/native-client-requirements.md), [BlobStore contract](../../../docs/04-specifications/blob-store-contract.md) and [binding behavior](../spec-vida-platform-bindings/binding-behavior.md) control if a recipe is ambiguous.

## Common method and oracle

- Prepare a named Persona vault, authorized Space, known signed-log frontier, stable operation ID and a fixture with Messenger message, Note edit, Project task, File attachment and pending outbox as applicable. Record the pre-cut state without logging private payload or keys.
- Inject at a **semantic boundary**: before durable commit, after commit but before callback, during staged byte write, before/after manifest publication, during projection rebuild, backup publication, migration or pruning. The adapter maps these to physical calls; the port does not prescribe tables or files.
- Terminate and reopen a fresh runtime. Query by stable ID for the validated operation, outbox intent, dedupe evidence, origin-durable frontier, blob manifest/pins and verified bytes, projection checkpoint/readiness and UI status. Compare with the pre-cut signed history and reference replay. Absence is conclusive only after recovery reaches its required frontier and authoritative log/dedupe lookup completes; before then the outcome remains unknown/pending. Never retry an ambiguous command with a new ID before querying.
- “Збережено локально” requires a recovered durable result for the **whole user action**, including required attachments. A pre-commit observer event or in-memory enqueue is not proof. The exact cross-platform commit-result API remains open in OQ-0035; fixtures constrain observable semantics, not its type signature. `Synchronized`, delivery and domain acceptance require separate receipts.
- Distinguish evidence tiers: **H** deterministic headless process kill/fault injection; **I** installed Android/iOS/Windows lifecycle and real storage directories; **P** abrupt OS crash/power interruption under the selected filesystem and durability policy. H or documentation never substitutes for P. Record results per tier, build and effective provider settings.

## Cut recipes

| Scope | Setup and cut | Reopen oracle and visible outcome |
|---|---|---|
| `STO-01/02/13`, `BND-02` | Create one offline action with stable ID and outbox. Cut before commit, then independently after commit/before callback. Inject disk-full/IO error at write, commit, temporary-file and checkpoint boundaries. | Before commit: no published logical operation, outbox, dedupe or advanced origin frontier; no Saved. After commit: all recover under the same ID, with Saved recoverable despite lost callback. If error leaves outcome unknown, reopen/query ID after recovery readiness; report failed only after complete authoritative lookup proves absence, or recover committed result if present. Staged orphan bytes may exist but no published reference points to them. Provider proves persisted facts; runtime proves one domain apply/no originating-command replay. |
| `REQ-CLIENT-009`, `STO-01/05` | Start one composed offline action with two required attachments; make second staging/verification fail after first succeeds. Cut again around logical publication. | The whole action is never marked Saved while any required component is uncommitted. A partial stage may leave collectible unreferenced bytes, not a dangling published reference. After restart UI distinguishes committed independent work from pending/failed components and never claims composed action succeeded. |
| `STO-03`, `BND-08` | Receive same signed operation twice with one missing causal dependency; kill after history insertion but before apply checkpoint. Restore dependency and reopen. | One validated history entry and dedupe identity, explicit pending dependency until applicable, no duplicate domain apply and no new originating command. Transport arrival alone yields neither `Synchronized` nor authority acceptance. |
| `STO-04/14`, `BND-04` | Lag or corrupt a search/UI projection, then kill during rebuild while observer detached. | Rebuild from validated signed history to declared frontier; remove stale terms under privacy rule. Until then return not-ready/stale rather than current view. Reattach supplies snapshot/frontier without inventing receipt or replaying command. |
| `STO-05/18`, `BND-14` | Cut origin file stage, flush, identity verification and manifest/pin publication. Separately race collection against new authorized pin; cut around metadata or byte removal. Test inbound download failure. | A published origin ref always has verified recoverable bytes; otherwise publication fails. Inbound failed download remains not-downloaded with retry path and no fabricated bytes. Live pin never dangles: either it wins with bytes or publication fails. Collection is restart-idempotent and retains unresolved variants. |
| `STO-07/08/12/17` | Interrupt live backup before publication, restore with pending outbox/unknown fields, interrupt physical migration, try an older valid backup after newer state/control head. | Only verified consistent backup replaces prior verified backup. Restore preserves stable IDs, pending work, historical fields and documented key path, or fails explicitly. Migration resumes forward or leaves previous layout readable; no partial ready state. Stale restore cannot silently reopen revoked data or replace newer recoverable state. This selects no anti-rollback proof or backup format. |
| `STO-06/19` | Resolve local file variant while another peer offline; attempt prune of history/outbox/dedupe/unknown extensions/blob refs and kill mid-prune. | Incomparable variants and every needed pin/replay/idempotency record remain until **separately selected** verified safe frontier proves cleanup. Age or local conflict resolution alone is insufficient. Restart preserves pending work; no OQ-0034 algorithm implied. |
| `STO-09/16` | After shared-Space rights revocation or seven days without authority-confirmed refresh, reopen stale cache with clock rollback. Concurrently open same Persona vault from two independent runtime instances/windows; suspend one writer. | Read gate blocks protected content despite stored ciphertext or projection. A single vault has no split writer or stale frontier publication; contender obtains typed busy/attach outcome, not second commit. Exact writer ownership across distinct Persona vaults remains open. |

`STO-10` is the provider × platform comparison axis for every applicable recipe, not another fault. `STO-11` repeats acknowledged-commit recipes at H/I/P tiers under each candidate's declared durability policy. `STO-15` additionally inspects release-build DB, WAL/journal, temporary, search, log and backup artifacts plus wrong-key/tamper behavior under the selected threat model. Record redacted provider revision, build, OS/device, storage-path class, effective config, exact cut, raw before/after observations, frontend claim and pass/fail. No secret or private content belongs in a report.

## Unresolved gates

- OQ-0034: safe frontier and retention proof; this recipe does not define it.
- OQ-0035: binding commit-result shape and multi-runtime ownership; observable Saved and one-writer behavior are required now.
- OQ-0036: provider tuple, durability tier, installed-platform conformance and benchmark evidence.
- OQ-0037/OQ-0053: key/restore custody and monotonic anti-rollback proof.

Security artifact tests use [OWASP MASVS-STORAGE-1](https://mas.owasp.org/MASVS/controls/MASVS-STORAGE-1/) and [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html) as verification references. They do not choose a provider, encryption implementation or deletion guarantee.
