updated: 2026-09-28T14:24

- (decision) Tor-only profile is a Release-1 product goal for autonomous anonymous Persona; ordinary Persona keeps direct-first plus approved VIDA relay fallback; this prevents implicit transport mixing.
- (constraint) A Tor-only action fails closed when Tor unavailable; local durable save remains possible, but no normal direct, relay, DNS, WebRTC, push, preview or diagnostics egress is permitted.
- (constraint) Tor is routing privacy, not content encryption, ACL or perfect anonymity; product wording cannot promise absolute anonymity.
- (capability) CAP-1: user selects isolated network profile for anonymous Persona; success is all named network egress routed through verified Tor path or held locally.
- (capability) CAP-2: anonymous Persona can synchronize and communicate with E2EE over Tor-compatible paths; success is peer receipts and ciphertext sync without direct-IP exposure in release-platform network traces.
- (capability) CAP-3: client fails closed during Tor outage or transport switch; success is pending local work and zero fallback packets to normal direct or relay.
- (assumption) Recommended: standard static Chromium Web remains a full ordinary VIDA Device in Release 1, but Tor-anonymous Web is not claimed until separate feasibility proof; user confirmation required.
- (question) Does Release-1 require Tor-anonymous mode in standard static Chromium Web as well as installed clients, despite raw socket and browser fingerprint constraints?
- (question) What anonymous native platform set is mandatory at Release-1 launch: Android only for first proof or Android, iOS and Windows together?
- (note) Chrome Direct Sockets is available to Isolated Web Apps, not ordinary static HTTPS pages; a remote gateway can see client IP before Tor and cannot prove Tor-only egress.
- (note) Arti landing and limitations pages disagree on production/onion readiness; current release and mobile support require proof rather than a premature library selection.

- (event) Preservation pass: Release-1 Tor goal, ordinary direct-first profile, fail-closed egress, E2EE separation, library gate, browser feasibility and story boundary appear in SPEC or adopted research/companion; no implementation proof claimed.
- (constraint) Correction: existing Release-1 installed platform scope is Android, iOS and Flutter Windows; Tor-only release evidence must cover all three, while first story may be Android proof before platform fan-out.

- (decision) Tor routing is an optional switch for any Persona and can be enabled or disabled at any time; turning it off requires a privacy warning, not a prohibition.
- (decision) Strict mutual Tor is a separate optional connection policy: peers must use a proven VIDA Tor route for that communication; local Tor routing alone does not require or announce the peer route.
- (constraint) When local Tor routing or mutual-Tor policy is active, unavailable Tor causes pending local work, never silent ordinary fallback. Switching modes re-evaluates queued sessions; Tor cannot erase past network exposure.

- (event) Coherence pass: CAP-1..4 preserve intent and observable success after optional-any-Persona toggle, separate strict mutual-Tor rule, typed invitation distinction, and Web boundary; story 2.13..2.15 remain drafts rather than implementation proof.

- (decision) Strict mutual-Tor policy may be configured at an individual chat or an entire Space. A strict Space requires Tor for all its network actions and resources; chat-level strict policy strengthens a non-strict Space and cannot weaken a strict Space.
- (decision) A Persona's Tor routing preference is a shared setting synchronized across that Persona's authorized Devices, not independently chosen per Device.
- (constraint) A Device cannot apply a newly synchronized Tor preference before receiving it while offline. UI must distinguish locally effective setting from propagation to other Devices and must not claim all Devices protected without evidence.
- (question) Can an existing ordinary Space be upgraded to strict Tor, or should a fully Tor-only Space be created as strict from the start to avoid stale offline Devices making ordinary connections before receiving the new policy?
