# Питання: часовий порядок, довірений AppCenter і майбутній вебдоступ

Це історичний пакет питань: початкові формулювання нижче не переважають пізніших відповідей. Погоджено: shared read блокується після 7 діб без rights proof; окремий AppCenter може мати належно надані ключі, але його деталізацію і web контур користувач відклав. Вебклієнта у v1 немає. Для task-status перший acceptance має пріоритет лише за спільного перевірного порядку; роз'єднані peers рівноправні, а concurrent rule відкритий (`REQ-SYNC-004/008`, ADR-0016).

1. **Час без доказу (`OQ-0034`).** Телефон офлайн показує 10:00, але відстає на день; ноутбук показує 10:05. Якщо жоден пристрій не має перевірного часу дії, чи показати `NeedsResolution` з обома намірами, щоб авторизований користувач обрав? Рекомендація: так; фізичний порядок не виводити з недовірених clock values.
2. **Час із невизначеністю (`OQ-0034`).** Два незалежні часові докази дають проміжки 10:00–10:06 і 10:03–10:08. Вони перекриваються. Чи вважати порядок недоведеним навіть коли відображені години різні? Рекомендація: так; автоматично обирати лише коли верхня межа одного інтервалу раніше нижньої межі другого.
3. **Межа доступу після 7 діб (`OQ-0062`).** Ноутбук місяць без мережі у shared Space. Читання заблоковане. Чи дозволяти створити новий локальний pending draft, який не читає старий вміст Space, чи призупинити і це до перевірки прав? Раніше durable-committed work у будь-якому разі зберігати захищеною й не видаляти; це питання не змінює безстроковий вік candidate.
4. **Підключення центру (`OQ-0057`).** Компанія запускає сервер. Чи Owner кожного shared Space окремо дозволяє йому стати decrypting peer, чи достатньо налаштування компанії? Рекомендація: окремий explicit grant для кожного Space; оператор вузла не отримує ключі автоматично.
5. **Межа ключів (`OQ-0057`).** Центр щойно підключено. Чи бачить він всю попередню історію Space, чи лише записи після підключення? Рекомендація: Owner обирає `future-only` або `history+future` при enrollment; показати обсяг доступу до підтвердження.
6. **Компрометація (`OQ-0057/0061`).** Сервер із ключами зламали. Хто може від'єднати його, змінити epochs і додати новий центр? Рекомендація: чинний Owner; offline peers не отримують нових ключів до reconciliation; вже скопійований plaintext не відкликати.
7. **Пріоритет sync (`OQ-0058`).** Центр онлайн і отримав задачу першим, телефон виконав зміну раніше офлайн. Чи є центр лише preferred replica/координатором доставки, а не автоматичним переможцем конфлікту? Рекомендація: так; порядок/authority — окремий контракт.
8. **Два центри (`OQ-0058`).** Компанія запустила два центри, зв'язок між ними зник. Чи обидва приймають остаточні зміни, чи один має чинний authority lease, а другий лише копіює/ставить у чергу? Рекомендація: не допустити двох незалежних остаточних acceptance одного control/resource scope; механізм визначити після topology decision.
9. **Дія людини (`OQ-0059`).** Олена через майбутній web UI змінює статус, але центр має технічні ключі всього Space. Чи operation має містити identity Олени й центру-виконавця та перевіряти її власне право `update`? Рекомендація: так; права центру на decrypt не підмінюють права Олени.
10. **Автоматизація (`OQ-0059`).** Правило само надсилає сповіщення о 9:00, коли всі телефони вимкнені. Чи дозволити центру робити це як окремому service principal з вузькими capabilities, а не під іменем Owner? Рекомендація: так, лише для явно ввімкненого AppInstance/Space.
11. **Межа виконання коду (`OQ-0061`).** Сторонній plugin Notes підключено до Space, де центр має ключі. Чи дозволено plugin працювати на центрі, чи у v1 його логіка лишається на користувацьких пристроях? Рекомендація: не запускати довільний сторонній код на центрі без окремого sandbox/capability рішення.
12. **Майбутня вебсесія (`OQ-0060`).** Людина закрила вкладку, але не вийшла. Чи ви мали на увазі 24 години **бездіяльності** й до тижня **абсолютної тривалості** сесії, чи інші межі? Рекомендація: визначити idle/absolute окремо, server-side expiry і повторну перевірку для зміни прав/ключів; точні числа затвердити після threat model. Це не змінює v1 native-only.

Орієнтири попереднього дослідження: [Google Spanner TrueTime](https://docs.cloud.google.com/spanner/docs/true-time-external-consistency) для доказів порядку; [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html), [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) для меж прав, ключів і сесій; [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html) для відокремлення людини від виконавця. Вони не встановлюють конкретного строку VIDA та не замінюють пізніші рішення користувача.

## Відповіді й зміна фокусу 2026-09-20

- На питання 1: якщо локальний час не дає певного порядку, перший успішний sync/authority acceptance застосовується як спільний стан. Другий автор за наявності чинного права може повторно подати свою зміну як нову або відмовитися від неї на користь уже застосованої. Механізм receipt лишається `OQ-0033`/`OQ-0034`.
- На питання 2: користувач очікує час до мілісекунд; це вимога до відображення timestamp, але не підтвердження точності годинників незалежних offline devices. Окремий bounded-time proof не є умовою вибору task-status за новим правилом.
- На питання 3: нову локальну чернетку без читання заблокованого shared content створювати можна; спільне прийняття потребує revalidation. Owner Personal Space підтверджує власні права локально. На цьому етапі Owner shared Space лишався `OQ-0063`; пізніше користувач затвердив для нього той самий семиденний read lock, що й для інших учасників.
- Питання 4–12 про окремий AppCenter, серверний код і майбутній web відкладено на прохання користувача; нинішній фокус — VIDA core і встановлювані застосунки пристроїв.
