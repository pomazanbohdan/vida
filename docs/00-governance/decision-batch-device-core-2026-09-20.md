# Наступні питання: VIDA core та застосунки пристроїв

> Historical decision batch. Platform timing in item 6 is finalized by `ADR-0020` on 2026-09-22: Release 1 includes Flutter Android/iOS/Windows; WinUI 3 may follow later.

Цей пакет зберігає початкові питання й відповіді, а не підміняє затверджені контракти. Окремий AppCenter/сервер і web користувач відклав. Для неавтомержних несумісних змін перший acceptance задає спільний стан лише за спільного перевірного порядку; непорівнювані peer-зміни потребують schema-level merge. Новий локальний draft після семиденного shared-read lock дозволений без читання заблокованих даних і лишається pending.

1. **Owner спільного Space (`OQ-0063`).** Два співвласники; один офлайн понад 7 днів, другий за цей час видалив його зі Space. Чи звільнити офлайн-Owner від read lock, хоча він може не знати про видалення, чи виняток має лише Owner власного Personal Space? Поточний документ підтверджує виняток лише для Personal Owner до вашої відповіді.
2. **Перше прийняття без постійного сервера (`OQ-0033/0034`).** Телефон і ноутбук локально змінили одну задачу, а потім з'єдналися напряму через Iroh. Що означає «синхронізувався першим»: перший пакет отримано, першу зміну надійно записано на іншому пристрої, чи першу зміну прийнято за Space authority policy? Рекомендація: останнє; receipt має бути спільно перевірним, інакше два пристрої можуть кожен назвати себе першим.
3. **Хто вирішує другий конфлікт (`OQ-0034`).** Телефон Богдана першим підтвердив `Done`; ноутбук Олени пізніше приніс `Cancelled`. Чи вибір «подати `Cancelled` як нову зміну / прийняти `Done`» належить лише Олені-авторці, чи будь-якому учаснику з поточним `update`? Рекомендація: авторці; адміністратор може окремо змінити стан звичайною новою командою.
4. **Текст і код (`OQ-0034`).** Телефон змінив перший абзац нотатки, ноутбук — третій: обидва редагування зберігаються автоматично? Якщо обидва змінили те саме речення, чи показати поруч два варіанти й дати редактору скласти фінальний текст? Рекомендація: так; не використовувати статусне first-sync правило як заміну merge тексту.
5. **Файли (`OQ-0034/0029`).** Два пристрої офлайн замінили той самий PDF/зображення різними файлами. Чи зберігати обидві версії та запитувати, яка є поточною, чи перша синхронізована заміна має перемогти? Рекомендація: обидві версії з явним вибором, без втрати вкладення.
6. **ОС першого випуску (`OQ-0008`).** Повноцінний Windows-клієнт погоджено. Чи одночасно в публічному v1 обов'язкові Android та iOS, або одна мобільна ОС може пройти beta раніше, поки друга наздоганяє? Це визначить обсяг спільного Rust core, bindings і conformance-матриці, але не обирає UI framework.

Орієнтири: [Automerge conflicts](https://automerge.org/docs/reference/documents/conflicts/) зберігає альтернативні scalar values і поєднує багато незалежних текстових змін; його deterministic winner не дорівнює VIDA authority acceptance. [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) вимагає перевіряти право на кожну нову команду. [Microsoft Windows Time](https://learn.microsoft.com/en-us/windows-server/networking/windows-time-service/how-the-windows-time-service-works) пояснює, чому мілісекундне відображення не гарантує точності годинника офлайн-пристрою.

## Відповіді користувача та залишкове питання

- **1:** початкова репліка не давала однозначної відповіді; пізніше користувач прямо затвердив семиденний read lock і для shared Owner. `OQ-0063` закрито в [ADR-0003](../03-architecture/decisions/ADR-0003-offline-revocation.md). Власний Personal Space не успадковує межу.
- **2:** самі connect, отримання пакета й запис на peer — етапи протоколу, не окремі варіанти продуктового рішення. Потрібен повний порядок auth/control/history/acceptance; дослідницький контур описано в [device-sync-session.md](../04-specifications/device-sync-session.md). Для одночасних прямих сесій `OQ-0033` лишається відкритим.
- **3:** рішення про пізніший несумісний variant бачить і приймає його автор на своєму пристрої; він має зрозуміти вже актуальний бізнес-стан. Автоматична допомога агента можлива, але правила її повноважень не затверджені.
- **4:** незалежні частини тексту/коду, як перший і третій абзаци, поєднуються автоматично; для того самого речення зберігаються обидва варіанти й потрібне рішення людини.
- **5:** у цій відповіді перша authority-accepted версія лишається поточною; пізніший автор може прийняти її, повторно подати свою або зберегти копію/ревізію. Пізніше уточнення рівноправності пристроїв нижче обмежує «першу» версію випадком спільного перевірного порядку; наступне рішення про непорівнювані PDF/status variants зафіксоване окремо в ADR-0017.
- **6:** Android та iOS включені у v1 з Flutter UI; Windows також у v1 як повний клієнт. Windows toolkit і точний binding лишаються відкритими. Користувач пізніше надасть репозиторій для оцінки повторного використання стека.

## Уточнення рівноправності пристроїв

Користувач відхилив наступну пропозицію про один призначений Owner-пристрій-арбітр. Для однієї Persona телефон, ноутбук та інші її авторизовані пристрої — рівноправні репліки; `Owner` є роллю учасника Space, не пристрою. Синхронізація й merge мають сходитися за однаковою історією без device-priority. Це прийнято в [ADR-0016](../03-architecture/decisions/ADR-0016-equal-device-peers.md). При цьому фізично «перший sync» у двох роз'єднаних групах не має спільного свідка.

## Уточнення конкурентних status/file змін

Користувач обрав явний multi-value conflict: після reconciliation несумісних непорівнюваних змін статусу задачі або заміни файла обидва варіанти зберігаються й показуються без автоматичного переможця. Людина з чинними правами на дію та читання обох variants вирішує його новою операцією на основі обох гілок; незалежні текстові правки зливаються. Два несумісні офлайн-рішення знову конфліктують; доведено еквівалентні дають один видимий результат із двома audit operations, а пізня прийнята несумісна гілка з непорівнюваним щодо рішення authority acceptance відкриває conflict знову. Це [ADR-0017](../03-architecture/decisions/ADR-0017-concurrent-status-file-conflict.md). Формат, proof, точний equivalence predicate, safe retention frontier і решта operation families відкриті в `OQ-0033`/`OQ-0034`.

## Відповіді на наступні десять питань

1. Еквівалентні офлайн-рішення: один видимий результат, обидва рішення й автори в історії; точний тест еквівалентності відкритий.
2. Пізня належно прийнята несумісна гілка з непорівнюваним щодо рішення authority acceptance: повторно відкрити конфлікт, не приховувати її старим рішенням; за порівнюваного acceptance діє правило першого прийняття.
3. Потрібні позначки «онлайн», «синхронізація», «завершено», «офлайн (один пристрій)» і число онлайн-пристроїв Space; це [UX-напрям](../04-specifications/sync-presence-status-model.md), не затверджений словник або протокол presence.
4. Незворотний зовнішній наслідок: чекати domain confirmation і відсутності відомого конфлікту; достатній proof і пізня гілка лишаються відкритими.
5. Агент пропонує рішення за замовчуванням; сам вирішує тільки після явного дозволу на цей тип дії та перевірки прав.
6. Resolver повинен мати доступ для читання кожного variant; закритий вміст не розкривається учаснику з одним лише правом update.
7. Owner shared Space підпадає під семиденний read lock; Owner Personal Space — ні.
8. Локальне рішення не дозволяє видалити альтернативний файл; потрібні safe retention frontier та попередження про використання місця.
9. Версія правила AppInstance прив'язується до вихідного fact; пристрої з різними версіями сходяться до одного логічного похідного resource.
10. Для альтернативи файла є дві окремі дії: ревізія того самого resource або нова копія з власним ID і перевіреними правами.

## Відповіді на пакет індикаторів, наслідків і файлів

1. Лічильник переноситься зі Space у профіль конкретного користувача: кількість його онлайн-пристроїв бачать усі, хто бачить профіль. Приватність анонімних/розділених Persona і можливість приховати presence відкриті в `OQ-0064`.
2. «Онлайн» означає можливість пристрою синхронізуватися з іншими, а не просто наявність інтернету. Proof, relay і старіння індикатора відкриті.
3–4. Користувач погодив роздільні стани, але просить напис «синхронізовано» замість «прийнято в Space». Це не скасовує різниці між реплікацією, domain acceptance і виконаним зовнішнім ефектом; точний обсяг напису відкритий.
5. Успішну синхронізацію з другим пристроєм Богдана користувач назвав «кворумом». Це ще не затверджує domain acceptance для shared Space: два пристрої однієї Persona можуть довести наявність двох копій, але не створюють другого незалежного учасника. Потрібно уточнити, що саме має підтверджувати цей кворум (`OQ-0033`).
6. Офлайн групове повідомлення, написане о 10:00 і опубліковане о 13:00, входить у спільний порядок о 13:00, а час написання показується окремо (`REQ-CLIENT-008`).
7. Для невідомого результату зовнішнього запиту користувач замовив дослідження референсів, а не затвердив retry policy. Порівняння RFC 9110, Stripe, Temporal, Iroh і Automerge додано до [effect constraints](../02-requirements/effect-execution-constraints.md); `OQ-0045` лишається відкритим.
8. Якщо зовнішній незворотний ефект уже виконано, а згодом виник конфлікт, пропонуємо виправлення; дії «скасувати вже виконане» немає (`REQ-EFFECT-011`).
9. Спеціальну схему «Owner/Admin дозволяє агенту» користувач відхилив: потрібна вже прийнята загальна permission model. Раніше погоджені opt-in для типу дії та поточні права не скасовані; їх точне відображення в ACL/ServicePrincipal — `OQ-0045`.
10. «Версія правила» потребує пояснення: це ревізія логіки `AppInstance`, а не новий запуск правила кожним пристроєм після sync. Якщо похідний ресурс уже створений, інший пристрій синхронізує його дані. Невирішений випадок — подія ще чекає виконання, а логіка тим часом оновилася (`OQ-0048`).
11. Для файлів буде налаштовувана межа автозавантаження; більший payload завантажується лише після явного підтвердження (`OQ-0066`). Це не відповідь на окреме питання, коли дозволено видаляти вже завантажені conflict variants (`OQ-0034`).

## Відповіді на пакет Iroh, receipts, conflict і schema evolution — 2026-09-21

1. Для анонімної Persona лічильник online-пристроїв видимий усім глядачам саме цього профілю; його не можна агрегувати з іншими Personas тієї самої людини.
2. Iroh лишається transport foundation, але `Endpoint::online`/address/QUIC ACK не є поточним application-liveness або apply proof. VIDA використовує власний authenticated sync handshake/receipt поверх Iroh; TTL ще відкритий (`OQ-0064`).
3. User-facing label — просто «синхронізовано». Його exact scope ще відкритий; він не означає authority acceptance або виконаний external effect.
4. Два пристрої однієї Persona після application receipt доводять replication redundancy/дві durable-копії, а не два незалежні authority votes.
5. Offline chat message отримує primary timestamp і shared order за publication після sync; local written-at лишається лише audit/detail metadata.
6. VIDA-to-VIDA request/outcome є durable state machine: owner resource записує outcome як signed state, requester отримує його звичайним sync після reconnect. Transport ACK не є outcome; сторонній API без durable status — окремий випадок.
7. Якщо operation із гілки поза causal confirmation frontier уже виконаного effect відкрила conflict, correction workflow створюється на стороні актора цієї гілки. Arrival order/clock не визначають автора конфлікту. Якщо поза frontier кілька непорівнюваних гілок, одного «винного» не призначаємо: correction чекає явного рішення. Попередній effect не стирається й не «скасовується» вигаданою дією.
8. Conflict merge/detection — глобальна core/runtime система для всіх schema-defined data; окремого `resolve_conflict` permission немає. Resolution авторизується як звичайна domain action плюс читання required variants.
9. Schema evolution використовує current schema для нових writes, versioned converter/migration для старих records і незмінну historical operation version. Additive defaulted fields можуть проектуватися lazy; activation/mixed-version/rollback mechanics відкриті в `OQ-0040`.
10. Якщо payload не записано на кінцевому пристрої, клієнт показує помилку та локальний стан файла «не завантажено»; shared manifest і remote copies не змінюються.
