# Рішення для епіків 1–2 — 2026-09-28

Статус: погоджено власником продукту в розмові; це поведінкові вимоги, не доказ реалізації. Межа: Stories 1.1–1.4 і 2.1–2.12. Раніше затверджені інваріанти direct-first, рівнозначних пристроїв, durable local save та application receipt залишаються чинними.

1. Два незалежні відновлення одним комплектом можуть локально працювати до зустрічі. Сумісні гілки об'єднуються; несумісні зміни controller/прав не отримують переможця за годинником чи типом пристрою. Спірні authority-дії зупиняються до перевірного узгодження, а локальні нотатки зберігаються.
2. Якщо після локального provisional restore доведено, що комплект раніше відкликали, старий grant не дає права публікації чи керування Persona. Незасинхронізований локальний текст не стирається мовчки: він доступний для копіювання/перенесення після нового підтвердження прав.
3. Після звичайної ротації recovery material створюється новий комплект і користувача наполегливо просять зберегти його; щоденне редагування не блокується. Випадок «комплект викрадено» є винятком: старий комплект відкликається негайно. UI не обіцяє відновлення зі старим комплектом.
4. Для підозрюваного витоку secret і bundle потрібна окрема термінова дія: новий комплект, відкликання старого та переузгодження пристроїв. Це захищає майбутній доступ, але не забирає дані, які вже встигли скопіювати.
5. Статичні Web-клієнти з різних HTTPS origins — різні пристрої; кожний проходить окреме явне enrollment з показом повного origin. Ідентичний код чи назва сайту не переносять ключі та grant між origins.
6. Підключений Web-клієнт у тому самому профілі браузера відкривається без повторного введення recovery secret; додаткове локальне блокування — опція. Це не робить чужий/скомпрометований браузер довіреним.
7. Якщо Web local write не вдався, UI показує «Не збережено», тримає текст на відкритому екрані та дозволяє retry або копіювання. Після закриття вкладки відновлення незбереженого тексту не обіцяється. Звичайний успішний save не отримує окремого browser warning.
8. Persona може налаштувати дозволений VIDA relay fallback або вимкнути relay-передачу. Direct залишається першим шляхом; якщо direct недоступний і relay вимкнено, durable local operation чекає без хибного «Синхронізовано».
9. Дві незалежні правки нотатки з однаковим підсумковим текстом і однаковими бізнесовими наслідками дають одну видиму проєкцію без conflict dialog; обидві операції лишаються в історії. Різні побічні наслідки не дозволяють вважати їх еквівалентними.
10. Старий клієнт не записує формат, якого не здатен безпечно прочитати чи передати. Несумісність обмежує зачеплений розділ/ресурс і показує потребу оновлення, не блокує всю VIDA; незбережений текст доступний для копіювання.

Реалізаційні питання залишаються відкритими: canonical controller history/reconciliation, compromised-kit rotation proof, byte/crypto profile, storage/commit fixtures, equality predicate, Web direct path and compatibility conformance. Ці рішення не змінюють `implementation-readiness.md` на PASS і не вважають тестові fixtures виконаними.

## Наступне погодження того самого дня

Власник продукту погодив решту запропонованих поведінкових рекомендацій щодо відновлення, пізнього прийняття операцій після зміни прав, delete-versus-edit, одночасних вставок, застарілої Web-вкладки та single-writer browser vault. Точний протокол/fixtures цих випадків ще треба відобразити в їхніх спеціалізованих контрактах; це погодження не означає, що вони реалізовані чи протестовані.

- Для Web Release 1 підтримувана browser family — **актуальні Chromium-based браузери**; Safari/Firefox не є вимогою першого випуску. Мінімальні версії визначить conformance matrix.
- Для Release 1 погоджено опціональну Tor-маршрутизацію будь-якої Persona з можливістю явного перемикання будь-коли. Окрема опція комунікації вимагатиме Tor від обох сторін; локальне вимкнення її не послаблює. Це не Delta Chat/Chatmail relay, не заміна E2EE та не дозвіл непомітно змішувати Tor зі звичайним direct/relay. [Вимоги](../02-requirements/tor-anonymous-mode-requirements.md) і [дослідження](../../_bmad-output/planning-artifacts/research/technical-vida-tor-anonymous-transport-2026-09-28/research.md) фіксують scope, але Rust runtime, Iroh adapter і доказ відсутності витоків лишаються відкритими. Формулювання «повністю анонімний» не є перевірною гарантією.

## Погодження Web/Tor межі

У Release 1 встановлювані Android, iOS і Flutter Windows мають пройти Tor conformance для будь-якої Persona, що ввімкнула Tor. Статичний Chromium Web залишається повноцінним клієнтом звичайного VIDA-профілю; для Tor-enabled Persona або strict mutual-Tor розмови він не виконує мережевих дій через звичайний direct/relay. Дозволені локальні зміни можуть чекати на Tor-сумісний клієнт. Browser Tor mode — окремий пізніший increment після нового delivery/security proof. Це продуктове рішення, не підтвердження готовності native Tor реалізації.
