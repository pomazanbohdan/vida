# ADR-0009: Керована прикладна логіка в пакетах і розширеннях

## Context

`ADR-0007` відділив пакети від довільного виконуваного коду клієнта. Користувач уточнив, що під «кодом плагіна» має на увазі прикладні операції над даними та схемами: власний застосунок може повторно використати базові Notes/Knowledge й додати, замінити або вимкнути частину їхньої поведінки. У попередньому research для цього розглядали Rhai-обробники та Wasm-компоненти; Iroh там є транспортом, а не рушієм прикладної логіки.

## Decision

`AppPackage` і пакет-розширення `MUST` мати можливість визначати керовану прикладну логіку над schema-defined ресурсами. Розширення `MUST` мати можливість додати, замінити або вимкнути **визначену поведінку базового застосунку** в дозволеному контексті через явний контракт runtime. Це стосується бізнес-правил, команд, обробки подій і workflow, а не права підмінити довірені механізми платформи.

VIDA core `MUST` залишатися владним для перевірки permissions, приймання й запису операцій, цілісності даних, ключів і синхронізації. Пакетна логіка `MUST` отримувати дані та ініціювати ефекти лише через контрольовані host API; результат обробника не є самодостатнім дозволом на зміну ресурсу. Iroh `MUST NOT` вважатися scripting/plugin engine: він належить до мережевого контуру `ADR-0005`.

Це рішення уточнює межу `ADR-0007`: заборона на **довільний** завантажуваний код не забороняє авторську прикладну логіку під контролем runtime. Водночас воно не обирає Rhai, Wasmtime/WIT, іншу мову чи sandbox і не схвалює прямий доступ плагіна до ОС, сховища або transport internals. Точний набір extension points, порядок обробників і scope заміни базової поведінки залишаються відкритими.

## Rationale

Інакше «плагін» був би лише набором форм і полів та не зміг би реалізувати користувацький сценарій Notes або власний процес без зміни Rust-ядра. Явна межа host API дозволяє розвивати прикладну поведінку окремо від інваріантів безпеки й синхронізації.

## Consequences

- Потрібні versioned extension contract, пакування логіки та capability negotiation.
- Потрібні правила для додавання, заміни, вимкнення й композиції обробників та вирішення конфліктів між кількома розширеннями.
- Потрібні ліміти виконання, контроль побічних ефектів, відтворюваність і conformance на підтримуваних платформах.
- Вибір Rhai проти Wasm/Wasmtime та виконання на підтримуваних встановлюваних mobile/desktop клієнтах проходять окремий prototype gate (`OQ-0009`). Wasm тут можливий як sandbox прикладної логіки, не як браузерний клієнт VIDA ([ADR-0014](ADR-0014-native-only-vida-clients.md)).

## Acceptance evidence

1. Тестовий пакет додає власну логіку до дії Notes без зміни Rust core або нового client release, коли підтримуваний runtime уже доступний.
2. Розширення замінює або вимикає названу прикладну дію Notes; невідома або непідтримувана точка розширення відхиляється явно.
3. Пряма заборонена команда з обробника відхиляється trusted core; пакету не надається прямий доступ до файлів сховища, ключів чи Iroh endpoint.

## Open questions

- Область дії заміни визначено пізнішим [ADR-0010](ADR-0010-instance-scoped-app-logic.md): лише цільовий `AppInstance`/Space.
- Пріоритет instance process і відповідальність розробника за композицію визначено в пізнішому [ADR-0011](ADR-0011-instance-trigger-precedence.md); точні фази, fallback і помилки залишаються відкритими.
- Який executor та пакетний формат прикладної логіки: Rhai, Wasm/Wasmtime або інше?
- Які дії можуть виконуватися локально повторно, а які потребують єдиного виконавця та durable idempotency?
