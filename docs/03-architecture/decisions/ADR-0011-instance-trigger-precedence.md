# ADR-0011: Пріоритет процесу AppInstance над базовим тригером

## Context

Після рішення про локальну для `AppInstance` логіку постало питання про два розширення, які працюють із тією самою дією. Користувач відхилив окремий вибір переможця Owner-ом і додаткове платформне відстеження бізнес-конфліктів. Композиція дій усередині застосунку належить його розробнику.

## Decision

Для визначених точок прикладного розширення (приклади: створення, зміна, збереження ресурсу) процес або handler, визначений застосунком у його `AppInstance`, `MUST` мати пріоритет над базовим handler на тому самому тригері. Це правило діє лише в межах цільового `AppInstance`/Space за `ADR-0010`.

Розробник застосунку `MUST` відповідати за композицію власних процесів і розширень, щоб вони не суперечили один одному. Додаткові незалежні дії, наприклад реакція після збереження, можуть співіснувати з основною дією. VIDA `MUST NOT` вимагати окремого Owner-level вибору одного з таких handler-ів чи вводити самостійну систему арбітражу їхніх бізнес-конфліктів усередині `AppInstance`.

Це не скасовує trusted перевірки доступу, приймання операцій, версійної сумісності й журналу безпекових/доменних операцій. Пріоритет застосунку не означає права перевизначити інваріанти ядра. Чи виконується базовий handler після пріоритетного автоматично або тільки за явним викликом/композицією, це рішення ще не визначає.

## Rationale

Розробник контролює логіку свого застосунку; додатковий вибір Owner-а створював би окрему модель керування там, де потрібен лише визначений контракт тригерів. Водночас пріоритет над базовою поведінкою потрібний для справжнього перевизначення, а не лише для додавання побічних дій.

## Consequences

- Потрібен версійний перелік доступних прикладних тригерів/дій і тест на пріоритет у межах одного instance.
- Визначення порядку декількох власних процесів — відповідальність пакета/розробника, не додатковий Owner-level arbitration UI.
- Правила продовження/приглушення базового handler та fail behavior після помилки потребують окремого рішення.

## Acceptance evidence

1. Для того самого тригера збереження Notes handler цільового `AppInstance` має пріоритет над базовим handler.
2. Незалежна дія після збереження може бути скомпонована розробником без запиту Owner-у на вибір «переможця».
3. Інші `AppInstance`/Spaces зберігають свою базову поведінку; заборонена команда з handler відхиляється core.

## Open questions

- Чи базовий handler пропускається за замовчуванням при instance override, чи виконується після нього автоматично?
- Яка конкретна семантика тригерів, фаз, помилок і побічних ефектів для кількох процесів застосунку?
