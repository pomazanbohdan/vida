# ADR-0016: Пристрої користувача рівноправні у синхронізації

## Контекст

Пропозиція призначити один Owner-пристрій арбітром serverless Space відхилена користувачем 2026-09-20. Роль `Owner` належить учаснику/Persona в Space, а не телефону чи ноутбуку. Будь-який авторизований пристрій цього учасника може вести локальну роботу й брати участь у прямій синхронізації.

## Рішення

- Жоден пристрій одного користувача `MUST NOT` мати внутрішній пріоритет, роль «master/Owner», одноосібне право остаточного sync commit чи перевагу в merge лише через тип пристрою, час онлайн або порядок з'єднання.
- Core `MUST` перевіряти право актора/Space та device binding окремо. Ідентифікатор репліки/сеансу `MAY` розрізняти конкурентні операції для причинності й dedupe, але `MUST NOT` сам означати вищі права або наперед визначену бізнес-перевагу пристрою.
- Усі рівноправні репліки `MUST` зберігати підписану причинну історію й, отримавши той самий валідний набір data operations **і той самий перевірений control/acceptance state**, сходитися до того самого стану незалежно від порядку доставки. Пристрій офлайн може підготувати локальний candidate за останніми відомими правами, але це не доказ чинного grant. Несумісні альтернативи `MUST` залишатися доступними для авторизованого вирішення; merge policy визначається типом ресурсу/операції, не конкретним пристроєм. Автоматичний winner за replica ID `MUST NOT` непомітно перетворюватися на бізнес-пріоритет.
- Пріоритет першого прийнятого sync застосовується лише там, де існує спільний перевірний порядок цих прийнять. Для незалежних одночасних змін у роз'єднаних peer-групах **глобального «першого sync» немає**; для task status і file replacement затверджено явний конфлікт у [ADR-0017](ADR-0017-concurrent-status-file-conflict.md), а proof, provisional UX та інші operation families залишаються `OQ-0033`/`OQ-0034`.

## Наслідки й перевірка

- Фізичний пристрій не отримує Owner-прав від підпису, Iroh endpoint, зберігання blob чи факту першого ACK. Control grants і відкликання лишаються domain policy.
- Conformance має переставляти порядок доставки, запускати дві ізольовані peer-групи та згодом з'єднувати їх: однакові data operations + однаковий перевірений control state → однаковий стан/набір конфліктів, незалежно від платформи й першого peer. Заміна телефона на ноутбук у сценарії не змінює результат; окремі fixtures перевіряють revocation проти офлайн-операції.
- [Automerge conflicts](https://automerge.org/docs/reference/documents/conflicts/) і [Loro sync](https://loro.dev/docs/tutorial/sync) демонструють детерміновану збіжність та окрему обробку конкурентних значень; це референси, не вибір конкретної бібліотеки чи бізнес-правила. Перевірено 2026-09-20.
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) вимагає перевіряти дозволи на кожну дію. Тому merge/re-submit не успадковує право від факту володіння пристроєм або колишнього grant; тест має відхиляти операцію відкликаного учасника після reconciliation. Перевірено 2026-09-20.
