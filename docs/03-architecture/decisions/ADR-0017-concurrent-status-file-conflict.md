# ADR-0017: Явний конфлікт конкурентних статусів задачі та замін файла

## Контекст

У serverless peer sync дві групи пристроїв можуть незалежно прийняти несумісні зміни одного статусу задачі або файла. Коли й підтвердження цих гілок не мають спільного перевірного порядку, локальний годинник, час прибуття пакета й replica ID не встановлюють спільного «першого». Користувач затвердив 2026-09-20 явне вирішення, а не автоматичний winner. Правило не змінює [ADR-0016](ADR-0016-equal-device-peers.md): пристрої рівноправні, права належать актору.

## Рішення

- Якщо несумісні зміни task status або заміни файла пройшли належну authority policy, але **їхні прийняття не мають спільного перевірного порядку**, після обміну гілками всі авторизовані peers `MUST` показати один явний стан «конфлікт — потрібне рішення» з обома variants; жоден `MUST NOT` оголошувати автоматичний canonical winner. Якщо самі операції створені конкурентно, але їхні authority acceptances порівнювані, діє правило першого прийняття з ADR-0016/REQ-SYNC-004, а не цей multi-value випадок. Відкликаний/невалідний pending candidate залишається recoverable за правами, але не проектується як прийнята спільна гілка лише через доставку; точний acceptance proof — `OQ-0033`.
- Обидва прийняті variants `MUST` залишатися durable/recoverable згідно з retention і чинними правами; читання конкретного variant потребує окремої чинної перевірки доступу. Для файла це включає blob payloads і pins, не тільки log references; локальне рішення однієї peer-групи саме по собі не доводить, що всі альтернативи можна unpin/GC до виявлення інших правомірних офлайн-рішень. Безпечний retention frontier лишається `OQ-0034`. Бібліотечний CRDT tie-break або звичайне assignment, що приховує/очищає внутрішній conflict, `MUST NOT` використовуватися як бізнесовий поточний статус/файл або тихе вирішення.
- Актор із **чинним** правом на цю дію та правом читати всі variants, потрібні для рішення, `MAY` подати нову resolution operation, яка причинно враховує обидві альтернативи й проходить перевірку Space/object/action rights та preconditions. Якщо актор не може прочитати хоча б один variant, клієнт показує лише безпечний сигнал про конфлікт без закритих деталей і спрямовує до уповноваженого учасника; право змінювати ресурс саме по собі не дозволяє вирішувати невидимий варіант. `sync.apply` цієї історії `MUST NOT` повторно запускати початкову бізнес-команду чи зовнішній ефект.
- Conflict engine є загальною частиною `vida-core`/`vida-runtime`, а не opt-in plugin і не окрема роль. Permission matrix `MUST NOT` містити універсальну capability `resolve_conflict`: resolution operation авторизується як звичайна зміна відповідного resource/action (`update_status`, `replace_file`, `edit_note` тощо) плюс доступ до variants, які вона причинно покриває. Це не скасовує domain-specific merge policy, UI для явного multi-value conflict або окремий opt-in агента на автоматичне виконання звичайної domain action.
- Якщо два уповноважені актори офлайн незалежно вирішили той самий conflict **з несумісними результатами**, обидві resolution operations пройшли застосовну authority policy, а їхні прийняття залишилися непорівнюваними, після reconciliation виникає **новий явний multi-value conflict між двома рішеннями**, без автоматичного winner. Подальше рішення `MUST` причинно врахувати обидва актуальні resolution heads і знову пройти перевірку чинних прав. Якщо прийняття порівнювані, діє правило першого прийняття. Точний proof/wire лишається `OQ-0033`/`OQ-0034`.
- Якщо два незалежні рішення мають доведено однаковий канонічний бізнес-результат **і ті самі наслідки**, після reconciliation `MUST` бути один видимий результат, але обидві operations, авторство і причинність `MUST` залишитися в історії. Збіг лише напису статусу, digest файла чи ID без перевірки наслідків не є доказом еквівалентності; точний equivalence predicate лишається `OQ-0034`. Повторне відтворення історії не дублює наслідки.
- Якщо після рішення надходить раніше невідома належно прийнята гілка, що причинно не входила до рішення, має з ним несумісний результат **і непорівнюване authority acceptance**, `MUST` знову з'явитися явний conflict без автоматичного winner. За порівнюваного acceptance діє правило першого прийняття. Старе рішення та пізню гілку `MUST` зберегти; невалідний або відкликаний pending candidate не відкриває прийнятий спільний conflict лише через доставку.
- Для альтернативної версії файла `MUST` бути доступні дві явні дії за чинними правами: зберегти як ревізію того самого ресурсу або створити окрему копію з власним ID і окремо перевіреними правами. Жодна з них не повинна тихо підміняти основний файл; точний lifecycle, metadata inheritance і UX лишаються `OQ-0034`.
- За спільного перевірного порядку прийняття лишається правило першого acceptance з `REQ-SYNC-004/007`. Незалежні зміни різних фрагментів тексту `MUST` поєднуватися автоматично за `REQ-SYNC-006`; це ADR не переносить status/file правило на всі operation families.

## Наслідки й перевірка

- Fixture створює дві ізольовані гілки з різними статусами або file replacements, міняє порядок доставки й платформи та перевіряє однаковий unresolved conflict із двома accepted variants без winner після reconciliation; invalid/revoked pending candidate не потрапляє до спільної проєкції. Blob GC не прибирає жоден живий variant до рішення.
- Нова resolution operation посилається на обидві гілки; тест на відкликане право або заборону читання одного variant відхиляє її без витоку закритого вмісту. Окремі fixtures перевіряють: два несумісні належно прийняті офлайн-рішення → новий однаковий unresolved conflict; два доведено еквівалентні рішення → один видимий результат, обидва audit records, один логічний наслідок; пізня прийнята несумісна третя гілка з непорівнюваним acceptance → повторний conflict, а з порівнюваним acceptance → правило першого прийняття; revision і copy не переписують основний файл та перевіряють права. Точне кодування, equivalence predicate, capability mapping, provisional UX та інші operation families лишаються `OQ-0033`/`OQ-0034`.
- [Automerge conflicts](https://automerge.org/docs/reference/documents/conflicts/) зберігає конкурентні значення, але його детерміноване видиме значення не є рішенням VIDA; [Loro sync](https://loro.dev/docs/tutorial/sync) демонструє збіжність peers незалежно від доставки. Перевірено 2026-09-20.
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) підтримує перевірку доступу для кожної нової дії й deny by default; тому старий grant не авторизує resolution. Перевірено 2026-09-20.
