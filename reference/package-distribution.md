# ADR-0008: VIDA marketplace and external package repositories

## Context

`ADR-0007` дозволяє сумісні зовнішні `AppPackage`, але не визначає, звідки їх знаходити та як дізнаватися про нові версії. Користувач підтвердив потребу в керованому VIDA маркетплейсі, підключенні сторонніх репозиторіїв і розповсюдженні як застосунків, так і розширень базових застосунків.

## Decision

VIDA `MUST` мати вбудований, контрольований проєктом маркетплейс для discovery застосунків і розширень. Клієнт `MUST` також дозволяти підключати зовнішні джерела/репозиторії сумісних пакетів; вбудований маркетплейс не є єдиним каналом розповсюдження. Походження пакета (`source repository`, видавець, якщо відомий) `MUST` залишатися видимим і не втрачатися після підключення джерела.

Модель розповсюдження `MUST` розрізняти пакет застосунку і пакет-розширення («плагін»), який має цільовий базовий застосунок. Підключений репозиторій `MUST` надавати метадані, за якими VIDA може виявити доступність нової версії пакета. Виявлення оновлення `MUST NOT` саме по собі означати дозвіл на встановлення, активацію або міграцію даних.

Усі пакети після отримання `MUST` проходити спільний compatibility/permission contract з `ADR-0007`. Зовнішнє походження не надає пакету чи його видавцю доступу до Space. Цей ADR не схвалює довільний виконуваний код плагіна на клієнті: до окремого рішення діє декларативна межа `ADR-0007`.

Подальше [ADR-0009](ADR-0009-managed-application-logic.md) надало саме таке уточнення: керована прикладна логіка пакета дозволена, довільний доступ до платформи — ні. Це не змінює рішення про канали розповсюдження.

## Rationale

Перший канал дає VIDA власний контрольований каталог; зовнішні репозиторії зберігають відкритість екосистеми. Окрема стадія discovery/update awareness дає інформацію про реліз без прихованого розширення прав або автоматичної зміни працюючого `AppInstance`.

## Consequences

- Потрібні окремі стани connected source, discovered release, obtained package та activated `AppInstance`.
- Потрібні package type і target-host relation для розширень; їхній точний контракт ще не затверджено.
- Потрібні provenance, metadata freshness, compatibility та update-status UX для обох каналів.
- Формат репозиторію/маніфесту, publisher trust, підписи, auto-update, міграції й rollback потребують наступних рішень.

## Acceptance evidence

1. Клієнт показує вбудований VIDA маркетплейс і дозволяє підключити окремий зовнішній репозиторій.
2. У тестовому зовнішньому репозиторії видно окремо пакет застосунку та розширення базового застосунку з позначеним джерелом.
3. Після публікації нової версії metadata дає статус «оновлення доступне», не змінюючи встановлений package або `AppInstance`.
4. Пакет із зовнішнього джерела не обходить перевірки сумісності та Space authorization.

## Open questions

- Керовану прикладну логіку пакетів уточнено в пізнішому [ADR-0009](ADR-0009-managed-application-logic.md); її виконавець і sandbox лишаються відкритими.
- Які формати package manifest, repository index і update metadata обрати?
- Яка політика довіри й схвалення встановлення для VIDA marketplace та сторонніх джерел?
- Як працюють версійні обмеження, підписи, відкликання, міграції, автоматичні оновлення й rollback?
