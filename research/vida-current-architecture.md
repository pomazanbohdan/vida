# Vida — актуальна модель просторів, прав, зберігання та синхронізації

> Статус документа: робочий архітектурний зріз  
> Дата актуалізації: 2026-09-18  
> Проєкт: Vida

## 1. Призначення

Документ фіксує поточну узгоджену модель Vida після обговорень про:

- персональні, організаційні, проєктні та публічні простори;
- застосунки, групи, канали, колекції й ресурси;
- багаторівневі права доступу;
- local-first роботу й Iroh-синхронізацію;
- змінні фізичні сховища: оптимізоване бінарне, Markdown/файли, SQL/NoSQL, S3 та зовнішні API;
- прозоре перемикання сховища без зміни коду застосунку.

## 2. Статуси рішень

| Статус | Значення |
|---|---|
| Прийнято | Частина цільової архітектури |
| Для прототипування | Потрібна практична перевірка |
| Кандидат | Технологія або реалізація ще не затверджена |
| Відкладено | Не входить у найближчу реалізацію |
| Відхилено | Не використовується |
| Замінено | Попереднє рішення втратило актуальність |

## 3. Прийняті принципи

1. Проєкт називається **Vida**.
2. Vida є portable/local-first платформою; центральна PostgreSQL не є обов'язковою основою всієї платформи.
3. **Iroh та його офіційна інфраструктура** є цільовою основою мережевої взаємодії та синхронізації.
4. За замовчуванням використовується оптимізоване бінарне локальне сховище.
5. Фізичне сховище можна змінювати для конкретного середовища, Space, екземпляра застосунку, контейнера, dataset або типу ресурсу.
6. Один пакет застосунку повинен працювати з різними storage providers без зміни прикладного коду.
7. Права доступу, прийняття операцій, фізичне зберігання та синхронізація є окремими архітектурними механізмами.
8. CRDT застосовується вибірково, а не до кожного виду даних.
9. Серверні застосунки й SaaS можуть використовувати SQL/NoSQL та S3.
10. Markdown може бути експортом або повноцінним файловим storage provider.
11. Зв'язок або відображення ресурсу в іншому Space саме по собі не надає доступу.

## 4. Незалежні архітектурні осі

Vida не повинна змішувати такі поняття:

| Вісь | Запитання |
|---|---|
| Ownership | Якому Space належить ресурс? |
| Authorization | Хто й за яких умов може виконати дію? |
| Governance/Authority | Який вузол або набір вузлів може прийняти операцію? |
| Storage Binding | Де і в якому форматі зберігаються дані? |
| Replication | Які дані, куди і за якою політикою синхронізуються? |
| Projection/Indexing | Які представлення та індекси можна перебудувати? |

Фізичне сховище не визначає автоматично права або авторитетність вузла.

## 5. Логічна модель ресурсу

Ресурс має стабільну ідентичність, незалежну від формату зберігання:

```text
ResourceId
SchemaId + SchemaVersion
OwnerSpaceId
AppInstanceId
ContainerId
Content
Relations
Attachments
Version/History
Access Policy
Synchronization Policy
```

Завдання, нотатка, документ, повідомлення, канал, тема форуму, адреса, новина або запис каталогу є різними схемами ресурсів, але використовують спільні механізми ідентифікації, прав, змін і синхронізації.

## 6. Простори та контейнери

### 6.1 Space

`Space` є основною межею володіння, членства, ключів, політик і конфігурації.

Підтримувані види просторів:

- персональний;
- організаційний;
- проєктний;
- командний;
- спільнота;
- міський;
- бізнес-простір;
- системний.

Користувач має персональний Space і може бути учасником кількох інших просторів.

### 6.2 Контейнери всередині Space

Space може містити:

- проєкти й робочі області;
- групи та спільноти;
- канали;
- форуми, категорії й теми;
- колекції та каталоги;
- приватні області;
- екземпляри застосунків.

Контейнер успадковує політики Space і може мати власні уточнення.

### 6.3 Володіння й повторне використання

- Кожен ресурс має один `OwnerSpaceId`.
- Ресурс можна підключати до інших просторів через link, mount, projection, overlay або data contract.
- Повторне використання не повинно дублювати master data.
- Доступ до пов'язаного ресурсу перевіряється окремо.

## 7. Модель застосунку

Пакет застосунку визначає:

- схеми та зв'язки;
- команди й запити;
- workflow;
- декларації прав;
- UI;
- Data Ports — семантичні вимоги до даних.

Пакет не містить жорсткої залежності від PostgreSQL, Markdown або конкретної файлової структури.

Необхідно розділяти:

- `AppPackage` — версійований пакет;
- `AppInstallation` — встановлення пакета;
- `AppInstance` — конкретний екземпляр у Space;
- `DataBinding` — прив'язка Data Port до логічного набору даних;
- `EnvironmentBinding` — прив'язка до конкретного фізичного provider у середовищі.

## 8. Багаторівнева модель прав

Політика може діяти на рівнях:

```text
Platform
  → Space
    → AppInstance
      → Container/Channel
        → Dataset/Collection
          → ResourceType
            → Resource
              → Field
                → Action
```

### 8.1 Суб'єкти

- користувач;
- власник;
- автор запису;
- роль;
- група;
- член або гість Space;
- модератор;
- застосунок;
- бот;
- сервісний акаунт;
- анонімний або публічний користувач.

### 8.2 Умови

Політика може враховувати:

- роль, групу та членство;
- власника й автора;
- Space, організацію, проєкт або канал;
- статус і стадію;
- тип ресурсу;
- значення полів;
- зв'язки;
- стан workflow;
- пристрій, мережу й offline-режим;
- час;
- рівень автентифікації;
- класифікацію даних.

Підтримуються `AND`, `OR`, `NOT`, `Allow` та `Deny`. Явний hard deny має перевагу.

### 8.3 Дії

- read/create/update/delete;
- comment/link/share;
- approve/publish/moderate;
- export/search/sync;
- execute command;
- read/write конкретного поля.

### 8.4 UI capability model

UI отримує розрахований `CapabilitySet`:

- hidden;
- disabled;
- readOnly;
- masked;
- required;
- allowedValues;
- rowFilter;
- fieldFilter;
- confirmationRequired;
- strongAuthenticationRequired.

Ідентифікатори UI-повноважень можуть мати вигляд `page.container.button` або семантичний namespace застосунку. Приховування UI не є захистом: команда завжди повторно перевіряється довіреним рушієм.

## 9. Offline-політика операцій

| Режим | Поведінка |
|---|---|
| `LocalAllowed` | Операція приймається локально й синхронізується |
| `DeferredValidation` | Зберігається як pending до перевірки authority-вузлом |
| `OnlineRequired` | Без з'єднання операція заборонена |
| `ReauthenticationRequired` | Потрібне повторне підтвердження особи |

Приклади:

- власник персонального Space редагує нотатку офлайн;
- редактор створює чернетку новини офлайн;
- публікація новини потребує серверного підтвердження;
- бан користувача потребує прав модератора;
- фінансова або адміністративна дія може бути `OnlineRequired`.

## 10. Семантика даних

CRDT не є універсальним механізмом для всіх ресурсів. Тип навантаження визначає модель змін:

| Semantic store | Приклади |
|---|---|
| `RecordLog` | задачі, довідники, звичайні записи |
| `CRDTDocument` | спільно редаговані документи |
| `AppendStream` | повідомлення та події |
| `StrictLedger` | права, платежі, голосування, критичні операції |
| `BlobObject` | файли й медіа |
| `DatasetRelease` | опубліковані набори даних |
| `EphemeralRoom` | тимчасова realtime-взаємодія |

Конкретний CRDT-рушій і формат бінарних envelope потребують прототипування та benchmark.

## 11. Storage profiles

| Профіль | Призначення |
|---|---|
| `NativeBinary` | Дефолтне компактне local-first сховище Vida |
| `FileWorkspace` | Markdown/JSON/YAML та вкладення відповідно до схем |
| `ServerDatabase` | SQL/NoSQL для серверних застосунків |
| `ObjectStorage` | Iroh Blobs, S3 або локальне blob-сховище |
| `ExternalProvider` | Зовнішня БД, API або master-data система |
| `Hybrid` | Комбінація writable store, реплік, індексів та експорту |

Markdown, SQL і binary є providers одного Data Contract, а не різними версіями застосунку.

## 12. Рівні вибору сховища

Storage policy має успадкування й може задаватися на рівнях:

1. дефолт Vida;
2. профіль вузла або середовища;
3. Space;
4. `AppInstance`;
5. контейнер, проєкт або канал;
6. `DataPort`, dataset або collection;
7. тип ресурсу;
8. клас вкладень;
9. у виняткових випадках — конкретний ресурс.

Більш конкретне правило перекриває загальне.

### 12.1 Приклад персонального Space

```yaml
space: personal
defaultStorage: NativeBinary

apps:
  wiki:
    documents: FileWorkspace/Markdown
    attachments: LocalFiles
    search: SQLiteFTS

  messenger:
    messages: NativeBinary/AppendStream
    media: IrohBlobs
```

### 12.2 Приклад серверного порталу

```yaml
space: ukrainian-portal
defaultStorage: ServerDatabase

datasets:
  news: PostgreSQL
  media: S3
  mobileReplica: NativeBinary
  publicSearch: SearchProjection
```

## 13. Logical policy та environment binding

### 13.1 Logical Storage Policy

Визначає:

- семантику даних;
- чи потрібен CRDT;
- чи дозволені локальні зміни;
- conflict policy;
- рівень реплікації;
- вимоги до пошуку;
- допустимі типи providers.

### 13.2 Environment Binding

Прив'язує логічну вимогу до конкретної реалізації:

- Markdown-каталог на десктопі;
- NativeBinary на телефоні;
- PostgreSQL на сервері;
- S3 для медіа;
- зовнішній API для довідника;
- SQLite/FTS або інший рушій локального пошуку.

Це дає можливість переносити застосунок між середовищами без зміни його коду.

## 14. Ролі storage provider

Один dataset може мати кілька providers із різними ролями:

| Роль | Значення |
|---|---|
| `WritableStore` | Приймає зміни |
| `Replica` | Зберігає синхронізовану копію |
| `Projection` | Оптимізоване представлення |
| `SearchIndex` | Пошуковий індекс |
| `Export` | Людиночитний або переносний експорт |
| `Archive` | Історичне зберігання |
| `BlobStore` | Вкладення та великі об'єкти |
| `ExternalMaster` | Зовнішній керований набір даних |

## 15. Життєвий цикл зміни

1. Користувач, бот або застосунок створює `ChangeRequest`.
2. Vida перевіряє членство, ролі, групи, політики, стан ресурсу та контекст.
3. Доменна логіка перевіряє допустимість команди й переходу стану.
4. Зміна нормалізується у стандартну підписану операцію.
5. Authority policy визначає: прийняти локально, відкласти чи передати для підтвердження.
6. Storage adapter записує зміну у NativeBinary, файли або БД.
7. Iroh синхронізує операцію, схему, manifest і потрібні blobs.
8. Репліки, проєкції, файли й індекси оновлюються відповідно до bindings.

Права визначають, чи дозволена зміна. Storage binding визначає, як і де її зберігати.

## 16. Authority nodes

Authority визначається політикою, а не типом БД:

- персональний Space — пристрої власника;
- проєктний Space — уповноважені вузли проєкту;
- організація — організаційний вузол або набір authority-вузлів;
- канал/спільнота — власник і модератори відповідно до операції;
- SaaS — серверний runtime;
- зовнішній master data — відповідний зовнішній provider.

## 17. Iroh у цільовій архітектурі

### Прийнято

- Iroh як основа P2P-з'єднань, discovery, NAT traversal, relay fallback та шифрованого транспорту;
- спільний `VidaNodeHost`, який володіє Endpoint/Router і протоколами;
- синхронізація операцій, схем, manifests, objects та attachments;
- blobs для передавання content-addressed об'єктів;
- відокремлення durable sync від realtime-повідомлень.

### Iroh не визначає

- модель прав;
- членство й модерацію;
- схеми Vida;
- workflow;
- допустимі переходи станів;
- storage binding;
- пошук та індексацію.

### Для прототипування

- точний склад офіційних компонентів Iroh;
- стабільність API та FFI;
- власні ALPN-протоколи;
- node profiles для Full/Mobile/Browser/Edge/Keeper;
- робота на ресурсно обмежених пристроях.

## 18. Замінені та відхилені припущення

| Рішення | Статус | Причина |
|---|---|---|
| Проєкт називається PersonalVida | Замінено | Правильна назва — Vida |
| PostgreSQL є єдиною головною БД усієї платформи | Відхилено | Не відповідає portable/local-first моделі |
| Один storage profile для всього Space або застосунку | Відхилено | Binding потрібен також для container/dataset/type та середовища |
| CRDT для кожного виду даних | Відхилено | Потрібні workload-specific semantic stores |
| Markdown лише як одноразовий експорт | Замінено | Може бути повноцінним FileWorkspace provider |
| Iroh сам визначає права, конфлікти й модель даних | Відхилено | Це відповідальність Vida |

## 19. Відкриті питання

1. Як обробляти зовнішнє редагування Markdown: автоматичний імпорт, proposed change чи заборона?
2. Який формат використати для канонічних binary envelopes і operation packs?
3. Який CRDT-рушій вибрати після benchmark?
4. Які storage bindings можуть мати кілька одночасних writable replicas?
5. Які операції потребують одного authority-вузла, кворуму або підписів кількох сторін?
6. Як версіонувати та мігрувати FileWorkspace і SQL-проєкції при зміні SchemaVersion?
7. Які можливості повинен мати перший `VidaNodeHost` прототип?

## 20. Найближчі прототипи

1. Один Data Contract для `Task` або `Document`.
2. Два providers: NativeBinary і Markdown FileWorkspace.
3. Одна SQL-проєкція або server binding.
4. Синхронізація операцій та вкладень через Iroh.
5. Перевірка однакових ResourceId і SchemaVersion у всіх представленнях.
6. Політика доступу за owner/group/status/stage з server/local recheck.
7. Конфліктне редагування одного ресурсу з телефона, Markdown і серверного UI.
