Я б будував систему не як три окремі продукти — TickTick, Notion і менеджер проєктів, — а як єдину local-first платформу сутностей, документів, зв’язків і подій.

Канонічними даними були б:

незмінні підписані операції;
періодичні знімки стану;
контент-адресовані вкладення;
маніфести, які пов’язують усе в одну версіоновану структуру.

Усе це зберігається звичайними файлами. SQLite використовується лише як швидкий локальний індекс, який можна видалити й повністю перебудувати. Iroh забезпечує P2P-з’єднання, доставлення об’єктів і live-сповіщення, але не є моделлю даних, системою прав або сервером зберігання. Сам Iroh позиціонується як модульний мережевий стек: Endpoint відповідає за ідентичність вузла, NAT traversal і relays, Router — за маршрутизацію протоколів через ALPN, а blobs/docs/gossip — за прикладні протоколи.

Ітерація 1. Єдина предметна модель
1.1. Не дублювати задачі, сторінки та проєкти

Базовою одиницею має бути не «задача TickTick» або «сторінка Notion», а універсальна Entity.

Entity
 ├─ id
 ├─ schemaId
 ├─ properties
 ├─ contentDocumentId
 ├─ relations
 ├─ parentId
 ├─ lifecycle
 ├─ permissionsScope
 └─ audit metadata

Різницю між задачею, нотаткою, проєктом і клієнтом визначає схема.

Функціональний об’єкт	Реалізація
Задача	Entity зі схемою Task
Нотатка	Entity зі схемою Note і block-документом
Сторінка Notion	Entity + BlockDocument
Проєкт	Entity зі схемою Project, цілями, етапами та зв’язками
Епік	Entity зі схемою Epic
Віха	Entity зі схемою Milestone
База Notion	Schema + набір сутностей + збережені Views
Папка або простір	Scope/Space + відношення parent
Коментар	Незмінна подія, прив’язана до Entity
Вкладення	BlobManifest, що посилається на контент-адресовані chunks
Канбан	View над сутностями, згрупованими за властивістю
Календар	View над властивостями дат
Gantt	View над датами та залежностями
Smart List TickTick	Збережений запит
Звичка	TaskTemplate + RecurrenceRule + OccurrenceLog
Нагадування	ReminderRule, а не окрема копія задачі

Отже, одна задача може одночасно:

з’являтися у «Сьогодні»;
бути рядком у таблиці;
бути карткою Kanban;
входити у проєкт;
відображатися у Gantt;
мати власну сторінку документації.

Це будуть різні представлення однієї сутності, а не п’ять синхронізованих копій.

1.2. Сторінка та задача можуть бути одним об’єктом

У Notion сторінка часто одночасно є записом у базі. Це варто зберегти:

Task Entity
 ├─ properties
 │   ├─ status
 │   ├─ priority
 │   ├─ assignees
 │   ├─ dueDate
 │   ├─ estimate
 │   └─ projectRelation
 └─ contentDocument
     ├─ description
     ├─ checklist
     ├─ images
     ├─ decisions
     └─ embedded views

Тому не потрібно окремо зберігати «коротку задачу» і «сторінку задачі».

1.3. View не володіє даними

View зберігає тільки:

ViewDefinition
 ├─ source schema/query
 ├─ filter
 ├─ sort
 ├─ group
 ├─ columns
 ├─ presentation: table/board/calendar/gantt/list
 ├─ manual ordering
 └─ local/shared settings

Усі фактичні дані залишаються в Entity.

Ітерація 2. Чому не можна просто синхронізувати Markdown і JSON

Наївний варіант:

tasks/task-1.json
pages/project-a.md
projects/project-a.json

і передавати змінені файли через Iroh.

Це працюватиме лише для одного користувача з послідовними змінами. Щойно два пристрої змінять файл паралельно, виникнуть проблеми:

конфлікт цілого файлу через зміну одного поля;
втрата однієї з версій;
проблеми з перейменуванням;
неоднозначність між видаленням і переміщенням;
пошкодження після аварійного завершення запису;
неможливість частково синхронізувати великий workspace;
складна історія змін;
неможливість правильно відкликати права;
мільйони дрібних файлів;
постійне перехешування великих документів.
Правильний поділ
Канонічний рівень

Машинний, незмінний, придатний для синхронізації:

operation packs;
snapshots;
manifests;
attachment chunks;
membership records;
key envelopes.
Людиночитаний рівень

Відновлювана проєкція:

Markdown;
JSON;
YAML frontmatter;
звичайна структура папок;
експорт вкладень під початковими іменами.
Канонічні об’єкти → Materializer → Markdown/JSON/SQLite
                                     ↑
                              File watcher/importer
                                     │
                         зовнішня зміна → нова операція

Користувач може редагувати Markdown зовнішнім редактором, але watcher не «перезаписує істину». Він:

читає попередній projection hash;
обчислює структурну різницю;
створює доменні операції;
застосовує їх через той самий merge engine;
оновлює проєкцію.

Таким чином, зовнішнє редагування залишається підтримуваним, але raw-файли не стають джерелом файлових конфліктів.

3.4. Формати

Я б використав:

Дані	Формат
Підписувані envelope і manifests	Deterministic CBOR
Локальний IPC .NET ↔ Rust	Protobuf/gRPC
Пакети операцій	CBOR + Zstandard
Хешування	BLAKE3
Людиночитані проєкції	Markdown + YAML frontmatter
Read model	SQLite + FTS5
Вкладення	Зашифровані chunks + manifest

Deterministic encoding потрібний, щоб однаковий логічний об’єкт мав однакове байтове представлення перед підписанням.

3.5. Атомарність запису

Незмінний об’єкт записується так:

створити файл у temp;
записати повністю;
fsync;
перевірити hash;
atomic rename до objects/<hash>;
оновити ref окремою атомарною операцією.

Існуючі об’єкти ніколи не перезаписуються. Змінюються тільки маленькі refs. Це значно спрощує crash recovery.

3.6. Не створювати файл на кожну дрібну операцію

Для маленьких операцій потрібні packs:

actor A, seq 1200–1350
       ↓
operation-pack-<hash>.cbor.zst

Окремі великі документи та вкладення залишаються окремими blobs.

Початкові пороги можна встановити так:

pack приблизно 1–4 MiB;
snapshot після певної кількості операцій або розміру oplog;
великі вкладення — chunking;
маленькі вкладення — один blob.

Ці числа мають визначатися benchmark-тестами, а не бути частиною wire-протоколу.

Ітерація 4. Як саме використовується Iroh
4.1. Ролі компонентів
Компонент Iroh	Використання у системі
iroh::Endpoint	Мережевий вузол пристрою, direct connection, relay fallback
Router	Розподіл підключень між прикладними ALPN-протоколами
Власний sync-протокол	Авторизація, manifests, version vectors, selective sync
iroh-blobs	Передавання незмінних packs, snapshots і вкладень
iroh-gossip	Сповіщення про новий scope head, presence, cursor awareness
iroh-docs	Прототип або trusted-device режим, але не основна team-база

Iroh blobs використовує BLAKE3 content addressing, перевіряє частини потоку під час передавання та підтримує range/resumable transfer. Це добре відповідає нашим незмінним packs і вкладенням.

Gossip варто застосовувати тільки як «з’явилася нова версія», а не як гарантований event bus. Сам протокол орієнтований на поширення повідомлень між учасниками topic із eventual delivery, а scoped topics рекомендовані для окремих просторів або документів.

4.2. Чому я не ставив би iroh-docs у центр production-моделі

iroh-docs уже пропонує:

key-value entries;
BLAKE3-посилання на вміст;
авторські підписи;
range-based set reconciliation;
blobs для фактичного вмісту;
gossip для live-сповіщень;
persistent redb storage.

Але для нашої системи є обмеження:

право запису визначається possession of NamespaceSecret;
holders цього секрету можуть вставляти записи;
team ACL, відкликання конкретного користувача та scope permissions залишаються нашою відповідальністю;
rich text, task semantics і project constraints все одно потребують прикладного CRDT;
persistent store iroh-docs — один redb-файл, а не наша переносна канонічна структура;
selective sync і шифрування за просторами доведеться будувати окремо.

Документація прямо описує NamespaceSecret як write capability: той, хто володіє ключем, може вставляти нові entries. DocTicket при цьому може містити public або private capability.

Тому:

для особистого MVP між довіреними пристроями iroh-docs допустимий;
для командного production я б використовував власний підписаний oplog і custom sync protocol;
iroh-docs можна залишити як експериментальний reconciliation adapter.
4.3. Поточний технологічний ризик

Станом на 27 серпня 2026 року core API Iroh має стабілізовану 1.x поверхню, але iroh-docs, iroh-blobs і iroh-gossip не входять до стабілізованих high-level FFI bindings. iroh-docs зараз документується як 0.101.0, а документація latest iroh-blobs містить попередження про production quality. Тому їх потрібно ізолювати за власними інтерфейсами, pin-ити сумісний набір версій і не зберігати доменний формат у типах конкретної бібліотеки.

Ітерація 5. Власний sync-протокол
5.1. ALPN

Окремо Router реєструє ALPN для blobs і gossip. Iroh Router маршрутизує підключення за ALPN і дозволяє кільком протоколам використовувати один Endpoint.

5.4. Синхронізація по кроках
Крок 1. Authentication

Iroh уже автентифікує Endpoint на рівні з’єднання, але EndpointId — це мережевий пристрій, а не користувач системи. Тому поверх Iroh потрібний прикладний challenge-response:

device certificate;
user identity;
workspace membership;
role;
дозволені scopes;
key epoch.
Крок 2. Control scope

Спочатку синхронізуються:

membership;
device grants;
revocations;
encryption key epochs;
schema definitions;
active scope list.

Лише після цього можна довіряти operation packs.

Крок 3. Version reconciliation

Для кожного scope peers обмінюються:

snapshot hash;
actor heads;
version vector;
Merkle root operation index;
tombstone watermark.

Для невеликих workspace достатньо:

Actor A → seq 1950
Actor B → seq 885
Actor C → seq 142

Peer, у якого Actor B має тільки 820, просить range 821–885.

Для великих workspace actor-range index мерклізується, щоб не передавати весь список.

Крок 4. Передавання

Через iroh-blobs передаються:

manifests;
operation packs;
актуальні snapshots;
за потреби block documents;
вкладення — lazy.
Крок 5. Перевірка

Отриманий об’єкт спочатку потрапляє в quarantine:

перевіряється BLAKE3;
розшифровується;
перевіряється AEAD tag;
перевіряється signature;
перевіряється device certificate;
перевіряється scope membership;
перевіряється key epoch;
перевіряється sequence;
перевіряються quota і schema version.

Тільки потім об’єкт переходить у canonical store.

Крок 6. Materialization

Після прийняття операцій:

оновлюється CRDT;
створюється новий entity state;
оновлюється SQLite read model;
оновлюється FTS;
перераховуються залежні views;
надсилається подія UI;
формується AckCheckpoint.
Крок 7. Anti-entropy

Gossip надсилає лише коротке повідомлення:

scopeId + newHeadDigest + deviceId

Peer запускає звичайний reconciliation. Якщо gossip-повідомлення загубилося, періодичний anti-entropy sync усе одно знайде відмінності.

Ітерація 6. CRDT і конфлікти
6.1. Один CRDT на весь workspace — помилка

Не слід робити один величезний Automerge/Loro document на всі задачі й сторінки. Це призведе до:

надмірного causal history;
великої пам’яті;
синхронізації непотрібних даних;
неможливості ізолювати права;
складного compaction;
конфліктів між незалежними модулями.

Правильна гранулярність:

Дані	Гранулярність
Workspace configuration	Один control scope
Схеми та shared views	Один або кілька catalog scopes
Метадані задач проєкту	Project scope
Велика сторінка	Окремий document scope
Коментарі	Append-only stream на entity
Вкладення	Окремі immutable blobs
Приватний простір	Окремий encrypted scope
6.2. Вибір CRDT engine

Для Notion-подібних блоків потрібні:

rich text;
movable tree;
movable list;
stable cursors;
version vectors;
history;
offline merge.

Архітектурно CRDT engine має бути змінним adapter. Як початковий вибір я б взяв Loro для block document і ручного порядку, оскільки він має rich text, movable tree, fractional ordering і version vectors.

Automerge залишається сильним альтернативним варіантом: він network-agnostic, має власний sync protocol і офіційний приклад інтеграції з Iroh.

Важливо не зберігати «файл Loro» як єдину платформну істину. Зберігаються:

наш signed envelope;
CRDT update payload;

Фізичне видалення одразу неприпустиме.

  entityId
  deletedBy
  deletedAt
  causalContext
}

Фізичний GC можливий лише після:

створення snapshot;
підтвердження активними replicas;
відсутності refs з history/undo;
відсутності legal hold;
завершення key rotation.
6.6. Центр конфліктів

Ітерація 7. Recurrence, нагадування і звички
7.1. Не створювати наперед тисячі повторюваних задач

Зберігається правило:

RecurrenceRule
 ├─ DTSTART
 ├─ RRULE
 ├─ timezone
 ├─ completionPolicy
 ├─ reschedulePolicy
 └─ exceptions

Occurrence ID визначається детерміновано:

hash(taskId + scheduledInstant + recurrenceVersion)

Завершення зберігається як:

CompleteOccurrence(taskId, occurrenceId)

Тому два пристрої, які завершили ту саму occurrence, не створять два різні завершення.

7.2. Нагадування

Синхронізується тільки правило нагадування. Локальний scheduler кожного пристрою створює platform notification.

ReminderRule → DerivedOccurrence → OS Scheduler

Сам факт показу локального notification не потрібно глобально синхронізувати. А от snooze або dismiss, якщо вони мають бути спільними між пристроями, — це окремі події з occurrence ID.

7.3. Автоматизації

Для automation run потрібний idempotency key:

automationId + triggerEventId + ruleVersion

Якщо автоматизація повинна виконатися рівно один раз, її виконує:

authority node;
або keeper із lease;
або сервер інтеграцій.

Звичайний gossip не дає exactly-once гарантій.

Не слід мати один workspace key на всі дані.

Кожен scope має key epoch:

  epoch 7 → old members
  epoch 8 → після revocation

Нові операції шифруються ключем epoch 8. Старий учасник не може читати нові дані.

8.6. Межі revocation

Відкликання права не може стерти дані, які користувач уже завантажив. Воно може:

заборонити нові valid operations;
припинити видачу нових object hashes;
змінити scope key;
не допустити читання майбутніх даних.

Це фундаментальне обмеження будь-якої offline-first системи.

8.7. Iroh encryption недостатньо для keeper storage

Iroh шифрує трафік end-to-end, і relay не може читати вміст. Але relay бачить connection metadata, а keeper після отримання даних матиме bytes на диску. Тому application-level encryption at rest залишається необхідним. Офіційна документація також зазначає, що relays можуть бачити IP-адреси, час і обсяг переданого через них трафіку.

8.8. Invitations

Не варто використовувати довгоживучий DocTicket як запрошення до workspace. Tickets:

reusable;
можуть містити IP-адреси;
можуть містити write capability;
можуть застарівати;
не є автоматично одноразовими.

Наш invite token має містити:

Invite
 ├─ workspaceId
 ├─ inviterEndpointHint
 ├─ inviteNonce
 ├─ requestedRole
 ├─ allowedScopes
 ├─ expiresAt
 ├─ oneTimeClaimId
 └─ inviterSignature

Після claim відбувається handshake, створюється Grant і окремі KeyEnvelopes.

Ітерація 10. Keeper, relay та coordination service

Ітерація 13. Приклад повного сценарію
Завершення повторюваної задачі на телефоні без інтернету
Користувач натискає «Виконано».
Застосунок обчислює occurrenceId.
Створюється:
CompleteOccurrence {
  taskId
  occurrenceId
  completedAt
  actorId
}
Операція отримує локальний sequence і causal context.
Payload шифрується.
Envelope підписується device key.
Об’єкт записується атомарно.
CRDT/read model оновлюються одразу.
UI показує completed без очікування мережі.
Після появи мережі телефон під’єднується до keeper.
Peers обмінюються scope heads.
Keeper запитує відсутній operation pack.
Перевіряє підпис і membership.
Зберігає encrypted object.
ПК пізніше отримує цей pack.
ПК бачить ту саму occurrence як completed.
Якщо ПК також завершив її offline, idempotent occurrence ID не створює дубль.

 ├─ state

 ├─ schemaVersion
 ├─ crdtAdapterVersion

15.2. Compaction

Операції не видаляються тільки тому, що з’явився snapshot.

Compaction дозволений, коли:

snapshot перевірено;
keeper має копію;
активні replicas підтвердили достатню версію;
закінчився history retention;
tombstones безпечні для видалення;
немає pending device recovery.

Старий пристрій після довгої відсутності отримує snapshot + tail, а не всю історію.

15.3. Garbage collection

Mark-and-sweep roots:

current manifests
pinned versions
active snapshots
undo window
unsynced local operations
peer recovery checkpoints
legal retention
exports in progress

Усе недосяжне спочатку переміщується в trash, і лише після grace period фізично видаляється.

перевірити signatures;
перевірити manifests;
знайти missing objects;
запросити repair у keeper або peer;
перевірити rebuild SQLite.

1.1. Єдина модель Entity + Schema + View

Свіжі проєкти не дають підстав змінювати цю модель.

Вибір між ними має завершитися benchmark-тестами, а не новим архітектурним припущенням.

        ↓

        ├─ LocalPackStore
        ├─ IrohBlobsProvider
        ├─ KeeperProvider
        ├─ S3Provider
        └─ DistributedClusterProvider

Тобто:

канонічна структура файлів — наша;
спосіб фізичного збереження і передавання — змінний provider.
3.3. Три площини object storage

З dstore варто перенести сам принцип поділу:

Площина	Що містить
Data plane	Незмінні chunks, nodes, packs
Catalog plane	Refs, placement view, leases, replication policy
Maintenance plane	Repair, scrub, rebalance, GC

dstore реалізує weighted rendezvous hashing, CASPaxos catalog, rebalancing і cluster-wide mark-and-sweep. Це сильний архітектурний референс. Водночас сам проєкт називає себе першою реалізацією і ще має незавершені recovery, gateway та access-control частини, тому робити його production-залежністю зараз не слід.

Важливе обмеження

CASPaxos із dstore доречний для:

cluster view;
placement;
mutable refs;
leases;
GC coordination.

Але не для задач, сторінок, статусів і коментарів. Домен PersonalVida залишається CRDT/oplog-based.

6. Relay architecture треба оновити

Попереднє рішення «два dedicated relays» правильне, але надто статичне.

Тепер потрібний компонент:

RelayManager
 ├─ relay profiles
 ├─ startup health checks
 ├─ authenticated relay credentials
 ├─ regional preference
 ├─ direct/relayed telemetry
 ├─ outage diagnostics
 └─ failover observation

flexaccess-iroh показує практичні патерни:

startup relay probe;
виключення недоступного relay перед bind;
home-relay failover;
повернення relay після відновлення;
endpoint-bound authentication transcript.

Водночас не слід дублювати те, що вже робить Iroh. Поточна офіційна документація зазначає, що Iroh clients автоматично перемикаються між relays, а для production рекомендуються dedicated або authenticated shared relays і щонайменше два регіони.

Тому наше рішення:

Iroh відповідає за path selection і network failover;
RelayManager відповідає за конфігурацію, health, метрики, tenant policy і діагностику;
власну реалізацію failover додаємо лише там, де integration tests виявлять реальну проблему.
7. Шифрування треба зробити дворівневим

Попередня модель:

Workspace
 └─ scopes
     └─ key epochs

залишається правильною.

Але diaswarm показує додатковий корисний pattern: immutable segments, окремий content key на segment і key wrapping для кожного reader. Blind peer може зберігати та роздавати ciphertext, не маючи можливості його відкрити; відкликання діє лише на майбутні segments, а вже завантажені дані відкликати неможливо. Сам проєкт прямо попереджає, що його криптографія не проходила review, тому переносити реалізацію не можна.

7.1. Нормальні workspace-дані
ScopeKey epoch N

Підходить для:

проєктів;
задач;
сторінок;
shared spaces;
package data.
7.2. Чутливі append-only streams
Segment
 ├─ segmentKey
 ├─ encrypted records
 └─ recipient KeyEnvelopes

Підходить для:

зовнішнього sharing;
audit logs;
медичних або фінансових даних;
приватних повідомлень;
історії agent execution;
тимчасових external participants.
7.3. Явно зафіксовані обмеження

Модель безпеки повинна прямо говорити:

revocation не видаляє вже отримані дані;
keeper бачить розміри, частоту та час передач;
relay може бачити network metadata;
неможливо довести, що peer видалив локальну копію;
read operations на локальній копії можуть бути невидимими;
ticket або EndpointAddr є адресою, а не автоматичним правом доступу.
8. AgentLink змінює агентний контур, але не storage core

Тепер знайдений точний проєкт — 704986409/AgentLink. Він використовує:

Avalonia desktop UI;
Rust Iroh bridge;
persistent Endpoint key;
local MCP service;
local agent registry;
explicit node trust;
explicit agent sharing;
directory synchronization;
message IDs;
routing receipts;
stable identity на основі node + agent instance.

Це підтверджує, що в VIDA потрібно додати окремий Agent Directory і Durable Agent Mailbox.

8.1. Модель агента
AgentInstance
 ├─ agentId
 ├─ ownerDeviceId
 ├─ provider
 ├─ role
 ├─ capabilities
 ├─ availability
 ├─ sharingPolicy
 └─ runtimeEndpoint

Ідентифікатор:

deviceId / stableAgentInstanceId

Назва Codex, Claude або Developer Agent не може бути primary key.

8.2. Повідомлення агента
AgentMessage
 ├─ messageId
 ├─ conversationId
 ├─ fromAgentId
 ├─ toAgentId
 ├─ replyTo
 ├─ payloadRef
 ├─ expiresAt
 ├─ requestedCapabilities
 └─ signature

Стани:

Created
→ AcceptedByRemoteNode
→ StoredInMailbox
→ ClaimedByAgent
→ Running
→ ResultProduced
→ Acknowledged
8.3. MCP не повинен бути wire-протоколом між вузлами

Правильний поділ:

Codex / Claude / інший Agent
          ↓ local MCP
      Vida Agent Service
          ↓ vida-agent/1
      Remote Vida Node
          ↓ local MCP/runtime adapter
      Remote Agent

MCP — локальний integration adapter. Мережевий протокол VIDA має залишатися власним, versioned і transport-neutral.

8.4. Що не переносимо з AgentLink
не переходимо автоматично на Avalonia лише через цей проєкт;
не використовуємо newline JSON через stdin/stdout як production IPC для data core;
не дозволяємо remote message автоматично виконувати команди;
network delivery не прирівнюємо до виконання задачі.

AgentLink добре підтверджує sidecar pattern, але в VIDA локальна межа має бути typed:

gRPC over UDS / Named Pipes
або
native FFI на mobile
9. WASM business rules треба зробити більш формальними

arena0 використовує content-addressed deterministic WASM programs, capability-oriented sandbox, typed effects і signed replayable receipts. Але проєкт позначений як very alpha, а його P2P networking ще перебуває в роботі.

З нього варто взяти архітектурний pattern, а не runtime.

9.1. Нова модель автоматизації
AutomationPackage
 ├─ wasmContentId
 ├─ interfaceSchema
 ├─ stateSchema
 ├─ capabilityManifest
 ├─ determinismProfile
 ├─ packageSignature
 └─ version
9.2. Розділення pure logic та effects
Input Event
    ↓
Deterministic WASM State Machine
    ↓
Requested Effects
    ↓
Capability/Permission Check
    ↓
Effect Executor
    ↓
Signed Execution Receipt

WASM-модуль не повинен напряму:

звертатися в інтернет;
читати весь workspace;
запускати process;
писати файли;
надсилати повідомлення;
змінювати права.

Він лише повертає typed effect requests.

9.3. Execution receipt
ExecutionReceipt
 ├─ automationId
 ├─ wasmHash
 ├─ inputHash
 ├─ previousStateHash
 ├─ outputHash
 ├─ requestedEffects
 ├─ acceptedEffects
 ├─ executor
 ├─ timestamp
 └─ signature

Це дозволить:

replay;
audit;
deterministic tests;
порівняння виконання на різних вузлах;
marketplace verification;
agent evals.

N-of-N agreement із arena0 потрібне лише для спеціальних міжорганізаційних контрактів, voting або shared approvals. Для звичайних задач і workflow це зайва складність.

10. Iroh не замінює orchestration та provisioning

ingot_cluster поєднує Iroh і Zenoh, але прямо зазначає: ці transport overlays можуть знаходити та з’єднувати вже запущені вузли, проте не запускають і не provision-ять їх.

Тому попередня серверна архітектура зберігається:

Iroh
 └─ device/peer connectivity та data transfer

Aspire
 └─ local development topology

Dapr
 └─ backend service invocation, workflows, pub/sub, secrets

Kubernetes / containers / systemd
 └─ deployment та process lifecycle

Zenoh зараз додавати в core не потрібно. Його можна пізніше розглянути як optional adapter для:

industrial edge;
high-frequency telemetry;
brokered LAN;
unreliable embedded networks.
