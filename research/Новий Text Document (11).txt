чи можна iroh розгорнути на esp32 типу m5stack papermono
Чи можно там реалізувати інтерфейс для нашої системи?
Продовжи
Висновок

Так, Iroh можна запустити на M5Stack PaperMono, і саме ця модель добре підходить для експерименту: ESP32-S3R8, 16 МБ Flash, 8 МБ Octal PSRAM, Wi‑Fi, microSD, сенсорний екран 480×800, NFC та LoRa. Офіційні характеристики PaperMono.

Команда Iroh уже має робочий приклад для ESP32-S3 з PSRAM. Він використовує опублікований iroh 1.0.2, підтримує прямі з’єднання, relay і pkarr-discovery. Прошивка прикладу займає близько 4,35 МБ і вимагає щонайменше 8 МБ Flash — PaperMono має достатній запас. Приклад Iroh для ESP32-S3 + PSRAM.

Але правильна роль PaperMono — не повний вузол усієї платформи, а автономний e‑ink клієнт/обмежена репліка.

Компонент	Реалістичність
Iroh Endpoint, QUIC, пряме з’єднання	Так
Iroh через relay та discovery	Так, завдяки 8 МБ PSRAM
Власний RPC-протокол поверх Iroh	Так
Динамічний UI зі схем	Так, з обмеженим набором компонентів
Локальний кеш та offline-outbox	Так, на microSD
Повний iroh-docs + blobs + gossip	Експериментально, поки не рекомендую
Повноцінний редактор рівня Notion	Ні
Звичайний .NET 10, MAUI або Blazor	Ні
Iroh безпосередньо через LoRa	Ні, Iroh потребує IP/UDP
Як інтегрувати PaperMono в нашу систему

Рекомендована архітектура:

Прошивка Rust + ESP-IDF

Iroh працює у Rust із std, FreeRTOS і Tokio. Головний застосунок краще робити саме на Rust.

M5Unified/M5GFX для обладнання

Екран, touch, живлення, microSD, NFC та LoRa підключаються через невеликий C/C++ wrapper до M5Unified/M5GFX. M5GFX підтримує ESP-IDF, а підтримку PaperMono додано у версії 0.2.22. M5GFX, реліз із PaperMono.

Окремий протокол device-ui/1 поверх Iroh

Він передає не всю базу, а:

UiBundle — схеми екранів;
ProjectionSnapshot і ProjectionDelta — дозволені дані;
Command — завершити задачу, змінити статус, створити нотатку;
Ack/Conflict — підтвердження або конфлікт;
SyncCursor — позицію останньої синхронізації.

Схожий практичний шаблон RPC для ESP32 уже показаний у iroh-smart-fan.

Повний вузол залишається на телефоні, ПК або домашньому хабі

Саме він тримає повний набір iroh-docs, iroh-blobs, iroh-gossip, файли, workflow, права та конфлікти. iroh-docs сам залежить від blobs і gossip, тому переносити весь цей стек на PaperMono без потреби недоцільно. Архітектура iroh-docs.

PaperMono зберігає тільки проєкцію

Наприклад:

сьогоднішні та найближчі задачі;
вибрані списки й дошки;
короткі нотатки;
картки об’єктів;
довідники, потрібні конкретному застосунку;
offline-outbox незасинхронізованих команд.
Динамічний інтерфейс

Можна зробити одну універсальну прошивку, яка інтерпретує схеми платформи. Для профілю epaper-small-v1 достатньо таких компонентів:

список, картка, вкладки-сторінки;
текст, число, дата, перемикач;
checkbox і checklist;
enum/select;
badge статусу;
коротке текстове поле;
кнопка дії;
QR-код;
спрощене відношення до іншого об’єкта.

Права слід застосовувати так:

основний вузол компілює повну схему в ефективну схему для конкретного пристрою й користувача;
невидимі поля та дії взагалі не передаються;
PaperMono локально виконує visible/readonly;
кожна команда повторно перевіряється повним вузлом;
для offline-режиму пристрій отримує обмежену capability: простір, типи об’єктів, дозволені дії та строк дії.

Тобто ESP32 не повинен самостійно виконувати весь глобальний рушій прав.

Особливості e‑ink

PaperMono має дуже пристойну швидкість для такого екрана:

якісне повне оновлення — близько 4,71 с;
текстове — 0,45 с;
швидке — 0,34 с;
найшвидше — 0,07 с.

Виробник рекомендує приблизно після десяти часткових оновлень робити повне очищення екрана. Режими оновлення PaperMono.

Тому UI має бути сторінковим:

без анімацій;
без плавного скролінгу;
з великими touch-зонами;
з оновленням лише зміненого рядка;
з періодичним повним refresh;
із вбудованим українським шрифтом із підмножиною кирилиці.
NFC, LoRa та живлення

NFC добре використовувати для:

первинного підключення пристрою;
вибору організації або простору;
відкриття картки об’єкта за NFC-міткою;
ідентифікації користувача;
check-in та підтвердження операцій.

LoRa не є транспортом для Iroh. Його варто використовувати окремо для малих підписаних повідомлень: сповіщення, аварійна подія, коротка команда, стан датчика. LoRa-шлюз уже перетворює таку подію на операцію системи.

Постійно тримати Iroh і Wi‑Fi активними на батареї небажано. ESP32-S3 не підтримує Wi‑Fi-з’єднання у light/deep sleep, тому оптимальний цикл такий:

пробудження → Iroh connect → відправлення outbox → отримання delta → оновлення екрана → sleep

Екран продовжить показувати інформацію без живлення. Для миттєвих постійних оновлень потрібне USB-живлення або окремий LoRa-механізм пробудження. Режими сну ESP32-S3.

Важливе застереження

ESP32 ще не вказаний у стандартній матриці підтримуваних платформ Iroh, а поточний приклад використовує спеціальний мінімальний crypto-provider і skip_verify() для TLS-перевірки relay-рівня. Це робочий proof of concept, але не готовий production-шаблон. Матриця платформ Iroh, код ESP32-прикладу.

Для production необхідні:

нормальна перевірка relay-сертифіката або certificate pinning;
Secure Boot v2;
Flash і NVS encryption;
стабільний Iroh-ключ у зашифрованому NVS;
підписані OTA-оновлення;
шифрування чутливого кешу на microSD;
повторна авторизація всіх команд на повному вузлі.

ESP-IDF прямо рекомендує для production одночасно використовувати Flash Encryption і Secure Boot v2. Рекомендації Espressif.

Отже, PaperMono варто брати як кишеньковий термінал нашої системи: задачі, checklist, короткі нотатки, картки, сповіщення, NFC-сценарії та прості бізнес-операції. Для повністю незалежного вузла з усіма документами, blobs, workflow і повнотекстовим пошуком краще залишити Linux-пристрій або телефон.

За потреби можна відстежувати, коли ESP32 стане офіційною платформою Iroh або з’явиться готовий приклад повного iroh-docs.
