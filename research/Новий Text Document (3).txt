Так. Те, що ядро застосунку написане на Rust, не означає, що всю бізнес-логіку й усі розширення також потрібно писати на Rust. Можна вбудувати середовище виконання плагінів і дозволити писати логіку окремо від ядра — на Rust, JavaScript/TypeScript або скриптовій мові. Для WebAssembly-компонентів уже існують відповідні інструменти, хоча можливості та зрілість підтримки відрізняються між мовами.

Для нашої платформи з Rust-ядром, Dioxus, переносними пакетами та синхронізацією iroh я рекомендую основний шлях: WebAssembly Component Model + WIT. На нативних платформах базовим кандидатом на виконання є Wasmtime. Для простих користувацьких правил можна додати Rhai, але як допоміжний механізм, а не другу незалежну систему застосунків.

А найбільш прямий варіант «взяти готовий плагінний фреймворк і вбудувати» — Extism. Він заслуговує на окреме порівняння, тому що зменшує початкову роботу, але має власний інтерфейс плагінів, який не тотожний WIT/Component Model.

Rust дозволяє взаємодіяти з нативними бібліотеками, але його власний ABI — двійковий інтерфейс викликів — не має гарантій стабільності. Для стабільнішої межі доводиться використовувати, наприклад, C ABI та спеціально проєктувати передавання даних.

Для нашого маркетплейсу це невдалий основний шлях: ми отримали б платформозалежні збірки та виконання стороннього нативного коду в процесі застосунку. Нативні модулі я залишив би для довірених частин самого продукту, які постачаються разом із клієнтом.

2. Як саме автори зможуть писати логіку

Я пропоную не змушувати автора застосунку починати з програмування. У нас мають бути три рівні.

Рівень 1. Декларативні правила — без коду

Це основа для нашого low-code:

Коли задачу переведено у стан «Завершено», перевірити обов’язкові поля, створити запис у журналі та запустити наступний крок процесу.

Автор налаштовує подію, умови та дії у конструкторі. У пакеті зберігається структурований опис правила, а ядро виконує його через заздалегідь визначені операції.

Сюди я відніс би перевірки полів, обчислювані значення, прості переходи станів і композицію стандартних дій.

Права доступу при цьому залишаються в нашому окремому конфігураторі прав. Дизайнер сторінки лише посилається на код дозволу на кшталт tasks.card.complete, а не містить власну копію перевірок користувача, групи та стану запису.

Рівень 2. Короткі скрипти — без збирання Rust-проєкту

Для цього підходить Rhai. Наприклад, формула пріоритету, якій ядро передає об’єкт task:

if task.urgent {
    3
} else {
    task.priority
}

Rhai дозволяє налаштувати обмеження кількості операцій, глибини викликів, розмірів рядків, масивів та інших структур. Це корисно для користувацьких правил, але обмеження потрібно явно налаштувати.

Моя пропозиція: спочатку дозволяти таким скриптам обчислювати результат, перевіряти дані або формувати запропоновані зміни. Не давати їм довільний доступ до файлової системи чи всього стану застосунку.

Результат скрипта ще має пройти перевірку ядра.

Рівень 3. Повноцінні плагіни — WebAssembly

Складніша логіка постачається як зібраний .wasm-компонент: імпортер документів, обробник повідомлень, інтеграційний конектор, алгоритм планування або власний крок бізнес-процесу.

На Rust автор пише звичайну бізнес-логіку та збирає компонент. Поточна документація рекомендує нативний шлях через cargo build --target wasm32-wasip2; окремий cargo-component уже не варто робити обов’язковою основою нового SDK.

На JavaScript/TypeScript також можна писати компоненти. У стандартному інструментарії для JavaScript використовуються componentize-js, jco та рушій StarlingMonkey. Це не означає, що TypeScript безпосередньо стає таким самим машинним кодом, як Rust: JavaScript виконується за участю вбудованого рушія.

Тому я б почав із Rust SDK для плагінів, а JavaScript/TypeScript SDK додав наступним. Користувач клієнта встановлює вже зібраний пакет — компілятор Rust йому не потрібен.

3. Як виглядатиме Wasm-плагін на практиці

Тут важливо розділити поняття:

Wasm — формат виконуваного коду.
WIT — опис контракту: які функції є, які аргументи вони отримують, що повертають.
WASI — стандартизовані системні інтерфейси, доступ до яких ми надаємо вибірково.

WIT сам по собі не містить бізнес-логіки: він описує взаємодію між компонентами.

Мінімальний приклад: нормалізація пріоритету задачі

Припустімо, у нашій моделі пріоритет — число від 0 до 3, а термінова задача повинна отримати 3.

У Rust library-проєкті створюємо файл wit/world.wit:

package vida:examples@0.1.0;

world task-rule {
    export normalize-priority: func(
        urgent: bool,
        current: u8
    ) -> result<u8, string>;
}

У src/lib.rs:

wit_bindgen::generate!({
    path: "wit",
    world: "task-rule",
});

struct TaskRule;

impl Guest for TaskRule {
    fn normalize_priority(
        urgent: bool,
        current: u8,
    ) -> Result<u8, String> {
        if current > 3 {
            return Err(
                "Пріоритет повинен бути в діапазоні 0–3".to_owned()
            );
        }

        Ok(if urgent { 3 } else { current })
    }
}

export!(TaskRule);

До Cargo.toml додаємо:

[lib]
crate-type = ["cdylib"]

Залежність і збирання:

cargo add wit-bindgen
rustup target add wasm32-wasip2

cargo build --release --target wasm32-wasip2

Тут cdylib разом із Wasm-ціллю дає Wasm-компонент, а не нативну DLL. Генерація обв’язки через wit-bindgen і таке збирання відповідають документованому шляху для Rust-компонентів.

Ядро завантажує компонент, викликає normalize-priority, отримує результат і вирішує, чи дозволено застосувати зміну. Для інтеграції на стороні Rust-хоста Wasmtime надає wasmtime::component::Component, linker і генерацію типізованих викликів.

Це приклад компонента, а не готового менеджера плагінів. Прив’язку до події task.before-save, активацію, дозволи, журналювання та оновлення ми додаємо у своїй платформній обв’язці.

4. Як вбудувати це саме в нашу архітектуру

Я пропоную таку межу відповідальності:

Dioxus: сторінки, форми, команди користувача
                     │
                     ▼
          API ядра / диспетчер команд
                     │
          перевірка прав і контексту
                     │
                     ▼
             Plugin Host
        ┌────────────┴────────────┐
        │                         │
  Wasm-компоненти          Прості правила
  через runtime           / опційно Rhai
        │                         │
        └────────────┬────────────┘
                     │
         результат / запит на зміни
                     │
                     ▼
        перевірка та запис операцій
                     │
              сховище → iroh

Плагін не повинен напряму переписувати наші файли. Інакше кожному розширенню доведеться знати внутрішній формат зберігання, правила узгодження та спосіб формування операцій синхронізації.

Натомість ми визначаємо невеликий стабільний API. Наприклад, такі назви — це пропозиція нашого майбутнього контракту, а не готовий SDK:

Група API	Що дозволяємо
records	Прочитати дозволені записи, виконати запит, запропонувати зміни
blobs	Прочитати конкретне вкладення або створити нове через контрольований інтерфейс
messaging	Надіслати повідомлення у дозволений канал або діалог

ui	Запросити відкриття форми, показ повідомлення або оновлення представлення
Важливо для наших динамічних схем

Не потрібно робити окремий базовий WIT-контракт для кожної користувацької сутності. Інакше додавання нового типу об’єкта почне вимагати змін у ядрі.

Я пропоную стабільні системні контракти, а дані динамічних об’єктів передавати з ідентифікатором схеми, її версією та погодженим форматом payload. Наш SDK може генерувати з цих схем зручні типізовані моделі для автора плагіна.

Тобто типізований приклад вище демонструє механізм, але не означає, що ядро має заздалегідь знати всі бізнес-об’єкти.

Межа безпеки

Для нас ефективний доступ плагіна я визначив би так:

Права користувача або службової ідентичності
∩ дозволи, надані плагіну
∩ політика workspace
∩ обмеження поточного виклику

Плагін не обирає довільно, від імені якого акаунта він працює. Контекст акаунта й workspace встановлює ядро. Дані та екземпляри виконання різних акаунтів потрібно ізолювати.

На рівні runtime Wasmtime має механізми переривання виконання за бюджетом обчислень або часом, а також налаштування обмежень пам’яті й інших ресурсів.

Окремо я заклав би ліміти розмірів запитів, відповідей, кількості операцій, логів і зовнішніх викликів. Обмеження інструкцій Wasm не замінює контроль вартості функцій ядра, які викликає плагін.

І ще принципово: плагін, якому дозволили прочитати приватний текст і відправити його в мережу, потенційно може цей текст розкрити. Тому для нашого месенджера доступ до вмісту розмов і зовнішніх інтеграцій має надаватися явно та окремо.

5. Як розширювати інтерфейс і пакувати застосунок

Я не прив’язував би переносний пакет до завантаження довільного нативного Dioxus-компонента.

Пропонована основа: плагін додає декларативний опис інтерфейсу, а Dioxus відображає його через наш renderer. Бізнес-обробники працюють окремо.

Наприклад, пакет може містити:

task-automation/
├── manifest.yaml
├── schemas/
│   └── task-extension.json
├── ui/
│   ├── task-card.json
│   └── actions.json
├── permissions/
├── workflows/
├── components/
│   └── business-logic.wasm
└── locales/

Це запропонована структура, не вимога Extism або Wasmtime.

Такий пакет може додати поле задачі, вкладку картки, команду «Створити підзадачі за шаблоном», форму налаштувань, обробник події та локалізації.

Кнопка в UI посилається на команду й код дозволу. Обробник отримує лише дозволені вхідні дані. Ядро перевіряє результат.

Для нестандартних віджетів згодом можна визначити окремий ізольований UI-контракт, але звичайні форми, списки та деталі не повинні вимагати власного рушія інтерфейсу в кожному плагіні.

Що має робити наш менеджер пакетів

Runtime виконує код, але для платформи потрібні ще перевірка сумісності API, підписів і залежностей, надання дозволів, міграції даних, активація версії та відкат після помилки.

Я пропоную зберігати версії пакетів незмінними. Під час оновлення нові виклики переходять на нову версію, а вже запущені операції завершуються за попередньою — або зупиняються за явно визначеним правилом.

Отримання пакета через iroh не повинно автоматично означати дозвіл виконати його код. Синхронізація, встановлення та активація — різні операції.

6. Бізнес-процеси й синхронізація: чого runtime не вирішить за нас

Для нашого local-first підходу я розділив би логіку на два класи.

Обчислення без зовнішніх ефектів: валідація, формули, перетворення даних, побудова представлення. Їх можна повторно виконувати на пристроях за погодженими вхідними даними та версією правила.

Дії із зовнішніми ефектами: надсилання повідомлення, створення нового запису, звернення до сервісу, запуск інтеграції. Для них потрібен визначений виконавець і захист від повторного виконання.

Наприклад, коли завершена задача синхронізувалася на телефон і ноутбук, обидва пристрої не повинні незалежно створювати одну й ту саму підзадачу.

Для таких сценаріїв я пропоную зберігати ідентифікатор події, ідентифікатор виконання, версію правила та ключ ідемпотентності — ознаку, за якою повторний запуск розпізнається як та сама дія.

Плагін як крок процесу, а не як процес, що живе вічно

Тривалий workflow не варто зберігати лише у пам’яті Wasm-екземпляра.

Подія → крок плагіна → запис результату
                         │
                         ▼
                    очікування
                         │
                         ▼
              наступний крок плагіна

Між кроками зберігаємо стан процесу, а не живий стек виконання. Після перезапуску клієнта процес продовжується з останнього підтвердженого стану.

І важливе для федеративної частини: результат плагіна на чужому клієнті не можна вважати доказом дозволеності операції. Перевірки доступу та критичних обмежень мають залишатися в довіреній логіці приймання операцій.

7. Android, iOS і браузер: один контракт, але не обов’язково один runtime

Саме тут потрібно перевіряти архітектуру раніше, ніж розширювати каталог плагінів.

Платформа	Запропонований шлях	Що потрібно підтвердити
Android	Wasmtime як кандидат для Rust-ядра	Збирання, запуск, споживання пам’яті та поведінку на реальних пристроях
iOS	Інтерпретований шлях, зокрема Wasmtime/Pulley, як кандидат	Технічну інтеграцію та окремо допустимість нашої моделі плагінів у магазині
Браузер	Компоненти через jco та браузерний WebAssembly	Доступність потрібних імпортів і відповідність наших адаптерів
Desktop / server	Wasmtime	Продуктивність, ізоляцію, життєвий цикл і ресурсні бюджети

Wasmtime прямо зазначає, що iOS та Android підтримуються, але тестуються менш широко, ніж основні desktop/server-платформи. Pulley є переносним інтерпретатором, проте має компроміс у швидкості порівняно з нативними компіляторами Wasmtime.

Для браузера jco перетворює компонент на придатну для JavaScript-середовища форму та дозволяє підставляти імпорти. Але браузерні можливості WASI обмежені платформою; частину інтерфейсів має реалізувати сам застосунок.

Отже, наша обіцянка має звучати так:

Один контракт плагіна та узгоджена поведінка на підтримуваних платформах, а не «будь-який .wasm автоматично працює всюди».

Окремий ризик — правила Apple

Правило 2.5.2 обмежує завантаження та виконання коду, який змінює функціональність застосунку. Водночас розділ 4.7 передбачає певні категорії мініапів, чатботів і плагінів, але встановлює додаткові умови, зокрема щодо доступу до нативних API та згоди користувача на передавання даних. Наявність Wasm-інтерпретатора сама по собі не гарантує схвалення нашої моделі маркетплейсу.

Це потрібно перевірити на конкретній продуктовій моделі, не відкладаючи до завершення розробки.

8. Що я остаточно рекомендую для нас

Основою зробити Component Model/WIT, а Wasmtime — першим нативним runtime-кандидатом. Це відповідає нашому напрямку переносних застосунків і не прив’язує мову бізнес-логіки до мови ядра.

Extism залишити альтернативою, а не обов’язковою залежністю. Він привабливий, коли важливіше швидко отримати просту систему виклику користувацьких модулів. Але для нас перехід на нього означатиме окреме рішення про контракт і SDK. До того ж готові нативні збірки та рекомендовані мобільні шляхи Extism не тотожні єдиній Rust-інтеграції на всіх платформах.

У першій версії не встановлювати всі скриптові рушії одразу. Почати з декларативних правил і Wasm-плагінів. Rhai додати тоді, коли з’явиться конкретна потреба редагувати короткі скрипти без циклу збирання.

Перший наскрізний прототип я побудував би навколо одного пакета: додаткове поле задачі → кнопка в Dioxus → Wasm-правило → перевірена зміна запису → синхронізація на інший клієнт без повторної побічної дії. Його варто перевірити на Android, iOS і в браузері до розширення SDK.

У підсумку: Rust залишається ядром, але не обмеженням для авторів застосунків. Прості сценарії вони налаштовують, складні — реалізують у плагінах, а доступ до даних, виконання команд і синхронізацію контролює наша платформа.

Порівняй функціональність Wasmtime та Rhai.
Чи можна на них написати всю логіку яка потрібна нашим додаткам, 

Так: і на Rhai, і у Wasm-плагінах під Wasmtime можна реалізувати всю прикладну бізнес-логіку наших типових застосунків — задач, нотаток, документообігу, керування проєктами, форумів і ботів. Але для цього ядро платформи має надати їм API роботи з даними, повідомленнями, інтерфейсом і фоновими завданнями. Самі середовища виконання цих сервісів не замінюють.

Важливе уточнення до попередньої відповіді: Rhai не обмежений короткими формулами. Він підтримує функції, модулі, власні обробники подій і стан між викликами — тобто на ньому можна побудувати цілий прикладний модуль.

Wasmtime має ширші можливості для незалежних складних розширень, але він не є мовою програмування. Логіку пишуть, наприклад, на Rust, компілюють у WebAssembly-компонент, а Wasmtime його виконує.

Для нашого вибору головне питання не «чи вистачить операторів мови», а скільки можливостей розширення зможе принести із собою, наскільки добре воно ізольоване та як працюватиме з асинхронними операціями.

3. Чотири відмінності, які найбільше впливають на наш вибір
3.1. Наскільки незалежним може бути розширення

Припустімо, автор застосунку хоче додати підтримку нового файлового формату.

З Wasmtime: він може використати сумісну бібліотеку, включити її у свій Wasm-компонент і постачати разом із плагіном. Якщо компоненту вистачає вже наявного API читання вкладень, ядро платформи змінювати не потрібно. Це випливає з моделі незалежно зібраних компонентів із явно визначеними імпортами.

З Rhai: автор може написати обробник на самому Rhai або використати доступні скриптові модулі. Але довільна Rust-бібліотека не стає доступною через import: її функції потрібно зареєструвати в рушії. Термін plugin module у документації Rhai позначає механізм експорту Rust-API у скрипти, а не автоматичне завантаження довільних ізольованих Rust-бібліотек із маркетплейсу.

Для нашого маркетплейсу це суттєво: Wasm дозволяє автору принести більше власної реалізації, не перетворюючи кожне нове розширення на запит до розробників ядра.

Водночас новий доступ до камери, системного сховища ключів або іншої можливості пристрою все одно потребуватиме відповідного інтерфейсу хоста. Сам компонент не повинен отримувати такі повноваження довільно.

3.2. Асинхронність: інтеграції, боти, завантаження, потоки

У Rhai задокументований спосіб роботи з асинхронними Rust-функціями: скрипт виконується в окремому потоці, передає команду виконавцю та чекає відповідь. Асинхронна робота відбувається зовні, але поточне виконання скрипта очікує результат.

Для нашої платформи я б переважно обрав інший контракт:

Скрипт формує завдання → ядро виконує його → після завершення викликається наступний обробник.

Так ми не триматимемо скрипт заблокованим на час завантаження файлу чи очікування зовнішнього сервісу. Проте послідовний сценарій доведеться розкладати на кроки.

У Wasmtime є підтримка асинхронних функцій хоста. Додатково 11 червня 2026 року вийшов WASI 0.3, який приніс async func, future<T> та stream<T> на рівень взаємодії компонентів; офіційна документація вказує підтримку у Wasmtime 46 і новіших.

Це робить Wasmtime зручнішим кандидатом для складних конекторів, потокової обробки та великої кількості одночасних очікувань. Підтримку потрібних конструкцій у конкретному SDK мови й на цільовій платформі все одно треба перевіряти.

Важлива межа: асинхронність не означає збереження процесу після вимкнення пристрою. Обидва варіанти потребують окремого механізму відновлення бізнес-процесів.

3.3. Продуктивність і зручність редагування

Для Rhai стандартний шлях — розібрати скрипт у AST і повторно виконувати це представлення. Це дозволяє редагувати логіку без збирання Rust-проєкту. У поточній документації також є експериментальний bytecode-рушій grain, але я не робив би його основою виробничої архітектури без окремої перевірки.

Wasmtime може компілювати Wasm у машинний код через Cranelift або використовувати інтерпретатор Pulley. Тому неправильно обіцяти однакову швидкість Wasmtime на всіх пристроях: інтерпретований режим має інші характеристики, ніж нативно скомпільований.

Моя практична оцінка:

Для перевірки форми, зміни статусу чи вибору наступного кроку зручність Rhai може бути важливішою за різницю швидкості.
Для власних обчислювально складних алгоритмів Rust → Wasm є сильнішим базовим кандидатом.
Якщо скрипт лише викликає важкий Rust-метод ядра, основні витрати припадатимуть на цей метод, а не на мову сценарію.

Вимірювань для нашого клієнта немає, тому конкретні коефіцієнти прискорення, розміри runtime та витрати батареї зараз були б необґрунтованими.

3.4. Безпека сторонніх плагінів

Rhai має sandbox-модель, але її безпека залежить від того, які функції, об’єкти й джерела модулів ми відкриваємо скриптам. Це не окремий процес із власною ізольованою пам’яттю.

Для Rhai потрібно налаштувати обмеження операцій, глибини викликів і розмірів даних, контролювати імпорти та не використовувати режим unchecked для недовірених сценаріїв. Ліміт операцій за замовчуванням необмежений, а один виклик Rust-функції може виконати набагато більше роботи, ніж одна проста операція скрипта.

Wasmtime додає перевірки меж пам’яті Wasm і обмежує взаємодію із зовнішнім середовищем явно підключеними інтерфейсами. Для нашого маркетплейсу я вважаю це кращою базовою межею ізоляції незалежного коду. Але Wasmtime також працює всередині хост-процесу й не звільняє нас від безпечної реалізації імпортованих функцій.

Його ResourceLimiter теж не обмежує всю пам’ять хоста: окремо потрібно контролювати виділення пам’яті нашими API, розміри результатів, кількість запитів і зовнішні операції.

Для обох варіантів я заклав би однакове правило:

Доступ виклику =
права користувача або бота
∩ дозволи плагіна
∩ політика workspace
∩ обмеження конкретної операції

Мова плагіна не повинна впливати на те, чи можна прочитати приватний документ або надіслати повідомлення від чужого акаунта.

4. Що означає «вся логіка на плагінах» у нашій платформі

Я пропоную розділити її на прикладну поведінку, контракти платформи та довірену інфраструктуру.

Прикладну поведінку можна повністю винести в пакети

Наприклад, пакет «Керування проєктами» містить:

правила завершення задач → обчислення прогресу → залежності → повторення → погодження → реакції на прострочення → створення повідомлень → команди інтерфейсу.

Це не має бути зашито у Rust-ядро. На Rhai така організація відповідає задокументованому підходу з модульними обробниками подій і станом; у Wasmtime — моделі компонентів із прикладними функціями.

Новий тип задачі, нова стадія, нове правило чи новий бізнес-процес не повинні вимагати випуску нового клієнта, якщо для них достатньо наявних можливостей платформи.

За такого розподілу бізнес-логіка не знає, чи запис фізично лежить у локальних файлах, чи серверний адаптер зберігає його у зовнішній інфраструктурі. Це дозволяє зберегти наш переносний клієнт і окремо підтримати серверні сайти на базі тих самих застосунків.

Головна умова повноти — достатність цього API. Навіть найпотужніша мова не надасть плагіну можливість надсилати повідомлення, якщо платформа не надала відповідного інтерфейсу.

Довірену інфраструктуру я залишив би поза звичайними плагінами

Йдеться про фізичний запис і відновлення сховища, транспорт iroh, управління ключами, перевірку повноважень, приймання синхронізованих операцій та взаємодію з ОС.

Це архітектурна рекомендація, а не твердження, що такі алгоритми неможливо реалізувати у Wasm. Частину з них технічно можна компонентувати. Але розширення з маркетплейсу не повинне ставати власником гарантій цілісності й безпеки всієї платформи.

Розподіл простий:

Плагін визначає, що потрібно зробити у предметній області.
Ядро забезпечує, чи дозволено це і як надійно виконати операцію.

5. Інтерфейс, права, процеси та синхронізація
Інтерфейс: логіку можна винести, renderer залишається

Для наших схемних сторінок я пропоную винести в пакет опис сторінки, джерела даних, обробники команд і посилання на дозволи. Rhai або Wasm виконуватиме поведінку, а UI-renderer відображатиме компоненти.

Наприклад, плагін може визначити, які дані завантажити після вибору проєкту, як перерахувати форму чи яку сторінку відкрити після створення запису.

Але довільний новий графічний віджет потребуватиме підтримуваного UI-контракту. Додавання Wasmtime не означає автоматичної можливості завантажити будь-який нативний UI-компонент.

Права: правила можна розширювати, перевірку не можна обходити

Наш окремий конфігуратор прав залишається джерелом правил: автор запису, група, стан, стадія, комбінації AND/OR.

Rhai або Wasm можна використати для додаткових обчислюваних умов. Проте результат «дозволено» від клієнтського плагіна я не вважав би достатнім доказом для сервера чи іншого учасника синхронізації.

Ядро має перевіряти повноваження під час фактичного виконання команди. Прихована кнопка — лише поведінка інтерфейсу, а не захист даних.

Бізнес-процеси: код кроку і життєвий цикл процесу — різні речі

Сценарій:

Створити заявку → дочекатися погодження → через два дні нагадати → після погодження створити задачі.

Логіку кожного переходу можна написати на обох варіантах. Але я не зберігав би двохденне очікування лише в пам’яті скрипта чи Wasm-екземпляра.

Потрібні збережені стан процесу, поточний крок, версія коду, очікувана подія, строк і результат останньої завершеної операції. Це можна реалізувати поверх нашого файлового сховища — обов’язковий PostgreSQL із цього не випливає.

Для гарантованої роботи бота, коли всі користувацькі пристрої офлайн, потрібен доступний виконавець. Простий транспортний релей без функції виконання цього завдання не розв’яже.

Синхронізація: одна подія не повинна породжувати дублікати дій

Якщо завершена задача потрапила на телефон і ноутбук, обидва пристрої не мають незалежно створювати наступну повторювану задачу.

Я пропоную розділити:

Повторювані обчислення: валідація, формули, підготовка представлення.

Дії з ефектом: створення запису, надсилання повідомлення, зовнішній запит.

Для другого класу потрібні визначений виконавець, ідентифікатор операції, контроль повторів і збережений результат. Вибір між Rhai та Wasmtime сам по собі цього не забезпечує.

Для відтворюваних обчислень також потрібно фіксувати версію логіки та вхідні дані. Навіть Wasm не є автоматично повністю детермінованим: документація Wasmtime окремо описує вплив зовнішніх функцій, числових операцій та інших джерел недетермінованості.

6. Переносність між телефоном, браузером і сервером

Rhai простіше розглядати як одну вбудовану мову для різних клієнтів. Сам рушій можна зібрати у WebAssembly для браузера. Проте у такій збірці немає звичайного доступу до скриптових файлів; завантаження модулів потрібно організувати через наш механізм пакетів.

Wasm-компоненти також можна використовувати в браузері, але це не означає, що там працюватиме той самий нативний Wasmtime. Для JavaScript-середовища є jco; браузерні можливості та імпорти потрібно адаптувати.

На Android та iOS Wasmtime підтримується, але офіційно ці платформи описані як менш широко протестовані, ніж Windows, macOS і Linux. Pulley дає інтерпретований шлях, проте не гарантує продуктивності нативного Cranelift.

Тому переносність для нас повинна означати:

Однаковий контракт, погоджені можливості та перевірена поведінка на цільових платформах.

Не просто однакове розширення файлу.

Технічно можливе й виконання Rhai всередині Wasm-компонента: тоді скрипти залишаються редагованими, а зовнішню межу виконання забезпечує Wasm-runtime. Можливість компіляції рушія Rhai у Wasm це дозволяє, але така схема додає ще один рівень виконання й потребує власних адаптерів. Я не обирав би її за замовчуванням без вимірювань.

7. Що обрати саме нам
Лише Rhai — достатньо для повної бізнес-логіки типових застосунків

Це обґрунтований варіант, коли головне — редагування логіки всередині застосунку, динамічні схеми, автоматизації, форми, документообіг і швидке створення прикладних пакетів.

Компроміс: ядро стає постачальником більшості складних технічних можливостей, а незалежні автори сильніше залежать від його API. Для асинхронних сценаріїв потрібен чіткий подієвий або покроковий контракт.

Тобто Rhai може бути основою повноцінного прикладного рівня, а не лише «редактором формул».

Лише Wasmtime — ширша основа для незалежних розширень

Для нашого повного задуму — маркетплейсу, переносних пакетів, складних імпортерів, інтеграцій, ботів і власних алгоритмів — я віддаю перевагу Wasm-компонентам як основному формату програмованих розширень.

Компроміс: автору Rust-плагіна потрібен цикл збирання, а нам — SDK, контракти, інструменти перевірки й узгоджена підтримка клієнтських платформ.

Прості правила при цьому можна залишити декларативними. Наявність Wasmtime не зобов’язує компілювати окремий Rust-плагін для кожної перевірки поля.

Wasmtime + Rhai — лише за наявності двох реальних потреб

Комбінація виправдана, коли одночасно потрібні незалежні складні плагіни та редагування довільних сценаріїв без збирання.

Але я не створював би дві паралельні платформи. Для них мають бути спільні API даних, дозволи, події, workflow, журналювання та менеджер пакетів. Відрізняється лише спосіб виконання коду.

Підсумок: Rhai достатньо, щоб написати всю бізнес-поведінку наших типових застосунків. Wasmtime дає більше незалежності авторам, кращу основу для ізоляції та складних асинхронних розширень. Для повного масштабу нашої платформи я обрав би Wasm як основний формат плагінів, декларативні правила як базовий low-code, а Rhai — як опційний режим редагованих сценаріїв, а не обов’язковий другий рушій із першого дня.

1. Що надає платформне API

Rhai-скрипт не працює напряму з файлами чи iroh. Rust реєструє для нього контрольований API, умовно:

task_get(id)
task_create(data)
task_update(id, changes)

Назви тут наші, не вбудовані в Rhai.

Тоді приклад логіки tasks.rhai може виглядати так:

// ============================================================
// Tasks application logic
// ============================================================

const STATUS_NEW         = "new";
const STATUS_IN_PROGRESS = "in_progress";
const STATUS_BLOCKED     = "blocked";
const STATUS_DONE        = "done";
const STATUS_CANCELLED   = "cancelled";

const PRIORITY_LOW       = 1;
const PRIORITY_NORMAL    = 2;
const PRIORITY_HIGH      = 3;
const PRIORITY_CRITICAL  = 4;


// ------------------------------------------------------------
// Створення задачі
// ------------------------------------------------------------

fn before_create(ctx) {
    let task = ctx.task;

    if task.title == "" {
        throw "Назва задачі обов'язкова";
    }

    if task.status == () {
        task.status = STATUS_NEW;
    }

    if task.priority == () {
        task.priority = PRIORITY_NORMAL;
    }

    task.created_at = now();
    task.created_by = current_user().id;

    task
}


fn after_create(ctx) {
    let task = ctx.task;

    // Сповіщаємо призначеного користувача
    if task.assignee_id != () &&
       task.assignee_id != current_user().id {

        notify(
            task.assignee_id,
            `Вам призначено задачу: ${task.title}`
        );
    }

    emit("task.created", #{
        task_id: task.id,
        project_id: task.project_id
    });
}


// ------------------------------------------------------------
// Валідація задачі
// ------------------------------------------------------------

fn validate(task) {

    if task.title.trim() == "" {
        throw "Задача повинна мати назву";
    }

    if task.priority < PRIORITY_LOW ||
       task.priority > PRIORITY_CRITICAL {

        throw "Некоректний пріоритет";
    }

    if task.status == STATUS_DONE &&
       task.completed_at == () {

        throw "Завершена задача повинна мати completed_at";
    }

    true
}


// ------------------------------------------------------------
// Початок роботи
// ------------------------------------------------------------

fn start_task(task_id) {

    let task = task_get(task_id);

    if task.status != STATUS_NEW &&
       task.status != STATUS_BLOCKED {

        throw "Цю задачу неможливо почати";
    }

    if !has_permission("tasks.start", task) {
        throw "Недостатньо прав";
    }

    // Не можна починати задачу з незавершеними залежностями
    let dependencies = get_open_dependencies(task.id);

    if dependencies.len > 0 {
        throw "Спочатку потрібно завершити залежні задачі";
    }

    task_update(task.id, #{
        status: STATUS_IN_PROGRESS,
        started_at: now()
    });

    emit("task.started", #{
        task_id: task.id,
        user_id: current_user().id
    });
}


// ------------------------------------------------------------
// Завершення задачі
// ------------------------------------------------------------

fn complete_task(task_id) {

    let task = task_get(task_id);

    if !has_permission("tasks.complete", task) {
        throw "Недостатньо прав";
    }

    if task.status == STATUS_DONE {
        return;
    }


    // ---------- checklist ----------

    if "checklist" in task {

        for item in task.checklist {

            if !item.completed {
                throw `Не виконано пункт: ${item.title}`;
            }
        }
    }


    // ---------- підзадачі ----------

    let open_children = task_query(#{
        parent_id: task.id,
        status_not_in: [
            STATUS_DONE,
            STATUS_CANCELLED
        ]
    });

    if open_children.len > 0 {
        throw "Спочатку потрібно завершити всі підзадачі";
    }


    // ---------- оновлення ----------

    task_update(task.id, #{
        status: STATUS_DONE,
        completed_at: now(),
        completed_by: current_user().id
    });


    // ---------- повторювана задача ----------

    if task.recurrence != () {
        create_next_occurrence(task);
    }


    // ---------- подія ----------

    emit("task.completed", #{
        task_id: task.id,
        project_id: task.project_id,
        user_id: current_user().id
    });
}


// ------------------------------------------------------------
// Повторювані задачі
// ------------------------------------------------------------

fn create_next_occurrence(task) {

    let next_date =
        calculate_next_date(
            task.due_at,
            task.recurrence
        );

    let new_task = #{
        title: task.title,
        description: task.description,

        project_id: task.project_id,

        assignee_id: task.assignee_id,

        priority: task.priority,

        status: STATUS_NEW,

        due_at: next_date,

        recurrence: task.recurrence,

        source_task_id: task.id
    };

    let created = task_create(new_task);

    emit("task.recurrence.created", #{
        previous_task_id: task.id,
        new_task_id: created.id
    });
}


// ------------------------------------------------------------
// Розрахунок наступної дати
// ------------------------------------------------------------

fn calculate_next_date(date, recurrence) {

    switch recurrence.type {

        "daily" =>
            date.add_days(recurrence.interval),

        "weekly" =>
            date.add_days(7 * recurrence.interval),

        "monthly" =>
            date.add_months(recurrence.interval),

        _ =>
            throw "Невідомий тип повторення"
    }
}


// ------------------------------------------------------------
// Прострочення
// ------------------------------------------------------------

fn check_overdue(task) {

    if task.status == STATUS_DONE ||
       task.status == STATUS_CANCELLED {

        return;
    }

    if task.due_at == () {
        return;
    }

    if task.due_at < now() {

        if task.assignee_id != () {

            notify(
                task.assignee_id,
                `Задача прострочена: ${task.title}`
            );
        }

        emit("task.overdue", #{
            task_id: task.id,
            due_at: task.due_at
        });
    }
}


// ------------------------------------------------------------
// Залежності
// ------------------------------------------------------------

fn get_open_dependencies(task_id) {

    let task = task_get(task_id);

    if !("dependencies" in task) {
        return [];
    }

    let result = [];

    for dependency_id in task.dependencies {

        let dependency = task_get(dependency_id);

        if dependency.status != STATUS_DONE &&
           dependency.status != STATUS_CANCELLED {

            result.push(dependency);
        }
    }

    result
}


// ------------------------------------------------------------
// Автоматичний пріоритет
// ------------------------------------------------------------

fn calculate_priority(task) {

    let score = 0;

    if task.due_at != () {

        let days = days_between(
            now(),
            task.due_at
        );

        if days <= 1 {
            score += 50;
        }
        else if days <= 3 {
            score += 25;
        }
        else if days <= 7 {
            score += 10;
        }
    }


    if task.is_important {
        score += 30;
    }


    let open_dependencies =
        get_open_dependencies(task.id);

    if open_dependencies.len > 0 {
        score -= 20;
    }


    if score >= 70 {
        PRIORITY_CRITICAL
    }
    else if score >= 40 {
        PRIORITY_HIGH
    }
    else if score >= 15 {
        PRIORITY_NORMAL
    }
    else {
        PRIORITY_LOW
    }
}


// ------------------------------------------------------------
// Зміна виконавця
// ------------------------------------------------------------

fn change_assignee(task_id, user_id) {

    let task = task_get(task_id);

    if !has_permission(
        "tasks.change-assignee",
        task
    ) {
        throw "Недостатньо прав";
    }

    let old_assignee = task.assignee_id;

    task_update(task.id, #{
        assignee_id: user_id
    });


    notify(
        user_id,
        `Вам призначено задачу: ${task.title}`
    );


    emit("task.assignee.changed", #{
        task_id: task.id,
        from: old_assignee,
        to: user_id
    });
}


// ------------------------------------------------------------
// Блокування задачі
// ------------------------------------------------------------

fn block_task(task_id, reason) {

    let task = task_get(task_id);

    if reason.trim() == "" {
        throw "Необхідно вказати причину блокування";
    }

    task_update(task.id, #{
        status: STATUS_BLOCKED,
        blocked_reason: reason,
        blocked_at: now(),
        blocked_by: current_user().id
    });


    emit("task.blocked", #{
        task_id: task.id,
        reason: reason
    });
}

fn approve_task(task_id) {

    let task = task_get(task_id);

    let approval =
        get_current_approval(
            "task",
            task.id
        );

    if approval.approver_id
            != current_user().id {

        throw "Ви не є погоджувачем";
    }

    approval_update(
        approval.id,
        #{
            status: "approved",
            approved_at: now()
        }
    );

    complete_task(task.id);
}

Але очікування погодження не означає, що Rhai-скрипт висить у пам'яті.

Правильно:

Rhai
 │
 ├─ створив approval
 └─ завершився

      ↓ через 3 дні

користувач натиснув Approve

      ↓

новий запуск Rhai
 │
 └─ approve_task()

Це дуже добре підходить під нашу файлову/local-first архітектуру.

4. Відкладені задачі

Наприклад, нагадати за день до дедлайну:

fn schedule_deadline_reminder(task) {

    if task.due_at == () {
        return;
    }

    let reminder_at =
        task.due_at.add_days(-1);

    schedule(
        "task.deadline_reminder",
        reminder_at,
        #{
            task_id: task.id
        }
    );
}

А потім:

fn deadline_reminder(data) {

    let task =
        task_get(data.task_id);

    if task.status == STATUS_DONE {
        return;
    }

    notify(
        task.assignee_id,
        `Завтра дедлайн: ${task.title}`
    );
}

Тут ми дуже чітко бачимо межу:

Rhai:
    вирішує КОЛИ і ЩО зробити

Rust runtime / scheduler:
    гарантує, що це буде виконано
5. Можна навіть створити власну поведінку конкретного типу задач

Наприклад пакет Software Development.

fn on_bug_created(task) {

    if task.type != "bug" {
        return;
    }

    if task.severity == "critical" {

        task_update(task.id, #{
            priority: PRIORITY_CRITICAL
        });

        let team =
            get_project_team(
                task.project_id
            );

        for member in team {

            if member.role == "developer" {

                notify(
                    member.id,
                    `Критичний дефект: ${task.title}`
                );
            }
        }
    }
}

Інший застосунок може взагалі не знати про severity.

Він підключає пакет:

Base Tasks
    ↓
Software Development
    ↓
Bug Tracking

де кожен додає свої поля, правила та обробники.

Це вже дуже близько до тієї системи пакетів/застосунків, яку ми обговорюємо.

Тобто попередній приклад можна переписати:

fn complete_task(task_id) {

    let task =
        record_get(
            "task",
            task_id
        );

    if task.status == "done" {
        return;
    }

    record_update(
        "task",
        task_id,
        #{
            status: "done",
            completed_at: now(),
            completed_by: current_user().id
        }
    );

    emit(
        "task.completed",
        #{
            task_id: task_id
        }
    );
}
