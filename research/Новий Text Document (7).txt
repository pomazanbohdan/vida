Дуже важлива деталь про Iroh

Тут Delta Chat фактично підтверджує напрямок, який ми раніше розглядали, але робить його більш практичним.

У Chatmail Core Iroh не замінює durable messaging transport. Він використовується для P2P, multi-device setup та realtime WebXDC. Основне повідомлення має store-and-forward шлях через SMTP/IMAP.

Це дає хороший hybrid:

                 FAST PATH
 Device A ───────── Iroh ───────── Device B
                  realtime/P2P
                       │
                       │ fallback / offline
                       ▼
 Device A ── Chatmail relay ── Federation ── Relay ── Device B
                 DURABLE PATH

Для месенджера це, на мій погляд, краще за Iroh-only: користувач B може бути offline добу, не потрібен одночасний online peer, є push, NAT traversal, federation і резервний delivery path.

Сам Chatmail relay уже містить Iroh relay та TURN, поряд із Postfix, Dovecot, push-сервісами й автоматичним видаленням старих повідомлень.

І немає центральної PostgreSQL для месенджера

Це також дуже близько до нашої концепції переносного локального стану.

На клієнті Delta Chat використовує локальну SQLite database, окрему для профілю, плюс blob directory для вкладень. Core має підтримку SQLCipher, тобто база може бути зашифрована.

Масштаб relay виглядає достатньо серйозно

Chatmail relay за замовчуванням має ліміти близько 10 000 IMAP та 1 000 SMTP одночасних connections, причому документація окремо описує інсталяції з 10k–100k+ addresses та необхідність налаштування connection limits.

Це не означає, що один relay автоматично витримає мільйон active users. Але фундамент тут вже production-oriented, а горизонтальне масштабування можна робити через багато федеративних relay:

         Community
             │
    ┌────────┼────────┐
    ▼        ▼        ▼
 Relay UA   Relay EU  Relay US
    │        │        │
  users    users    users

Для нашої моделі це особливо привабливо: користувач не повинен належати одному центральному кластеру нашої компанії.

Multi-relay — ще одна дуже корисна новинка 2026

Останні версії вже дозволяють одному профілю використовувати декілька relay. Клієнти надсилають повідомлення до кількох relay, синхронізують relay configuration між пристроями й можуть продовжувати працювати, якщо один relay недоступний.

Тобто можна мати:

                 ┌── Relay A
User identity ───┼── Relay B
                 └── Relay C

Relay A DOWN
      ↓
B/C продовжують працювати

Це дуже добре відповідає нашій вимозі переносності й відсутності залежності від одного central backend.

І принципово:

transport ≠ messaging model.

Тобто Message, Group, Channel, Community нічого не повинні знати про Iroh або relay.

1. Iroh — fast path
Alice ───────────── Iroh ───────────── Bob
       direct QUIC connection

Якщо обидва пристрої доступні:

повідомлення;
typing;
presence;
WebRTC signaling;
великі файли;
realtime app state;

можуть йти напряму.

Delta Chat уже демонструє практичне використання Iroh для P2P та realtime WebXDC.

2. Але потрібен наш durable relay

Ось це ключове.

Не:

SMTP mailbox

а:

Messaging Relay

Наприклад:

Alice
  │
  │ encrypted envelope
  ▼
┌────────────────────────┐
│ Relay                  │
│                        │
│ recipient/device queue │
│ encrypted envelopes    │
│ blob references        │
│ TTL                    │
│ delivery cursors       │
└───────────┬────────────┘
            │
         Bob offline
            │
          later
            ▼
           Bob

Relay не повинен розшифровувати повідомлення.

Він бачить мінімально необхідне:

Envelope {
    protocolVersion
    destination
    messageId
    timestamp
    ttl
    encryptedPayload
}

А краще ще сильніше мінімізувати metadata.

3. Iroh + relay одночасно

Тобто доставка:

send(message)
       │
       ▼
 Encrypt
       │
       ├────► Iroh direct
       │
       └────► Relay durable queue

Але необов'язково завжди дублювати весь payload.

Наприклад:

try direct

if recipient ACK:
    relay stores only short-lived fallback
else:
    relay keeps envelope until ACK/TTL

Це вже можна окремо оптимізувати.

4. Для великих груп P2P fan-out робити не можна

Наприклад:

Group = 50 000 users

не можна робити:

sender
 ├─ peer1
 ├─ peer2
 ├─ peer3
 ...
 └─ peer50000

Замість цього:

                    ┌── Relay A
Publisher ──────────┼── Relay B
                    ├── Relay C
                    └── Relay D
                          │
                    subscribers

Тут Delta Chat Broadcast Channels корисні нам більше як crypto/protocol reference, ніж як transport implementation. Їхні E2EE broadcast channels уже вирішують частину проблеми шифрування великої аудиторії.

5. Я б зробив усі повідомлення event-based

Це добре стикується і з нашою загальною платформою.

Не:

message row

а:

Event
{
   id
   streamId
   author
   device
   sequence
   timestamp

   type:
      MessageCreated
      MessageEdited
      MessageDeleted
      ReactionAdded
      MemberJoined
      MemberBanned
      RoleChanged
      TopicCreated
      ...

   payload

   signature
}

Тоді:

Conversation = ordered event stream

Це одразу вирішує дуже багато проблем:

offline;
multi-device;
replication;
history;
forum;
moderation;
bots;
audit;
incremental sync;
conflict resolution.

І добре стикується з нашою попередньою file/local-first архітектурою.

6. Community і Forum стають природними
Community
│
├── Members
├── Roles
├── Moderators
├── Ban list
│
├── Channel: News
│
├── Channel: General
│

     │
     ├── Category
     │    ├── Topic
     │    │    └── Thread events
     │    └── Topic
     │

Усе це той самий event protocol.

Не потрібен окремий «forum backend».

7. Identity теж не email

Це особливо важливо.

Я б узагалі не вводив у protocol поняття:

user@example.com

Identity повинна бути криптографічною:

User
 └── IdentityKey
      │
      ├── DeviceKey A
      ├── DeviceKey B
      └── DeviceKey C

Наприклад:

UserId = hash(public identity key)

А username:

@bogdan

це лише human-readable alias із directory layer.

Так користувач може:

змінювати username;
використовувати декілька relay;
працювати без центрального account provider;
мігрувати між relay;
використовувати локальну мережу;
працювати P2P.
8. Relay не є identity provider

Це теж принципова відмінність від email.

Identity ≠ Relay account

Користувач:

Identity X
   │
   ├─ Relay Kyiv
   ├─ Relay Europe
   └─ direct Iroh

може просто опублікувати:

ReachabilityDescriptor {
    identity
    devices[]
    relays[]
    irohEndpoint
    capabilities
}

підписаний identity key.

Це дуже добре стикується з multi-relay ідеями Delta Chat, але вже без email baggage.

Що тоді таке Delta Chat для нашого проєкту

Я б тепер формально поставив його сюди:

                  OUR PLATFORM
                       │
        ┌──────────────┴───────────────┐
        │                              │
OUR IMPLEMENTATION              REFERENCE PROJECTS
                                       │
                              ┌────────┼────────┐
                              │        │        │
                          DeltaChat  Signal   Nostr
                              │
                         extract ideas

А не:

OUR UI
   ↓
Delta Chat Core

Це важлива зміна.

Найцінніше, що можна забрати з Delta Chat

Я б тепер окремо розібрав їхній код на 7 модулів, які потенційно варто адаптувати або перевикористати:

peer_channels.rs — Iroh/gossip;
broadcast channel implementation;
group membership protocol;
crypto/key rotation;
SecureJoin;
WebXDC realtime/state synchronization;
multi-device synchronization.

А imap.rs, smtp.rs, mimefactory.rs, mimeparser.rs, transport email configuration тощо для нашої архітектури — не потрібні взагалі.

Отже виправлений напрямок: не “форк Delta Chat”, а “native Iroh messenger protocol, використовуючи Delta Chat як перевірений донор алгоритмів/реалізацій там, де вони не пов'язані з email”. Це значно краще відповідає нашій початковій концепції переносної, local-first, multi-relay платформи.
