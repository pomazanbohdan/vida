Консолідована архітектура платформи

Головне рішення: платформу потрібно будувати не навколо окремих сутностей на кшталт «задача», «нотатка» чи «форум», а навколо універсального ядра:

Контури володіння даними — персональний простір або організація.
Воркспейси — робочі середовища всередині контуру.
Ресурси та записи — універсальні об’єкти, файли, колекції, сторінки.
Типи об’єктів і зв’язків — системні або створені користувачем.
Застосунки — пакети схем, сторінок, ролей, workflow та інтеграцій.
Контракти доступу — безпечне підключення даних між просторами.
Capability runtime — контроль того, що може робити встановлений застосунок.

Задачі, нотатки, документи та проєкти мають постачатися як системні застосунки, реалізовані через той самий механізм пакетів, що й marketplace-застосунки. Вони встановлені за замовчуванням і мають підвищений рівень довіри, але не створюють окрему паралельну архітектуру.

Ітерація 1. Межі системи та основні поняття
1.1. Контур володіння — OwnershipScope

Це головна межа:

володіння даними;
політик безпеки;
шифрування;
розміщення даних;
встановлених застосунків;
білінгу;
retention-політик;
аудиту.

Типи контурів:

Тип	Призначення
Personal	Автоматично створюється для кожного користувача
Organization	Створюється користувачем або адміністратором
System	Системні каталоги, marketplace, службові дані

Не потрібно вводити окремі контури Community, Forum, Website, OSBB. Це не нові типи tenant’ів, а застосунки та воркспейси всередині організаційного контуру.

Організація має власні:

групи й учасників;
ролі;
застосунки;
схеми об’єктів;
розширення схем;
workflow;
інтеграції;
політики доступу;
ключі шифрування;
брендинг;
домени;
тариф і квоти.

Персональний простір використовує ту саму модель, але за замовчуванням має одного власника.

1.2. Воркспейс — Workspace

Воркспейс — це не tenant і не власник даних. Це робоче середовище всередині контуру:

персональний;
командний;
проєктний;
керований застосунком;
приватний;
публічний;
архівний.

Воркспейс визначає:

навігацію;
набір підключених застосунків;
локальні ролі;
списки, дошки, календарі та сторінки;
колекції ресурсів;
локальні представлення даних;
учасників, які не обов’язково є повними членами організації.
1.3. Встановлення та екземпляр застосунку

Потрібно розділити:

AppInstallation

Фіксує:

який пакет встановлений;
його версію;
дозволені capabilities;
залежності;
ліцензію;
довіру до видавця;
застосовані міграції.
AppInstance

Фіксує конкретну конфігурацію застосунку:

конкретний форум;
конкретний сайт новин;
конкретне ОСББ;
конкретний чат;
конкретний проєктний портал.

Одна інсталяція пакета Forum може мати декілька екземплярів форумів.

Organization Scope
├── AppInstallation: Forum 2.4.1
│   ├── AppInstance: Форум будинку №1
│   └── AppInstance: Форум правління
├── AppInstallation: News CMS 1.8.0

└── Workspaces
    ├── Адміністрація
    ├── Мешканці

1.4. Ресурс — універсальний об’єкт безпеки

Resource — усе, до чого можна надати доступ:

воркспейс;
колекція;
запис;
файл;
папка;
сторінка;
dashboard;
app instance;
workflow;
форма;
опублікований матеріал.

Кожен ресурс має рівно один контур-власник.

Один ресурс не повинен одночасно належати персональному простору й організації. Для підключення до інших просторів використовуються:

гранти;
mounts;
контракти даних;
копії;
overlays;
зв’язки.

Це усуває невизначеність щодо видалення, аудиту, шифрування та права власності.

ABP доцільно залишити модульним каркасом для trusted-модулів платформи. Він підтримує модульність і multi-tenancy, але ABP Tenant, OwnershipScope і Workspace не слід механічно ототожнювати. OwnershipScope має залишатися канонічною предметною моделлю платформи.

Ітерація 3. Універсальна модель об’єктів
3.1. Базова модель запису

Логічно запис складається з двох частин.

Resource
- Id
- OwnerScopeId
- HomeWorkspaceId?
- ParentResourceId?
- ResourceKind
- OwnerPrincipalId
- CreatedAt
- UpdatedAt
- DeletedAt?
- Revision
- SecurityClassification
- SyncMode

Record
- ResourceId
- TypeVersionId
- LifecycleState
- Title
- Data
- SearchProjection
- ExtensionSetId?

Resource відповідає за:

володіння;
ієрархію;
доступ;
аудит;
видалення;
sync;
mounts.

Record відповідає за предметні поля.

3.2. Гібридне зберігання

Не варто використовувати:

чистий EAV;
окрему фізичну таблицю для кожного користувацького типу;
тільки schemaless JSON;
event sourcing для всіх сутностей.

Оптимальна модель:

Універсальна таблиця records.
Системні поля — типізовані SQL-колонки.
Користувацькі поля — JSON/JSONB.
Вибрані поля — індексні проєкції.
Для критичних або високонавантажених типів — спеціалізовані projection-таблиці.

Наприклад:

Task має projection для status, due_at, priority, assignee;
Message має append-only storage;
Document має окремий CRDT/content store;
FileAsset посилається на content-addressed blob;
інші custom records залишаються в універсальному store.

PostgreSQL підтримує індексування jsonb, зокрема GIN-індекси, а Row Level Security дозволяє обмежувати видимість і зміну рядків. У цій архітектурі RLS слід використовувати для захисту межі контуру як defense-in-depth, але не як єдиний механізм складної графової авторизації.

3.3. Підтримка PostgreSQL і MSSQL

Формат застосунків і типів має залишатися незалежним від БД.

Потрібні адаптери:

IRecordStore
IRecordQueryCompiler
IIndexPlanner
IRowIsolationProvider
ISchemaMigrationProvider

Референсна реалізація:

PostgreSQL;
JSONB;
GIN/expression indexes;
RLS;
generated columns;
partitioning за потреби.

MSSQL-адаптер:

JSON columns;
computed columns;
provider-specific indexes;
власна реалізація row filtering.

Не потрібно зводити всю платформу до найменшого спільного знаменника двох БД. Package format залишається однаковим, а physical query/index plan — provider-specific.

3.4. Розміщення tenant-даних

ScopePlacement визначає, де фізично зберігається контур:

shared database;
окремий schema;
окрема БД;
окремий кластер;
локальний вузол;
hybrid/local-first.

Невеликі персональні та організаційні контури можуть працювати в shared DB. Великі організації можуть бути перенесені до окремої БД без зміни ID або package model.

4.3. Data schema та UI schema мають бути окремими

Один тип може мати:

Тому:

DataSchema != FormSchema != PageLayout != ViewDefinition

Зміна форми не повинна створювати нову версію data schema.

4.4. Власні типи створюються як локальний застосунок

Коли користувач через low-code UI створює:

тип;
поле;
зв’язок;
сторінку;
роль;
workflow,

платформа фактично редагує локальний пакет:

local.<scope-id>.<app-id>

Це забезпечує:

версіонування;
export/import;
тестування;
міграції;
подальшу публікацію в marketplace;
відсутність «магічної конфігурації» поза package system.
4.5. Розширення існуючих типів

Не можна прямо змінювати schema стороннього застосунку. Використовується TypeExtension.

Base type:
  forum.thread

Organization extension:
  local.my-org.forum-extension
    + sponsor
    + internalPriority
    + responsibleModerator

Порядок композиції:

Platform base
→ Base app
→ Publisher extensions
→ Organization extensions
→ App-instance configuration
→ Workspace views
→ User preferences

Правила:

base fields не видаляються локальним extension;
нові поля мають власний namespace;
тип базового поля не змінюється без міграції;
локальні extensions оновлюються незалежно;
оновлення base app не перезаписує локальні поля;
workspace-рівень зазвичай змінює views/forms, а не основну persistent schema.
Ітерація 5. Власні зв’язки
5.1. Три різні категорії зв’язків

Їх не можна змішувати.

1. Системна ієрархія
scope → workspace;
workspace → collection;
collection → resource;
app instance → managed workspaces.

Вона впливає на навігацію та може впливати на успадкування доступу.

2. Предметні зв’язки
задача належить проєкту;
квартира знаходиться в будинку;
стаття має автора;
заявка пов’язана з обладнанням.

Вони самі по собі не надають доступ.

3. Authorization relations
owner;
viewer;
editor;
member;
moderator;
delegated administrator.

Вони використовуються системою доступу.

Предметний зв’язок може бути позначений як authorizationBearing, але лише якщо app package явно задає правило компіляції в authorization relation.

Наприклад:

Apartment --resident--> User

може породжувати:

User has viewer access to Apartment

Але зв’язок:

Apartment --locatedIn--> Building

не повинен автоматично надавати доступ до всіх квартир будинку.

5.2. RelationTypeDefinition

Тип зв’язку визначає:

типи лівого та правого endpoint;
напрямок;
inverse name;
cardinality;
required/optional;
унікальність;
payload schema;
temporal validity;
delete behavior;
cross-scope policy;
permission propagation;
sync strategy;
ownership/composition.

Підтримувані категорії:

one-to-one;
one-to-many;
many-to-many;
directed;
symmetric;
containment;
association;
dependency;
membership;
temporal relation.

RelationInstance може мати власні поля:

User --residentOf--> Apartment
- role: owner | tenant | family-member
- validFrom
- validTo
- primary
- verified
5.3. Cross-scope relations

Зв’язок між різними контурами дозволяється лише якщо:

Користувач має link на source.
Користувач має link або create relation на target.
Тип зв’язку дозволяє cross-scope.
Існує відповідний DataAccessContract.
Жодна сторона не порушує app capability policy.

Cross-scope relation:

не передає ownership;
не створює каскадне видалення;
не надає автоматично доступ;
не відкриває приховані поля;
після revoke перетворюється на недоступний handle або tombstone.

6.3. Модель рішення
ALLOW =
    PlatformEntitlement
  ∧ ActiveAccount
  ∧ ScopeBoundary
  ∧ AppCapability
  ∧ RelationshipAccess
  ∧ RoleActionPermission
  ∧ StatePolicy
  ∧ FieldPolicy
  ∧ DataAccessContract
  ∧ NOT HardDeny

Наприклад:

застосунок має capability читати core.task;
організація має entitlement на застосунок;
користувач має роль ProjectMember;
персональний власник відкрив лише title, status, dueAt;
користувач може змінювати тільки status.

Результат: організація не бачить приватний description або attachments навіть якщо користувач є адміністратором app instance.

cross-organization relations.

OpenFGA реалізує relationship-based authorization, підтримує conditions і contextual tuples, зокрема authorization у контексті конкретної організації.

Policy Compiler — дії, поля й стани

Окремий вузький policy runtime відповідає за:

custom permission IDs;
app-specific roles;
object state;
field visibility;
field editability;
purpose;
request context;
conditional actions.

Це не повинен бути другий загальний authorization graph. Він отримує результати relationship check і застосовує типізовані правила.

Casbin.NET можна залишити внутрішньою реалізацією цього шару, але:

app packages не повинні залежати від синтаксису Casbin;
канонічним форматом має бути власний typed policy AST;
OpenFGA залишається джерелом relationship truth.
Database RLS — останній захисний бар’єр

RLS або provider-specific row filtering захищає від випадкового читання чужого OwnershipScope.

Він не замінює:

OpenFGA;
field policies;
app capabilities;
data contracts.

6.9. Пошук з урахуванням прав

Не слід робити OpenFGA ListObjects єдиним способом побудови кожного списку. Його продуктивність залежить від складності моделі та кількості relations.

Матеріалізована AccessProjection.

Сильна перевірка перед write/export/share.

Офіційна документація OpenFGA окремо попереджає, що продуктивність ListObjects залежить від складності relations і кількості потенційних результатів.

В authorization tuples не потрібно зберігати email, ПІБ або інші персональні дані — лише opaque IDs.

Ітерація 9. Легкий workflow engine

Потрібно розділити три поняття, але показувати їх в одному дизайнері.

9.1. Рівень 1: Business Rule

Синхронне виконання в межах команди.

Використовується для:

Business Rule:

deterministic;
без network;
без довгих очікувань;
без side effects;
виконується в транзакції.
9.2. Рівень 2: Automation

9.6. Runtime

Рекомендована модель:

generic declarative graph interpreter;
Dapr Workflow як durable execution runtime;
activity workers для side effects;
event/outbox triggers;
definition snapshot pinned до instance.

Dapr Workflow підтримує event-sourced execution state, durable retries, timers, pause/resume, external events і розподілене виконання workflow activities.

Generic orchestrator не повинен під час replay довільно читати БД або викликати зовнішні API. Він працює з зафіксованою версією graph, а side effects виконуються activities.

9.7. Гарантії виконання

Activities потрібно вважати at-least-once.

Кожний side effect отримує idempotency key:

workflowInstanceId + nodeId + iteration + attemptScope

Потрібні:

retry;
exponential backoff;
timeout;
dead-letter;
compensation;
cancellation;
pause/resume;
max loop count;
max execution depth;
quotas.

Не потрібно обіцяти «exactly once» для зовнішніх API.

9.8. Run-as model

Workflow запускається як:

triggering user;
app service principal;
system principal;
спеціальний delegated workflow principal.

За замовчуванням:

manual workflow — від імені користувача;
scheduled workflow — від імені app installation;
external webhook — від імені connector principal.

Кожен крок перевіряє права під час виконання. Workflow не зберігає назавжди права, які користувач уже втратив.

9.9. Human tasks

delegation;

WorkItem можна показувати в загальному Inbox поряд із задачами.

9.10. Event delivery

Зміна record і створення domain event повинні бути в одній транзакції через outbox.

Dapr підтримує transactional outbox для state/pub-sub сценаріїв, а його pub/sub використовує CloudEvents envelope.

App event payload має бути мінімальним:

scope ID
revision

correlation

Повні дані app отримує через звичайний authorized read. Це запобігає витоку прихованих полів через event bus.

9.11. Elsa

Elsa доцільно залишити як опційний Advanced Workflow app для:

спеціального workflow studio;
advanced operator tooling.

Elsa підтримує versioned definitions, persisted instances, custom activities і multitenancy, але не потрібно робити його обов’язковою моделлю для простих користувацьких automations.

Iroh Collections не слід використовувати як заміну graph database або вкладеної структури воркспейсів: collections у blobs — це послідовності hash references, а не повноцінна queryable object graph.

10.3. Інтеграція з .NET

Актуальні офіційні bindings Iroh охоплюють Rust, Python, Swift, Kotlin, JavaScript і C; офіційного C# binding у переліку немає. Тому для .NET-платформи оптимальний варіант — окремий Rust Sync Node, доступний через local gRPC або Unix domain socket.

        │ gRPC/UDS
        ▼

        ├── iroh-blobs
        ├── iroh-docs / Automerge
        ├── peer connections
        └── relay connections

На Android можна використовувати Kotlin binding у native sync layer.

Атомарно змінити локальний head ref.
Оновити локальні projections.
Запланувати синхронізацію.

На файловій системі атомарність останнього кроку забезпечується atomic replace/rename або маленькою транзакцією embedded store.

2.4. Commit DAG

Коміти утворюють DAG:

A ── B ── C
      └── D ── M
           ↑
        інший пристрій

Ресурс може мати:

один лінійний writer;
декілька writers із deterministic merge;
CRDT;
authority-only режим;
manual conflict resolution.

Automerge доцільно використовувати для блокового тексту та справді collaborative JSON-like документів, а не для всіх об’єктів платформи. Він розрахований на local-first роботу, локальні зміни та подальшу синхронізацію реплік.

Ітерація 3. Resource facets і реальна field-level безпека

У local-first системі не можна просто віддати іншому користувачеві encrypted blob, а потім приховати частину полів у UI. Якщо отримувач отримав ключ, він фізично має всі дані.

Тому logical resource потрібно розкладати на facets.

Task
├── PublicFacet
│   ├── title
│   ├── status
│   └── dueAt
├── ContentFacet
│   └── description
├── PrivateFacet
│   └── privateNotes
├── AttachmentsFacet
└── OrganizationOverlay

Кожен facet має:

окремий encryption key;
окремі права;
окрему replication policy.
3.1. Два способи часткового sharing
Наперед визначені facets

Тип об’єкта розподіляє поля за security groups:

public
member
confidential

secret
Матеріалізована shared projection

Коли потрібна довільна комбінація полів:

      │
      ├── title
      ├── status
      └── dueAt
           │
           ▼
SharedProjection resource

Організація синхронізує саме projection, а не вихідну задачу.

Так забезпечуються:

revoke для майбутніх версій;
незалежні organization overlays.

Повністю стерти вже розшифровану й законно завантажену копію неможливо. Тому окремо контролюються:

download;
offline storage;
export;

Ітерація 5. Мережева топологія і релеї
5.1. Різні види вузлів
Вузол	Функція
Client Node	Телефон, ноутбук, desktop
Scope Authority Node	Приймає strict commands конкретного scope
Availability Node	Тримає encrypted replica для доступності
Transport Relay	Передає encrypted packets
Discovery Node	Зіставляє Endpoint ID з адресою/relay
Mailbox Node	Store-and-forward encrypted envelopes
Worker Node	Workflow, integrations, builds
Site Runtime	Обслуговує публічний сайт або портал
Control Plane	Каталоги, trust, billing, admin
Marketplace Mirror	Кеш застосунків і data products
5.2. Transport Relay не є data server

Iroh намагається встановити пряме QUIC-з’єднання, а relay використовує як fallback. Relay не розшифровує трафік і не зберігає application state; self-hosted або dedicated relays можна замінювати незалежно від даних.

Тому потрібне розділення:

Transport Relay
- stateless
- encrypted packets
- NAT traversal fallback

Availability Node
- encrypted blobs
- commits
- snapshots
- offline delivery

Authority Node
- strict command validation
- sequential state
- workflow coordination
5.3. Mailbox

Коли цільовий вузол offline:

sender завантажує encrypted envelope;
mailbox не знає payload;
envelope має TTL;
recipient забирає його після появи online;
великі blobs залишаються на availability nodes;
mailbox передає лише heads, commands і wake-up hints.
5.4. Discovery

Можливі режими:

realm DNS/Pkarr;
self-hosted DNS/Pkarr;
DHT;
LAN/mDNS;
QR/ticket;
manually configured endpoints.

Iroh підтримує signed address records через DNS/Pkarr, а також окремий DHT-based lookup, тому офіційний discovery service не повинен бути єдиною точкою доступу.

5.5. Browser

Браузерний runtime може використовувати Iroh через WebAssembly, але через обмеження браузерної sandbox-моделі його з’єднання мають проходити через relay. Тому повний sovereign node краще запускати як native mobile/desktop app, а browser використовувати як web replica або portal client.

5.6. Sync protocol

Пропоновані ALPN protocols:

vida/sync/1
vida/blob/1
vida/commands/1
vida/events/1
vida/mailbox/1
vida/authority/1
vida/dataset/1

Синхронізація:

Встановлення authenticated Iroh connection.
Передача capability proof.
Обмін доступними segment heads.
Порівняння commit DAG.
Передача відсутніх commits.
Передача manifests.
Lazy transfer blobs.
Перевірка signatures та schema.
Merge або authority validation.
Оновлення projections.

Iroh позиціонується саме як набір composable networking protocols: encrypted connections, blobs, gossip, documents та можливість будувати власні протоколи поверх ALPN.

Знайдені й перевірені за період приблизно 27 серпня — 10 вересня 2026 року проєкти підтверджують правильність основного напряму:

немає обов’язкової центральної БД;

індекси, пошук та аналітичні представлення можна перебудувати.

Однак нові проєкти показали, що попередня модель була надто універсальною у чотирьох місцях:

Vault не повинен означати один універсальний commit-DAG для всіх типів даних.
Iroh endpoint, relay policy та ALPN-протоколи повинні належати окремому Node Host, а не застосункам.
Потрібно формально розділити semantic data, blobs, datasets, realtime media, strict ledgers і projections.
Workflow потрібно розділити на звичайні процеси, AI-agent jobs і багатосторонні agreement sessions.

Тобто потрібна PersonalVida Portable Architecture vNext, але зі збереженням попередніх фундаментальних рішень.

Ітерація 1. Що залишається без змін
1.1. ScopeVault залишається головною межею переносності

Кожен персональний або організаційний простір має переносний ScopeVault.

Він залишається:

межею володіння;
межею ключів;
одиницею експорту;
одиницею резервного копіювання;
одиницею перенесення між пристроями, VPS, NAS або realms;
коренем для ресурсів, політик, застосунків і data bindings.

Але тепер Vault треба визначити не як одну конкретну storage engine, а як переносний контейнер із декількома профілями сховищ.

1.2. Один ресурс — один логічний власник

Інваріант залишається:

Кожен Resource має рівно один OwnerScope.

Інші простори можуть отримати:

reference;
mount;
projection;
data contract;
encrypted replica;
overlay;
fork.

Але фізична репліка або використання ресурсу в іншому застосунку не змінює ownership.

1.3. Data Contracts залишаються єдиним способом перевикористання даних

Міський адресний довідник, каталог людей, файли, платежі, календарі або інші ресурси не повинні відкривати внутрішнє сховище застосункам.

Зберігається модель:

Provider
→ Data Contract
→ Data Port
→ Data Binding
→ Consumer App

Consumer не має знати, де фізично розташовані дані:

у локальному vault;
в Iroh-репліці;
у S3;
у Parquet;
у DuckDB;
у зовнішній SQL-БД;
у зовнішньому API.
1.4. Control Plane не стає джерелом істини для користувацьких даних

Головна адмінка, marketplace, billing, discovery, relay fleet і portal SaaS залишаються окремими службовими площинами.

Втрата глобального control plane не повинна блокувати:

локальне читання;
локальне редагування;
роботу встановлених застосунків;
peer-to-peer sync за відомими адресами;
локальні organization nodes;
self-hosted сайти.
Ітерація 2. Vault потрібно перетворити на контейнер профільних сховищ
2.1. Проблема попередньої моделі

Раніше всі зміни логічно проходили через однакові immutable commits. Це добре для переносності, але погано масштабується на різні навантаження:

задача;
спільний документ;
чат із мільйонами повідомлень;
відеопотік;

2.4. Що підтвердили нові проєкти

diaswarm практично підтверджує, що недовірений вузол може тримати й віддавати ciphertext, не маючи можливості його прочитати. Він також показує реальну семантику відкликання: користувач перестає отримувати ключі нових сегментів, але вже завантажену розшифровану копію відкликати неможливо.

Ітерація 3. Додати Node Host і окрему Protocol Plane
3.1. Застосунок не повинен створювати власний Iroh endpoint

Знайдені проєкти показують більш правильну модель:

Physical Node
└── Vida Node Host
    ├── Endpoint Manager
    ├── Relay Manager
    ├── ALPN Router
    ├── Service Registry
    ├── Local IPC
    ├── Admission Layer
    ├── Lifecycle Manager
    └── Diagnostics

Застосунок реєструє сервіс у Node Host, але не:

створює власний endpoint;
вибирає relay;
зберігає endpoint key;
відкриває довільний порт;
реалізує NAT traversal;
керує discovery.

peerline-host демонструє практичну модель одного composable host із сервісами, ALPN routing, UDS/WebSocket/Iroh transports, service registry та graceful shutdown. flexaccess-iroh додатково показує relay probing, failover і прив’язану до endpoint identity application-authentication.

Iroh маршрутизує прикладні протоколи за ALPN, а endpoint ticket містить інформацію для знаходження endpoint, але сам по собі не повинен трактуватися як повна предметна авторизація.

3.2. Один endpoint на фізичний вузол

За замовчуванням:

1 фізичний пристрій
→ 1 persistent Node Identity
→ 1 Iroh Endpoint
→ багато versioned application protocols

Окремі endpoint identities допускаються для:

жорсткої security isolation;
анонімного/public surface;
регульованих організацій;
окремого site runtime;
тестового середовища;
тимчасової sandbox-сесії.

Але створювати endpoint на кожен застосунок або workspace не потрібно.

3.3. Ідентичності треба остаточно розділити
AccountId       ≠ DeviceId

Endpoint key може бути:

замінений під час перевстановлення.

При цьому user, scope і resource IDs повинні залишатися стабільними.

Ітерація 5. Перебудувати безпеку навколо чітких шарів
5.1. П’ять рівнів перевірки

5.2. Необхідно типізувати tickets

Різні проєкти використовують слово ticket і як адресу, і як credential. pun прямо використовує possession of ticket як capability, а quackhole вкладає в ticket також token, який фактично дає доступ. Це зручно для окремих інструментів, але небезпечно як неявна загальна модель платформи.

BlobTicket	Hash, size, providers; доступ перевіряється окремо
DatasetTicket	Release і partitions
SessionTicket	Приєднання до room/agreement session

CapabilityTicket має містити:

audience;
actions;
resource selector;
expiration;
nonce;
delegation depth;
offline/export policy;
revocation reference.
5.3. KeyEpoch і реальна семантика відкликання

Ітерація 16. Які проєкти як використовувати
Як кандидати для фундаменту після spike
офіційний Iroh endpoint і transport;
Rust portable core;
embedded Rust bindings для mobile;
content-addressed blob protocol;
DuckDB/Arrow/Parquet як projection/query layer;
Wasm components для sandboxed logic.
Лише як архітектурні референси зараз
dstore — placement, repair, GC;
diaswarm — encrypted replicas, key epochs, revoke semantics;
peerline-host — node host і service routing;
flexaccess-iroh — relay failover і handshake;
iroh-co2-monitor — edge profile;
iroh-android-native — Android lifecycle;
ringdrop — verified resumable blobs;
quackhole — P2P query node;
bevy_iroh / openstream — rooms і media;
AgentLink — durable AI jobs;
arena0 — multi-party agreement runtime;
BLE/WebRTC transports — майбутні optional adapters.

Більшість цих свіжих проєктів є прототипами або ранніми реалізаціями. Вони достатньо корисні для перевірки меж компонентів, але недостатньо зрілі, щоб робити їх незамінними production dependencies.

Як функціональні референси
Twenty — object/app SDK і versioned apps;
Plane — work items, cycles, pages, views;
OpenProject — enterprise work management;
Formbricks — forms, audiences і distribution;
Documenso — document trust і signing;
PostHog — analytics, events, flags, traces.

Їхню предметну модель доцільно врахувати, але не переносити їхню DB-centric server architecture.

Остаточне рішення

Архітектуру потрібно підняти до наступної версії з такою центральною формулою:

PersonalVida — це не одна P2P-БД, а переносний application/data runtime, у якому Vault є межею володіння та експорту, профільні stores відповідають за різні види даних, Node Host — за мережу й протоколи, Data Contracts — за повторне використання, а зовнішні SaaS/S3/БД залишаються змінними providers.

Головна зміна порівняно з попереднім варіантом:

Було:
Vault + універсальні commits + Iroh sync

Стає:
Portable Vault Envelope
├── профільні semantic stores
├── content-addressed object store
├── optional availability fabric
├── query/projection plane
├── realtime/media plane
├── execution plane
└── shared Node Host із versioned protocols

Це не відмова від попередньої архітектури, а її необхідне розкладання на правильні технологічні й безпекові межі. Саме так вона залишатиметься мобільною та переносною, але при цьому зможе підтримувати великі довідники, marketplace, сайти, портали, чат, документи, AI-агентів, організації та спеціалізовану зовнішню інфраструктуру.
